## 1. 软件工程基础与过程模型

### 1.1 软件生命周期与五大基本流程 ⭐⭐⭐

**Q [⭐⭐⭐]【1.1.Q1】：什么是软件生命周期？软工的五大基本流程是什么？（北航真题）**

A：**软件生命周期**指软件从提出、开发、使用到最终废弃的全过程。**五大基本流程**（面试标准答法，按顺序）：

| 阶段       | 回答什么问题           | 主要产品         |
| -------- | ---------------- | ------------ |
| **需求分析** | 做什么              | 需求规格说明书（SRS） |
| **设计**   | 怎么做（概要设计 + 详细设计） | 设计说明书、UML 模型 |
| **编码实现** | 把设计翻译成程序         | 源代码          |
| **测试**   | 做对了没有            | 测试用例、测试报告    |
| **运行维护** | 交付之后怎么改          | 变更记录、新版本     |

**Q [⭐⭐]【1.1.Q2】：五大基本流程之间是什么关系？哪个阶段耗时最长？**

A：**前一阶段的输出就是后一阶段的输入**（需求文档 → 设计文档 → 代码 → 测试报告），所以是一条严格递进、可追溯的链条；完整过程还包含立项与可行性研究、计划、发布与退役。**维护阶段耗时最长**——占整个生命周期成本的 **50% 以上**，这正是"软件维护"要单独成章的原因。

### 1.2 过程模型对比 ⭐⭐⭐

**Q [⭐⭐⭐]【1.2.Q1】：常见的软件开发（过程）模型有哪些？各自优缺点与适用场景是什么？**

A：

| 模型       | 核心思想          | 优点          | 缺点          | 适用     |
| -------- | ------------- | ----------- | ----------- | ------ |
| **瀑布**   | 按阶段线性顺序推进     | 简单、文档齐全     | **需求变更代价大** | 需求明确   |
| **快速原型** | 先做可运行原型让用户提意见 | 需求容易澄清      | 原型容易被当成品    | 需求不明确  |
| **增量**   | 按功能分批交付       | 早期可用        | 架构需前瞻       | 大系统    |
| **螺旋**   | 风险驱动迭代        | **风险控制好**   | 复杂          | 高风险项目  |
| **敏捷**   | 小步快跑、拥抱变化     | **灵活、快速响应** | 文档少、大项目难管理  | 需求变化频繁 |

**Q [⭐⭐⭐]【1.2.Q2】：瀑布模型和敏捷开发有什么区别？（北航真题）**

A：

| 对比项  | 瀑布               | 敏捷                      |
| ---- | ---------------- | ----------------------- |
| 交付方式 | 阶段线性推进，最后一次性交付   | 迭代小步交付，**每轮都有可运行版本**    |
| 需求态度 | 前期冻结，变更代价大       | **拥抱变化**，欢迎后期调整需求       |
| 文档   | 文档驱动，文档齐全        | 可工作的软件 > 详尽的文档          |
| 客户参与 | 主要在前期与验收         | 客户/产品负责人**全程参与**        |
| 团队   | 分工明确、按阶段交接       | 自组织小团队、每日站会（Scrum 的常见实践） |
| 适用   | 需求明确稳定、合规性要求高的项目 | 需求不明确或变化频繁的项目           |

一句话：瀑布用"前期把需求定死"换"后期不需要返工"，敏捷用"容许需求变化"换"必须持续交付与持续集成"。

**Q [⭐⭐⭐]【1.2.Q3】：螺旋模型的特点是什么？为什么说它是"风险驱动"的？**

A：螺旋模型 = **瀑布 + 原型 + 风险分析**，把开发切成多轮螺旋，每轮四个象限：**制定计划 → 风险分析 → 实施工程 → 客户评估**。它每一轮迭代都专门做**风险分析**，把"可能做不成"的风险提前暴露并处理，因此适合大型、高风险项目；代价是复杂度高、需要专门的风险评估能力，客户也得愿意为风险分析买单。

### 1.3 瀑布模型的阶段 ⭐⭐

**Q [⭐⭐]【1.3.Q1】：瀑布模型有哪几个阶段？**

A：六阶段：**计划 / 可行性研究 → 需求分析 → 设计 → 编码 → 测试 → 运行维护**。各自产出：可行性分析报告与项目计划 → 需求规格说明书 → 设计说明书与 UML 模型 → 源代码与单元测试 → 测试用例与测试报告 → 变更记录与新版本。

**Q [⭐⭐]【1.3.Q2】：瀑布模型的特点和缺陷是什么？**

A：**特点**——阶段之间严格顺序推进、存在因果关系；每个阶段结束要**评审**（里程碑）；**文档驱动**，上一阶段文档是下一阶段的输入；发现问题必须**回溯**到前面阶段，代价大。
**缺陷**——**测试滞后**：缺陷发现得越晚，修复代价越大（需求阶段的错误要到测试阶段才暴露，成本放大数十倍）；需求变更代价高。V 模型就是为强化"测试与开发的对应关系"提出的变体。

### 1.4 软件工程三要素 ⭐⭐

**Q [⭐⭐]【1.4.Q1】：软件工程的三要素是什么？**

A：**方法 + 工具 + 过程**：

| 要素     | 含义                            | 举例                         |
| ------ | ----------------------------- | -------------------------- |
| **方法** | 完成软件开发的技术手段，回答"怎么做出软件"        | 结构化方法、面向对象方法、需求/设计/测试方法    |
| **工具** | 支撑方法的自动化软件                    | IDE、Git、建模工具、JUnit、Jenkins |
| **过程** | 把方法和工具组织起来的工作框架，回答"按什么步骤和顺序做" | 瀑布、增量、螺旋、敏捷                |

一句话：方法是"技术手段"，工具是"支撑环境"，过程是"管理与组织框架"，三者缺一不可。

### 1.5 软件工程需要遵守的规范 ⭐⭐

**Q [⭐⭐]【1.5.Q1】：软件工程需要遵守哪些规范？**

A：规范不是某一条规则，而是分层的约定体系：

| 层面         | 规范内容                                                          |
| ---------- | ------------------------------------------------------------- |
| **过程规范**   | 遵循选定的过程模型；阶段评审、里程碑、文档齐套（GB/T 8566《软件生存周期过程》）                  |
| **文档规范**   | 需求规格说明书、设计说明书、测试报告的模板与内容要求（GB/T 8567《计算机软件文档编制规范》）            |
| **编码规范**   | 命名、注释、格式、异常处理、日志的统一约定（Google Style、阿里 Java 开发手册）+ 代码评审 + 静态检查 |
| **配置管理规范** | 版本控制与分支策略（如 Git Flow）、变更控制流程（申请→评审→实施→回归）                     |
| **测试规范**   | 用例设计方法、覆盖率门限、缺陷分级与跟踪流程、出口准则                                   |
| **管理规范**   | 进度/成本/质量/风险管理；用 CMMI 成熟度等级衡量组织的规范化程度                          |

一句话：本质是让开发**可重复、可追溯、可交接**——把"个人的手艺"变成"团队的流程"。

### 1.6 程序复杂度的度量 ⭐⭐⭐

**Q [⭐⭐⭐]【1.6.Q1】：软件工程中如何衡量程序的复杂度？**

A：

| 方法               | 度量什么             | 关键指标                                                                       |
| ---------------- | ---------------- | -------------------------------------------------------------------------- |
| **代码行 LOC**      | 规模               | 有效代码行数，简单但与语言强相关                                                           |
| **功能点 FP**       | 从**用户视角**度量的功能规模 | 5 类要素（输入/输出/查询/内部逻辑文件/外部接口文件）加权，再用技术复杂度因子调整                                |
| **McCabe 环形复杂度** | 程序控制流的**逻辑复杂度**  | $V(G)=E-N+2$ = 判定节点数 + 1 = 独立路径数                                           |
| **Halstead 复杂度** | 从算子/操作数度量体积与难度   | 体积 $V=N\log_2 n$，难度 $D=\frac{n_1}{2}\cdot\frac{N_2}{n_2}$，工作量 $E=D\cdot V$ |
| **结构度量**         | 模块结构质量           | 扇入（被调用次数，越高复用越好）、扇出（调用次数，越高越复杂）、耦合与内聚                                      |
| **面向对象度量 CK**    | 类的设计质量           | WMC（方法数加权）、DIT（继承深度）、NOC（子类数）、CBO（耦合类数）、RFC（响应集）、LCOM（内聚缺乏度）               |

**Q [⭐⭐⭐]【1.6.Q2】：McCabe 环形复杂度怎么算？它有什么用？**

A：$V(G)=E-N+2$（$E$ 为边数、$N$ 为节点数），等价于**判定节点数 + 1**，也等价于**线性无关路径数**。三个用处：① 直接告诉你**基本路径覆盖需要设计几条用例**；② 判断模块是否过于复杂，工程上一般要求 $V(G)\le 10$；③ 与代码行数一起估算测试与维护工作量。

### 1.7 项目管理铁三角 ⭐⭐

**Q [⭐⭐]【1.7.Q1】：项目管理铁三角是什么？**

A：**进度、成本、质量**三者互相制约——要更快就得加成本或降质量，要更高质量就得加时间或加成本，三者不可能同时最优。项目管理的本质就是在这三者之间做取舍与权衡（把"范围"也算进来，就是常说的**四约束**）。

## 2. 需求工程

### 2.1 需求的类型 ⭐⭐

**Q [⭐⭐]【2.1.Q1】：软件需求分为哪几类？**

A：

| 类型        | 含义            | 举例             |
| --------- | ------------- | -------------- |
| **功能需求**  | 系统必须做什么       | "用户可以搜索商品"     |
| **非功能需求** | 系统必须怎么样（质量属性、约束） | "响应时间 < 200ms" |
| **领域需求**  | 来自应用领域的约束     | "金额保留 2 位小数"   |

补充一个常被追问的角度：按**抽象层次**还可分为**业务需求**（为什么要做）、**用户需求**（用户要完成什么）、**系统需求**（系统具体做成什么样）——功能需求与非功能需求都属于系统需求。

### 2.2 需求工程的过程与需求变更管理 ⭐⭐

**Q [⭐⭐]【2.2.Q1】：需求工程包含哪些活动？（北航真题）**

A：五步：**需求获取 → 需求分析 → 需求规格说明 → 需求验证 → 需求管理**。

| 活动        | 做什么                                | 产出        |
| --------- | ---------------------------------- | --------- |
| **需求获取**  | 访谈、问卷、观察、原型演示、文档分析                 | 原始需求素材    |
| **需求分析**  | 建模（用例图 / 活动图 / 领域类图 / DFD），发现冲突与不一致 | 分析模型      |
| **需求规格说明** | 写成 SRS，作为后续设计与验收的基准                | 需求规格说明书   |
| **需求验证**  | 评审、原型演示、用例检查，确认需求正确、完整、一致、可验证      | 确认后的需求基线  |
| **需求管理**  | 需求基线控制、追踪矩阵、变更控制                   | 变更记录、追踪表  |

**Q [⭐⭐]【2.2.Q2】：需求变更了怎么办？**

A：走**变更控制流程**：① **提出变更申请**；② **影响分析**（评估对进度、成本、设计、测试的影响）；③ **变更控制委员会（CCB）审批**；④ 批准后**修改需求文档与基线**，同步更新设计与代码；⑤ **实施并做回归测试**。核心思想：变更不可怕，可怕的是"私下改"——所有变更都要**留痕、评估、可追溯**。

## 3. 软件设计

### 3.1 高内聚低耦合 ⭐⭐⭐

**Q [⭐⭐⭐]【3.1.Q1】：什么是内聚？内聚分哪几种（从强到弱）？**

A：**内聚**衡量**模块内部**各元素结合的紧密程度，越高越好：

| 内聚类型 | 强度     | 说明            |
| ---- | ------ | ------------- |
| 功能内聚 | **最强** | 所有元素完成同一功能    |
| 顺序内聚 | 强      | 前一元素输出=后一元素输入 |
| 通信内聚 | 中      | 操作同一数据集       |
| 逻辑内聚 | 弱      | 逻辑相关但功能不同     |
| 偶然内聚 | **最弱** | 无关系硬凑         |

**Q [⭐⭐⭐]【3.1.Q2】：什么是耦合？耦合分哪几种（从弱到强）？**

A：**耦合**衡量**模块之间**依赖的紧密程度，越低越好：

| 耦合类型  | 强度     | 说明               |
| ----- | ------ | ---------------- |
| 非直接耦合 | **最弱** | 无直接联系            |
| 数据耦合  | 弱      | 只传数据（参数）         |
| 标记耦合  | 中      | 传数据结构（整个记录/对象）    |
| 控制耦合  | 较强     | 传控制信息（用标志位指挥对方分支） |
| 内容耦合  | **最强** | 直接访问另一模块内部         |

**Q [⭐⭐⭐]【3.1.Q3】：为什么模块设计要追求"高内聚低耦合"？**

A：内聚高 → 模块职责单一，好理解、好测试、好复用，改一处不会牵动别处；耦合低 → 模块间依赖少，某个模块内部变动不容易波及全局，系统更易扩展、替换、并行开发。黄金组合是**功能内聚 + 数据耦合**。

### 3.2 常见设计模式 ⭐⭐

**Q [⭐⭐]【3.2.Q1】：设计模式分为哪几类？各有哪些代表模式？（北航真题）**

A：按 GoF 分三类：

| 类型      | 代表模式                  | 核心思想       |
| ------- | --------------------- | ---------- |
| **创建型** | 单例、工厂、抽象工厂、建造者、原型     | 控制对象的创建方式  |
| **结构型** | 适配器、装饰器、代理、组合、外观      | 组合对象获得新结构  |
| **行为型** | 观察者、策略、状态、模板方法、责任链    | 对象间通信与职责分配 |

**Q [⭐⭐]【3.2.Q2】：单例、工厂、观察者模式分别解决什么问题？**

A：**单例**保证一个类**只有一个实例**并提供全局访问点（数据库连接池、配置管理器），代价是全局状态难以测试；**工厂**把"创建什么对象"从调用方剥离，创建逻辑不暴露，新增产品时不必改客户端；**观察者**建立一对多依赖，主题状态变化时**自动通知**所有观察者，是事件驱动 / 发布订阅模式的基础。

### 3.3 面向对象 vs 面向过程 ⭐⭐⭐

**Q [⭐⭐⭐]【3.3.Q1】：面向对象与面向过程的软件工程有什么区别？（可从需求分析、设计两方面回答）**

A：

| 维度      | 面向过程                         | 面向对象                                |
| ------- | ---------------------------- | ----------------------------------- |
| 关注点     | 实现的具体**过程与因果关系**（先做什么、再做什么）  | **对象（独立体）能完成哪些功能**                  |
| 最小单位    | 函数                           | 类 / 对象                              |
| 需求分析的思路 | 以**功能**为线索分解：数据流图（DFD）、功能分解图 | 以**现实世界实体**为线索建模：用例图、领域（概念）类图       |
| 设计的思路   | 自顶向下、逐步求精，产出模块结构图            | 识别类与对象、定义属性与操作，用**封装/继承/多态**组织，产出类图 |
| 耦合与扩展   | 耦合度高，**一环出问题整个系统受牵连**，扩展力差   | 耦合度低，扩展力强，更容易处理复杂的业务逻辑              |
| 复用性     | 没有"独立体"概念，**难以组件复用**         | 封装 + 继承 + 多态，**组件复用性强**             |
| 成本      | 前期投入低、开发快                    | 前期投入高，需要大量系统分析与设计                   |
| 适用场景    | 业务逻辑比较简单、流程固定的程序             | 业务复杂、需求易变、规模大的系统                    |

一句话：面向过程关注"**怎么做**"，面向对象关注"**谁来做**"；需求变更时 OO 的改动范围更小，这是它"低耦合、易扩展、可复用"的直接结果，代价是前期投入更高。

### 3.4 UML 图分类与泳道图 ⭐⭐⭐

**Q [⭐⭐⭐]【3.4.Q1】：UML 有哪些图？**

A：UML 2.x 共 **13 种** = 结构图（静态）**6 种** + 行为图（动态）**7 种**：

| 类别  | 图      | 说明                              |
| --- | ------ | ------------------------------- |
| 结构图 | **类图** | 类、属性、操作及类间关系（关联/聚合/组合/泛化/实现/依赖） |
| 结构图 | 对象图    | 某一时刻的对象实例及它们之间的链接               |
| 结构图 | 包图     | 包以及包之间的依赖与组织关系                  |
| 结构图 | 组件图    | 构件及其对外接口（实现视角）                  |
| 结构图 | 部署图    | 节点与构件的物理部署（硬件拓扑）                |
| 结构图 | 组合结构图  | 类的内部结构（部件、端口、连接件）               |
| 行为图 | **用例图** | 参与者与用例，描述系统对外的功能                |
| 行为图 | **顺序图** | 按**时间顺序**描述对象间的消息交互             |
| 行为图 | 通信图    | 描述对象交互，强调对象之间的**链接结构**          |
| 行为图 | **活动图** | 业务流程/控制流，支持判断、并发、泳道             |
| 行为图 | **状态机图** | 一个对象的状态及状态之间的转移                 |
| 行为图 | 定时图    | 交互过程中对**时间约束**的描述               |
| 行为图 | 交互概览图  | 活动图与顺序图的混合（交互的概览）               |

**Q [⭐⭐⭐]【3.4.Q2】：什么是泳道图？泳道里有什么？**

A：泳道图**不是 UML 的第 14 种图**，UML 官方术语叫**活动分区（activity partition）**，"泳道"只是行业俗称（源自跨职能流程图 / BPMN 的 lane）。做法是用若干条平行"泳道"把**活动按执行者**（角色/部门/系统）分区，每条泳道只放它负责的活动。
**泳道里有什么**：泳道名（负责的参与者）、活动节点、控制流（判断、分叉、汇合、合并）、开始与结束节点、对象流（传递的数据）。
**作用**：一眼看出"**谁负责哪一步**"，适合跨部门/跨角色的业务流程与责任划分。一句话：**泳道图 ⊂ 活动图**——不加泳道照样是活动图，加了泳道只是多了一层"按执行者分区"。

**Q [⭐⭐]【3.4.Q3】：类图中类与类之间有哪几种关系？各自的记法是什么？**

A：六种：

| 关系            | 含义                        | 记法                    |
| ------------- | ------------------------- | --------------------- |
| **关联**        | 类之间有稳定联系                  | 实线                    |
| **聚合**        | 整体—部分，部分**可独立存在**（课程—教师）  | 空心菱形 + 实线（菱形指向整体）     |
| **组合**        | 整体—部分，部分**随整体消亡**（订单—订单项） | 实心菱形 + 实线（菱形指向整体）     |
| **泛化**        | 继承关系（is-a）                | 空心三角 + 实线（指向父类）       |
| **实现**        | 类实现接口                     | 空心三角 + 虚线（指向接口）       |
| **依赖**        | 临时使用（作参数、局部变量）            | 虚线箭头（指向被依赖者）          |

**Q [⭐]【3.4.Q4】：顺序图和通信图、活动图和状态机图分别有什么区别？**

A：**顺序图 vs 通信图**：两者语义等价，都描述对象交互；顺序图**纵向铺时间**（生命线 + 自上而下的消息，强调先后），通信图**横向铺对象**（对象间连线 + 编号 `1: 2: 3:`，强调谁和谁有链接）。被问"时序"要答**顺序图**。
**活动图 vs 状态机图**：活动图画**一条流程**被走一遍（步骤先后、可并发、可加泳道表示责任人）；状态机图画**同一个对象**由外部事件驱动的状态迁移（状态 + 事件 + 转移，可循环）。判断技巧：出现"谁先谁后、分支并发"→ 活动图；出现"一个对象的生命周期、事件触发改变状态"→ 状态机图。

**Q [⭐]【3.4.Q5】：用例图中 include 和 extend 有什么区别？**

A：**«include»（包含）**表示**必然发生**的公共行为被抽出去复用——基用例每次执行都会走它（如"下单"总要"校验库存"），箭头由基用例指向被包含用例；**«extend»（扩展）**表示**可选/条件性**的增量行为（如"下单"在满足条件时可扩展"使用优惠券"），箭头由扩展用例指向基用例。一句话：include 是"一定会做的公共步骤"，extend 是"有时才做的额外分支"。

## 4. 软件实现与编码

### 4.1 结对编程 ⭐⭐

**Q [⭐⭐]【4.1.Q1】：什么是结对编程？它有哪些术语？**

A：**结对编程（Pair Programming）**是极限编程（XP）的核心实践之一——两名开发者共用一台机器、一个键盘，共同完成同一段代码。

| 术语                       | 含义                                  |
| ------------------------ | ----------------------------------- |
| **Driver（驾驶员 / 操作者）**    | 手放在键盘上的人，专注把当前这行代码写出来               |
| **Navigator（领航员 / 观察者）** | 不碰键盘的人，负责审查代码、思考下一步策略、发现遗漏与隐患       |
| **角色互换（Switch）**         | 每隔一段时间（如 15–30 分钟或一个测试周期）交换角色       |
| **Ping-Pong 结对**         | 一人先写一个失败的测试，另一人写实现让它通过，交替推进（TDD 风格） |
| **重新配对（Re-pairing）**     | 每个任务完成后重组搭档，避免固定配对形成的认知盲区           |

**Q [⭐⭐]【4.1.Q2】：结对编程的优缺点是什么？两个人写同一段代码是不是浪费？**

A：**价值**——**实时的代码评审**（把事后评审变成过程中评审）、知识共享（避免"只有一个人懂这块代码"）、显著降低缺陷率、新人上手快；**代价**——短期人力投入近似翻倍。所以它适合复杂或高风险模块，不适合需要长时间静默思考的探索性任务。一句话：用一部分人力换掉大量返工与沟通成本。

### 4.2 重载 vs 重写 ⭐⭐⭐

**Q [⭐⭐⭐]【4.2.Q1】：重载和重写的定义与区别是什么？**

A：

| 对比项  | 重载 Overload            | 重写 Override             |
| ---- | ---------------------- | ----------------------- |
| 发生位置 | **同一个类**中（同一作用域内）      | **子类与父类**之间（必须有继承关系）    |
| 方法名  | 相同                     | 相同                      |
| 参数列表 | **必须不同**（类型 / 个数 / 顺序） | 必须相同                    |
| 返回值  | 无限制（但不能只靠返回值区分重载）      | 相同或**协变**（子类类型）         |
| 绑定时机 | **编译期**（静态绑定 → 静态多态）   | **运行期**（动态绑定 → 动态多态）    |
| 访问权限 | 无限制                    | **不能缩小**（可以放大）          |
| 抛出异常 | 无限制                    | 不能抛出更宽的**受检异常**         |
| 注解   | 无                      | `@Override`（Java，编译期校验） |

**Q [⭐⭐]【4.2.Q2】：重写要遵守什么规则？"两同两小一大"指什么？**

A：重写规则可记成"**两同两小一大**"：方法名与参数列表**相同**（两同）；**返回值和抛出的受检异常不放大**（两小）；**访问权限不缩小**（一大）。绑定时机决定多态类型——重载在**编译期**按静态类型确定调用版本，叫**静态多态**；重写在**运行期**按实际对象类型确定调用版本，叫**动态多态**（这才是 OO 多态的本体）。

### 4.3 可变对象 vs 不可变对象 ⭐⭐

**Q [⭐⭐]【4.3.Q1】：可变对象和不可变对象的定义与区别？**

A：

| 对比项   | 可变对象                                                               | 不可变对象                                                                 |
| ----- | ------------------------------------------------------------------ | --------------------------------------------------------------------- |
| 定义    | 创建后**内部状态可以被修改**                                                   | 创建后**状态不可改变**，任何"修改"都返回一个新对象                                          |
| 例子    | Java：`StringBuilder`、数组、`ArrayList`；Python：`list` / `dict` / `set` | Java：`String`、`Integer` 等包装类、`BigDecimal`；Python：`str` / `tuple` / 数字 |
| 线程安全  | 需要加锁等同步手段                                                          | **天然线程安全**，可以自由共享                                                     |
| 作为哈希键 | 有风险（修改后 hash 变了就找不到）                                               | 安全，`hashCode` 可以缓存                                                    |
| 代价    | 修改没有额外开销                                                           | 每次修改都新建对象，有内存与性能开销                                                    |

**Q [⭐⭐]【4.3.Q2】：怎么实现一个不可变对象？final 能保证对象不可变吗？**

A：实现五步——类声明为 `final`（防继承改写行为）；所有字段 `private final`；不提供 setter；构造时对可变类型做**防御性拷贝**；不把内部可变引用暴露出去（返回时也拷贝）。
**不能**——Java 的 `final` 只保证**引用不可变**，不保证被引用对象的内容不可变：`final List<String> list` 里的 list 仍可 `add`。所以要靠"防御性拷贝 + 不暴露内部引用"配合，光加 `final` 不够。

## 5. 软件测试

### 5.1 白盒 vs 黑盒 ⭐⭐⭐

**Q [⭐⭐⭐]【5.1.Q1】：白盒测试和黑盒测试的定义与区别是什么？（北航真题）**

A：**白盒测试**：知道程序内部结构，按**内部逻辑**设计用例，又称结构测试、逻辑驱动测试。**黑盒测试**：不管内部结构，只依据**需求规格说明书**从输入输出角度验证功能，又称功能测试、数据驱动测试。

|         | 白盒测试          | 黑盒测试          |
| ------- | ------------- | ------------- |
| 知道内部结构？ | **是**         | 否             |
| 关注点     | 逻辑覆盖          | 功能正确性         |
| 方法      | 语句/分支/路径/条件覆盖 | 等价类划分/边界值/因果图 |
| 时机      | 单元测试          | 系统测试          |

### 5.2 静态测试 vs 动态测试 ⭐⭐⭐

**Q [⭐⭐⭐]【5.2.Q1】：静态测试和动态测试的定义与区别是什么？**

A：**静态测试**不运行程序，审查代码、文档、模型（代码评审、走查、桌面检查）并用静态分析工具（lint、SonarQube）检查；**动态测试**运行程序，按白盒/黑盒方法设计用例执行，比较实际输出与预期输出。

|        | 静态测试                                       | 动态测试                       |
| ------ | ------------------------------------------ | -------------------------- |
| 是否运行程序 | **不运行**                                    | **运行**                     |
| 测试对象   | 代码、文档、模型（需求规格、设计图）                         | 可执行程序                      |
| 方法     | 人工审查（代码评审、走查、桌面检查）+ 静态分析工具（lint、SonarQube） | 按白盒/黑盒方法设计用例执行，比较实际输出与预期输出 |
| 优点     | 做得早（需求/设计阶段即可）、发现缺陷的成本低                    | 能验证真实运行行为（性能、并发、异常）        |
| 缺点     | 无法验证运行期行为                                  | 依赖环境，缺陷发现得晚                |

注意：**白盒/黑盒**是按"是否知道内部结构"分，**静态/动态**是按"是否执行程序"分，是两个不同维度，别混着答。

### 5.3 覆盖率递增 ⭐⭐⭐

**Q [⭐⭐⭐]【5.3.Q1】：白盒测试的覆盖准则由弱到强怎么排？最强和最弱分别是什么？**

A：$\text{语句覆盖} < \text{判定覆盖} < \text{条件覆盖} < \text{判定/条件覆盖} < \text{路径覆盖}$。**语句覆盖最弱**（每个语句至少执行一次），**路径覆盖最强**（每条路径都走一遍）。
补充：判定/条件覆盖要求"每个判定取真取假各一次 + 每个条件取真取假各一次"，但它**仍不一定覆盖全部路径**（条件组合未穷尽），所以还有更强的**条件组合覆盖**；工程上通常要求判定覆盖，核心模块再补路径覆盖。

### 5.4 测试层次 ⭐⭐

**Q [⭐⭐]【5.4.Q1】：软件测试分为哪几个层次？各自测什么？**

A：

| 层次       | 对象    | 方法                        |
| -------- | ----- | ------------------------- |
| **单元测试** | 单个模块  | 白盒为主                      |
| **集成测试** | 模块间接口 | 增式（自顶向下 / 自底向上 / 三明治）与非增式 |
| **系统测试** | 整个系统  | 黑盒为主                      |
| **验收测试** | 用户验收  | α 测试（开发者环境）/ β 测试（用户环境）   |

**Q [⭐⭐]【5.4.Q2】：测试和调试有什么区别？**

A：**测试 = 找 bug**——系统化、可规划，按用例执行，目的是**证明程序有错**；**调试 = 修 bug**——在发现错误之后分析定位并修复，目的是**消除错误**。一句话：测试证明"有问题"，调试找出"问题在哪、怎么解决"。

### 5.5 单元测试 ⭐⭐⭐

**Q [⭐⭐⭐]【5.5.Q1】：什么是单元测试？（北航真题）**

A：**定义**——对软件中**最小可测试单元**（函数 / 方法 / 类）进行的测试，通常由**开发者自己编写**并随代码一起维护，是测试体系的最低一层。**要点**：一般以**白盒方法**设计用例（语句/分支/路径覆盖），辅以黑盒的边界值；被测试单元若依赖尚未完成的模块，用**桩模块**替代下层、用**驱动模块**模拟上层调用；常用框架 JUnit / pytest / GoogleTest，做法是"准备数据 → 调用被测方法 → 断言结果"；它是**持续集成（CI）**中每次提交都要自动跑的第一道防线，也是重构的安全网。

**Q [⭐⭐]【5.5.Q2】：桩模块和驱动模块分别是什么？**

A：都是**替代未完成模块的临时替身**，方向相反——**桩模块（Stub）**模拟**被被测模块调用的下层模块**（自底向上测试用），只需返回预设数据；**驱动模块（Driver）**模拟**调用被测模块的上层模块**（自顶向下测试用），负责传参、发起调用、接收结果。记忆法：**桩在下、驱动在上**——桩"被调用"，驱动"去调用"。

### 5.6 软件测试的流程 ⭐⭐⭐

**Q [⭐⭐⭐]【5.6.Q1】：软件测试的流程是什么？**

A：五步：

| 步骤              | 做什么                                  | 产出        |
| --------------- | ------------------------------------ | --------- |
| **1. 需求分析**     | 分析需求是否可行、是否可测，梳理出测试点                 | 测试需求      |
| **2. 编制测试计划**   | 确定测试范围、策略、资源、进度、环境                   | 测试计划      |
| **3. 编写测试用例**   | 用等价类/边界值/覆盖准则设计用例并评审（用例是**指导测试的文档**） | 测试用例、测试数据 |
| **4. 执行测试**     | 搭环境跑用例，**提交缺陷**、跟踪修复、做**回归测试**       | 缺陷单、测试记录  |
| **5. 编写测试总结报告** | 统计缺陷与覆盖率，判断是否达到出口准则                  | 测试总结报告    |

其中**写用例是核心**——用例质量直接决定测试的有效性；整体执行顺序按"**单元 → 集成 → 系统 → 验收**"递进。

**Q [⭐⭐]【5.6.Q2】：缺陷的生命周期是怎样的？测试什么时候算结束？**

A：**缺陷生命周期 = 提交 → 指派 → 修复 → 验证 → 关闭**，若验证没通过则**重开**（回到指派）。
**测试出口准则**（测试结束的判断依据）：测试用例执行率达标；覆盖率达标（如判定覆盖 100%）；缺陷收敛——严重/主要缺陷全部关闭、新增缺陷速率明显下降；需求已全部覆盖且关键功能验证通过。

### 5.7 回归测试 ⭐⭐⭐

**Q [⭐⭐⭐]【5.7.Q1】：什么是回归测试？它有什么作用？**

A：**定义**——产品修正了缺陷或增加了功能后生成新的版本，对**这个新版本**重新进行测试，就叫回归测试。**作用有两条，务必都答**：① **验证原有错误是否确实被修正了**——确认修复真的生效；② **发现因修改而可能引入的新错误**——改动常常"修好一个、弄坏一个"，回归测试是防止老功能退化的安全网。

**Q [⭐⭐]【5.7.Q2】：回归测试什么时候做？怎么才能做得动？**

A：**触发时机**——修复缺陷后、新增功能后、重构后、运行环境或依赖变更后。**范围策略**——**全量回归**（慢但保险）与**选择性回归**（基于**影响分析**挑出受影响模块和用例，更常用）。**落地关键**——回归测试**必须自动化**，把回归用例固化成脚本并接入 CI，否则每次都要人工重跑，成本高到做不动。

## 6. 软件维护

### 6.1 软件维护的四种类型 ⭐⭐

**Q [⭐⭐]【6.1.Q1】：软件维护分为哪几类？各自占比多少？**

A：

| 类型        | 占比       | 说明       |
| --------- | -------- | -------- |
| **完善性维护** | 最多(50%+) | 增加新功能    |
| **适应性维护** | 20%+     | 适应环境变化   |
| **改正性维护** | ~20%     | 修复缺陷     |
| **预防性维护** | 最少       | 提前改善可维护性 |

一句话：**完善性维护占比最高**说明"交付之后继续加功能"才是软件生命周期的常态，而不是"写完就不动了"——这也解释了为什么维护阶段耗掉整个生命周期 50% 以上的成本。
