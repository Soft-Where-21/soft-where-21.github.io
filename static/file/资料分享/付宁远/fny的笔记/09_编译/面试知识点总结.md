# 编译原理 - 保研面试知识点总结

> [!info]+ 复习策略  
> 编译原理的核心逻辑是"从源代码到可执行程序的翻译流水线"。面试考编译，重点不在手写分析器，而在**理解每一步在做什么、为什么这样设计**。记住"编译=前端+后端"，前端跟语言有关，后端跟机器有关，中间代码是分界线。
>
> 重点标注：⭐⭐⭐ 高频 | ⭐⭐ 中频 | ⭐ 低频但重要
>
> 北航软院面试高频考点：从代码到可执行程序的步骤、词法/语法/语义分析、CFG、LL/LR分析

---

> [!abstract]+ 学科总览  
> 编译原理按照"翻译流水线"组织——每个阶段处理源程序的一个层面，逐层降低抽象级别：
>
> - **前端**（与语言有关）：词法分析→语法分析→语义分析→中间代码生成。前端把字符流变成结构化的中间表示，回答"这段程序是什么意思"。
> - **后端**（与机器有关）：代码优化→目标代码生成。后端把中间表示变成特定机器的指令，回答"怎样高效执行"。
> - **贯穿始终**：符号表管理、错误处理。
>
> 章节逻辑：**编译过程总览**（从源码到可执行、编译 vs 解释）→ **文法**（定义语言的"语法规则"）→ **词法分析**（字符→Token，用正则/自动机）→ **语法分析**（Token→语法树，用 CFG+LL/LR）→ **语义分析与中间代码**（语法树→带语义的三地址码）→ **运行时环境**（为代码生成提供存储模型）→ **代码优化与生成**（三地址码→目标机器指令）。
>
> 暗线：**每一层都是上一层的"消费者"——词法分析器消费字符流产出 Token 流，语法分析器消费 Token 流产出语法树，以此类推**。编译的每个阶段就像工厂流水线，每个工位只看前一个工位的产出。

## 0. 编译过程总览

> [!note]+ 章节导引  
> **本章知识点之间的关系**：这是全书的"地图"——用一条链把整条翻译流水线串起来：**从源代码到可执行程序**（预处理→编译→汇编→链接）→ **编译内部的五个阶段**（词法/语法/语义/中间代码/目标代码）→ **两种执行方式**（编译执行 vs 解释执行）→ **贯穿全程的两条线**（符号表、错误处理）。
>
> **与后续章节的关系**：后面每一章深入流水线的某一段，本章回答"在哪一步、为什么这么分"。
>
> **与学科的关系**：北航软院面试的经典开场题就是"从代码到可执行程序的步骤"，属于必须张口就来的内容。

### 0.1 从源代码到可执行程序的完整流程 ⭐⭐⭐

| 步骤        | 工具  | 输入 → 输出          | 做什么                              |
| --------- | --- | ---------------- | -------------------------------- |
| **① 预处理** | cpp | `.c` → `.i`      | 展开 `#include`、宏替换、去注释、条件编译       |
| **② 编译**  | cc1 | `.i` → `.s`      | 词法→语法→语义→中间代码→优化→汇编代码（真正的"编译原理"） |
| **③ 汇编**  | as  | `.s` → `.o`      | 汇编指令 → 机器指令，生成可重定位目标文件           |
| **④ 链接**  | ld  | `.o` + 库 → 可执行文件 | 符号解析、重定位、合并段；分静态链接与动态链接          |

> [!tip]+ 一句话  
> 广义的"编译"= 预处理 + 编译 + 汇编 + 链接；狭义的"编译"只是第 ② 步。被问"从代码到可执行程序"，**先答这四步，再展开第 ② 步内部的五个阶段**（词法、语法、语义与中间代码、优化、目标代码生成）。

**编译器内部的七个逻辑部分**（龙书划分）：上述五大阶段 + **符号表管理**、**错误处理**——后两者**贯穿全过程**，不是独立的一遍。

> [!tip]+ 前端 vs 后端  
> 前端（与源语言有关）：词法、语法、语义、中间代码生成；后端（与目标机器有关）：优化、目标代码生成。**中间代码是分界线**——一种前端 + 多个后端 = 一种语言编译到多种机器。

### 0.2 词法分析 / 语法分析 / 语义分析：定义与作用 ⭐⭐⭐

| 阶段       | 输入 → 输出          | 定义（做什么）                                           | 作用                             | 典型错误                    |
| -------- | ---------------- | ------------------------------------------------- | ------------------------------ | ----------------------- |
| **词法分析** | 字符流 → Token 流    | 按**正则文法**把字符拼成"词素"，识别关键字、标识符、常数、运算符               | 屏蔽字符细节，给后续阶段统一的 Token          | 非法字符、标识符写法不合法（如 `1abc`） |
| **语法分析** | Token 流 → 语法树    | 按**上下文无关文法（CFG）**判断 Token 序列能否构成合法句子，构造语法树 | 确定程序的**结构**（谁嵌套在谁里），是后续一切分析的基础 | 括号不匹配、缺分号、`if` 缺 `else` |
| **语义分析** | 语法树 → 带语义信息的中间表示 | 检查**上下文有关**的约束：类型是否匹配、变量是否先声明、运算是否合法，并填符号表        | 保证程序"讲得通"，为代码生成提供类型和存储位置       | 类型不匹配、变量未声明、实参形参不符      |

> [!tip]+ 面试一句话  
> "词法分析认**词**（字符→Token，用正则/DFA），语法分析认**句**（Token→语法树，用 CFG+LL/LR），语义分析认**意思**（类型检查、作用域、声明先于使用）。前两者解决'写得对不对'，后者解决'说得通不通'。"

### 0.3 编译执行 vs 解释执行 ⭐⭐

| 维度     | 编译执行                      | 解释执行                       |
| ------ | ------------------------- | -------------------------- |
| 翻译时机   | 运行**前**一次性翻译成目标代码         | 运行**时**逐句翻译并立即执行           |
| 运行速度   | **快**（无翻译开销，可做全局优化）       | 慢（反复翻译，难做全局优化）             |
| 启动速度   | 慢（要先编译链接）                 | **快**（边读边执行）               |
| 可移植性   | 差（目标代码与机器/OS 相关，换平台要重新编译） | **好**（有解释器就能跑同一份源码）        |
| 体积与内存  | 目标文件大，运行时不需解释器            | 需常驻解释器，源码即程序               |
| 调试与动态性 | 难（源码与目标码对应弱），不能边跑边改       | **易**（报错直接对应源码行），支持动态求值    |
| 代表     | C/C++、Go、Rust             | Python、Shell、早期 JavaScript |

> [!tip]+ 折中方案  
> **字节码 + 虚拟机（JVM/CLR）**：先编译成与平台无关的字节码，运行时由 **JIT** 把热点代码即时编译成机器码——兼得"可移植"与"运行快"。注意 Python 的 `.pyc` 只是省掉词法/语法分析，**仍然是解释执行**。

### 0.4 错误处理与错误恢复 ⭐⭐

**错误按发现的阶段分类**：词法错误（非法字符）、语法错误（结构不合法）、语义错误（类型/作用域不符）；**逻辑错误**编译期发现不了。编译器发现错误后**不会立刻停下**，而是报告并**设法继续**，尽量把所有错误一次报完。

| 恢复策略       | 做法                                       |
| ---------- | ---------------------------------------- |
| **恐慌模式恢复** | 丢弃输入符号，**直到遇到同步记号**（如 `;`、`}`、语句结束）再继续分析 |
| **短语层次恢复** | 在出错点附近做最小修正（补一个分号、删一个多余的括号），然后继续         |
| **出错产生式**  | 预先为常见错误定义产生式，识别到错误就按"假装正确"的产生式继续         |
| **全局纠正**   | 找与输入编辑距离最小的合法串（理论上最优，代价过大，实际很少用）         |

> [!tip]+ "遇到错误后处理几个字符？"  
> **没有固定的字符数**——取决于恢复策略：恐慌模式的答案是"**丢弃若干字符，直到遇到同步记号**"，这个"若干"可能是 1 个字符，也可能是一整行，由**同步集**决定，而不是"固定处理 3 个字符"。
>
> 如果问的是**分析器的向前看能力**：LL(1) 只看 **1 个** Token，LR 也只看 **1 个**展望符，只有 LR(k) 才看 k 个。
>
> 要点：错误恢复的目标不是"把程序改对"，而是**避免第一个错误引发连锁报错**，把错误尽量定位在一处。

## 1. 文法与语言

> [!note]+ 章节导引  
> **本章知识点之间的关系**：文法是编译的"语法规则"——定义什么样的字符串是合法程序。逻辑链：**乔姆斯基文法分类**（0/1/2/3 型，越来越严格）→ **CFG**（2型文法，编程语言的文法类型）→ **推导与归约**（生成/识别字符串的两个方向）→ **短语/句柄/素短语**（语法分析要归约的对象）→ **FIRST/FOLLOW 集**（LL 分析的核心工具）。
>
> **与上一章的关系**：第 0 章已铺好整体流程，本章开始深入翻译流水线的"定义层"——文法是描述语言的第一块基石。
>
> **与学科的关系**：文法是编译的"定义层"——后续词法分析和语法分析都是在特定文法上做识别。

### 1.1 乔姆斯基分类 ⭐⭐⭐

| 类型     | 名称               | 产生式约束                       | 对应自动机     | 典型        |
| ------ | ---------------- | --------------------------- | --------- | --------- |
| 0型     | 无限制文法            | 无限制                         | 图灵机       | /         |
| 1型     | 上下文有关文法          | $\|\alpha\| \leq \|\beta\|$ | 线性有界自动机   | /         |
| **2型** | **上下文无关文法（CFG）** | $A \to \beta$               | **下推自动机** | **编程语言**  |
| 3型     | 正则文法             | 右线性 $A \to wB$ 或 $A \to w$  | **有限自动机** | **Token** |

> [!tip]+ 面试一句话  
> 编程语言用 2 型文法（CFG）描述，Token 用 3 型文法（正则）描述。正则文法 ⊂ CFG ⊂ CSG ⊂ 无限制。

### 1.2 四种文法举例介绍 ⭐⭐⭐

| 类型     | 名称            | 产生式形式                                                  | 对应自动机       | 例子                                    |
| ------ | ------------- | ------------------------------------------------------ | ----------- | ------------------------------------- |
| **0型** | 短语结构文法（无限制文法） | **左部至少含一个非终结符**，右部可为空（ε），无其他限制                         | 图灵机         | $aS \to b$、$A \to \epsilon$ 等任意形式     |
| **1型** | 上下文有关文法       | **$xUy \to xuy$**（$xUy\le xuy$，长度不缩短；U 的替换受上下文 x、y 约束） | 线性有界自动机     | $aAb \to aabb$（A 仅在前后是 a、b 时才替换）      |
| **2型** | 上下文无关文法       | **$U \to u$**（左部是**单个非终结符**，替换与上下文无关）                  | （不确定的）下推自动机 | $E \to E+T \mid T$、$T \to n$；**编程语言** |
| **3型** | 正则文法          | **$U \to a$ 或 $U \to aW$（右线性：右部至多一个非终结符且在最右端**）        | **有穷状态自动机** | $S \to aA$、$A \to b$；标识符、Token        |

> [!tip]+ 四型的递进约束  
> 0型最自由（左部含非终结符即可）→ 1型限制"替换受上下文约束且长度不缩短"→ 2型限制"左部必须是单个非终结符"→ 3型再限制"右部至多一个非终结符且在最右"。**约束越严，对应自动机越简单**。

> [!tip]+ "给一张图问是什么文法"怎么判（三步）  
> **① 看左部**：左部形状任意、只要求**至少含一个非终结符** → **0 型**；左部形如 $xUy$（有左右上下文）→ **1 型**；左部是**单个非终结符** $U$ → 继续看右部。  
> **② 看右部**：右部是**任意串**（可含多个非终结符、可为 ε）→ **2 型（CFG）**；右部形如 $a$ 或 $aW$（**至多一个非终结符且在最右端**）→ **3 型（正则）**。  
> **③ 验"是否缩短"**：1 型要求 $xUy \leq xuy$（长度不缩短）；若形态像 1 型却会缩短（如 $A \to \epsilon$、$aB \to b$）→ 归 **0 型**。  
> 记忆锚点：**0 任意 / 1 带上下文 / 2 单个非终结符在左 / 3 单个非终结符在右**。

### 1.3 短语 / 句柄 / 素短语 ⭐⭐⭐

| 概念        | 定义                  | 分析方法中的对应        |
| --------- | ------------------- | --------------- |
| **短语**    | 相对于某非终结符的推导结果       | /               |
| **直接短语**  | 一步推导得到的短语           | /               |
| **句柄**    | 最左直接短语              | **LR 分析归约的对象**  |
| **素短语**   | 至少含一个终结符且不含更小素短语的短语 | /               |
| **最左素短语** | 最左的素短语              | **算符优先分析归约的对象** |

> [!tip]+ 容易错的三个点
>
> - **句柄 ≠ 所有直接短语**：句柄只是**最左**的那一个直接短语
> - **句柄 ≠ 素短语**：句柄是"最左直接短语"（可以不含终结符），素短语**必须至少含一个终结符**——所以 LR 归约句柄、算符优先归约最左素短语，两者归约的对象可能不同
> - **同一符号串可能成为多个句柄候选**：若多个产生式的右部相同（如某串既可由 $E \to X$ 也可由 $T \to X$ 归约），只有**最右推导中实际使用的那条产生式**对应的串才是句柄

> [!tip]+ 辨析  
> LR 分析每次归约**句柄**（最左直接短语），算符优先分析每次归约**最左素短语**。这是两者的核心区别。

### 1.4 语言与文法的对应关系 ⭐⭐

**核心结论：一种语言可以对应多种文法；一种文法只能描述一种语言。**

- **一种语言 → 多种文法（多对一的反向）**：**等价文法**（产生式不同、非终结符命名不同、推导结构不同）可以生成完全相同的句子集合。典型例子：
  - 二义性文法与非二义性文法可以描述**同一个表达式语言**
  - $E \to E + E \mid n$ 与 $E \to E + T \mid T$，$T \to n$ 描述**同一语言**（只是推导树不同）
- **一种文法 → 唯一语言**：给定文法 $G$，其生成的语言 $L(G)$（所有从 $S$ 推导出的终结符串集合）是**唯一确定**的

> [!tip]+ 面试一句话  
> "语言与文法是**一对多**：同一语言可由多种文法描述（如二义/非二义版本），而一个文法生成的语言是唯一的。所以判定'两文法是否等价'= 判断它们生成的语言是否相同。"

### 1.5 上下文无关文法（CFG）的特点 ⭐⭐⭐

**定义**：产生式形如 $A \to \beta$（左部**必须是单个非终结符** $A$，右部 $\beta$ 是任意符号串、可为 ε）的文法，即乔姆斯基 **2 型文法**。

| 特点               | 说明                                                          |
| ---------------- | ----------------------------------------------------------- |
| **左部单一，替换不看上下文** | 左部只能是一个非终结符，把它替换成 $\beta$ 时**不需要看左右邻居**——这正是"上下文无关"的含义      |
| **表达能力适中**       | 强于正则文法（能描述括号配对、嵌套结构），弱于上下文有关文法                              |
| **递归性**          | 产生式可自我嵌套（如 $E \to E + T$），天然描述**递归嵌套**的程序结构（括号、if-else、语句块） |
| **识别工具**         | （不确定的）**下推自动机 PDA**——比有限自动机多一个**栈**，栈提供"记数/配对"能力            |
| **是编程语言的文法**     | 表达式、语句、函数定义都用 CFG 描述；绝大多数编程语言的语法是 CFG 的近似                   |
| **局限**           | 描述不了**上下文有关约束**（变量先声明后使用、类型匹配、形参实参一致）——这些交给**语义分析**         |

> [!tip]+ 为什么编程语言选 CFG，不选更复杂的文法  
> ① **表达力够用**：程序的嵌套结构本质是"配对"，PDA 的栈刚好够；② **分析效率高**：CFG 的 LL/LR 分析可做到线性时间；③ **剩余的上下文约束交给语义分析**，比写进文法更灵活、更易报错。

## 2. 词法分析

> [!note]+ 章节导引  
> **本章知识点之间的关系**：词法分析是编译的"第一道工序"——把字符流变成 Token 流。逻辑链：**正则表达式**（描述 Token 的模式）→ **NFA**（正则→非确定自动机，Thompson 构造法）→ **DFA**（NFA→确定化，子集构造法）→ **最小化 DFA**（合并等价状态）。整条链是"从描述到实现"——正则是人的描述语言，DFA 是机器的执行模型。
>
> **与上一章的关系**：词法分析基于 3 型文法（正则文法），是文法最严格的子类。
>
> **与学科的关系**：正则→NFA→DFA→最小化是编译面试的经典考点，也是正则引擎的实现原理。

### 2.1 正则 → NFA → DFA → 最小化 ⭐⭐⭐

| 步骤        | 方法                  | 目标     |
| --------- | ------------------- | ------ |
| 正则 → NFA  | Thompson 构造法        | 自动化构造  |
| NFA → DFA | 子集构造法               | 消除不确定性 |
| DFA 最小化   | Hopcroft 算法（合并等价状态） | 减少状态数  |

> [!tip]+ 面试一句话  
> 正则描述 Token，NFA 是过渡，DFA 是最终可执行的自动机。词法分析器本质就是一个最小化 DFA。

### 2.2 NFA 与 DFA 的介绍 ⭐⭐⭐

|             | NFA（非确定有限自动机）                              | DFA（确定有限自动机）                 |
| ----------- | ------------------------------------------ | ---------------------------- |
| 状态转移        | 同一状态读同一输入可**转到多个状态**，允许 **ε 转移**（不读入字符的跳转） | 同一状态读同一输入**只能转到一个状态**，无 ε 转移 |
| **初态**      | 可以是**一个初态集合**                              | **唯一**                       |
| **空串（ε）输入** | **允许**（读空串就转移）                             | **不允许**                      |
| 路径          | 可能有多条路径——**只要存在一条**到达接受状态即接受               | 路径**唯一**——读完输入恰好停在接受状态才接受    |
| 构造难度        | **容易**（Thompson 构造法直接从正则得出）                | 较难（需要子集构造法）                  |
| 执行          | 需回溯/并行跟踪，慢                                 | 每步查表 O(1)，**可直接照搬成程序**       |


> [!tip]+ 面试一句话  
> "NFA 是'会选择的机器'——多条路径+ε 跳转，适合从正则构造；DFA 是'确定的机器'——路径唯一，适合直接执行。所以词法分析器的最终形态是（最小化）DFA。"

> [!tip]+ 三条最常被追问的差异（真题口径）
>
> 1. **下一状态是否唯一**：DFA 读入一个符号后**只有一个**后继状态；NFA 可能是**一个状态集合**（多条路径并行）。
> 2. **初态**：DFA **初态唯一**；NFA 可以是**一个初态集合**。
> 3. **空串（ε）输入**：NFA **允许**读空串转移（ε 转移）；DFA **不允许**。
>
> **术语对应**：NFA = **不确定**的有穷自动机 = **非确定**有限自动机（nondeterministic finite automaton）——"不确定"与"非确定"只是同一个词的不同译法，面试两种说法都认。

### 2.3 人工编程实现词法分析（举例）⭐⭐

**人工实现思路**：不用 lex/flex 等工具，自写词法分析器的标准两步是——**① 先根据词法规则（正则表达式 / 3 型文法）画出词法分析器的状态图（状态转换图）**；**② 再根据状态图编写程序**，通常用"**状态变量 + 读字符循环**"手工模拟状态转移（等价于直接实现这个 DFA）。

> [!tip]+ 为什么要"先画图再写程序"  
> 词法规则描述的是"什么样的字符序列构成什么 Token"（正则），状态图把正则**可视化为状态机**——每个 Token 类别对应一条（或几条）从初态到终态的路径。**先画状态图能保证规则不遗漏，程序只是对状态图的照搬**。

**举例：识别标识符、关键字和整数的简单词法分析器**

**第一步——根据词法规则画状态图**：标识符 = 字母开头的字母/数字串，整数 = 数字串，关键字 = 特定单词查表。画出状态转移：

- 状态 0（开始）：字母 → 状态 1；数字 → 状态 2
- 状态 1（标识符）：字母/数字 → 保持状态 1；其他字符 → 结束，查关键字表
- 状态 2（整数）：数字 → 保持状态 2；其他字符 → 结束

**第二步——照着状态图写程序**：

伪代码：

```
state = 0; token = "";
loop:
  c = getchar();
  switch (state):
    case 0:
      if (isalpha(c)) state = 1;
      else if (isdigit(c)) state = 2;
      else error;
    case 1:
      if (isalnum(c)) token += c;        // 仍在标识符中
      else                              // 识别结束
        if (is_keyword(token)) 输出"关键字" + token;
        else 输出"标识符" + token;
        token = ""; state = 0; 回退处理 c;
    case 2:
      if (isdigit(c)) token += c;
      else 输出"整数" + token; token = ""; state = 0; 回退处理 c;
```

> [!tip]+ 要点  
> 人工写词法分析器 = **手写 DFA 的状态机程序**。正则→NFA→DFA 这条链的意义正在于此：先把模式**确定化**，再照着 DFA 写程序，就不会漏掉任何转移状态。

### 2.4 正则文法、NFA、DFA 的转换关系 ⭐⭐

**结论先行：都能转换。**（三者等价，都描述正则语言）

| 问题               | 答案                  | 方法                              |
| ---------------- | ------------------- | ------------------------------- |
| 正则文法一定能变成 NFA 吗？ | **能**               | 文法→NFA 构造法（非终结符作状态）             |
| NFA 一定能变成 DFA 吗？ | **能**（NFA 与 DFA 等价） | **子集构造法**                       |
| DFA 能继续化简吗？      | **能**               | 最小化（**分割法**／Hopcroft 算法，合并等价状态） |

**文法（3型）→ NFA 的构造法**：

- 每个非终结符对应一个状态，开始符 S 为**初态**，另设**终态 F**
- $A \to aB$ → 状态 A 经输入 a 转移到状态 B
- $A \to a$ → 状态 A 经输入 a 转移到终态 F
- $A \to \epsilon$ → 状态 A 经 ε 转移到终态 F

> [!tip]+ 面试一句话  
> "正则文法↔NFA↔DFA"三者完全等价，都能表示正则语言。方向：文法直接构造 NFA，NFA 用子集构造法定化成 DFA，再最小化。唯一代价：确定化时**状态数可能指数增长**。"

### 2.5 读正则表达式：它表示什么语言 ⭐⭐

| 正则表达式                                                      | 表示的语言                           | 说明                                |
| ---------------------------------------------------------- | ------------------------------- | --------------------------------- |
| $a(a\lvert b)^*$                                           | **以 a 开头、后面跟任意个 a 或 b 的串**      | 首字符固定为 a，其余任意组合（后缀可为空，故 "a" 本身也算） |
| $(a\lvert b)^*$                                            | 所有由 a、b 组成的串（**含空串 ε**）         | 全字符表上的 Kleene 闭包                  |
| $a^*b^*$                                                   | 任意个 a 后跟任意个 b（**先 a 后 b，不能交错**） | 与 $(ab)^*$ 不同，后者只能是 abab… 这种交替形态  |
| $a(a\lvert b)^*b$                                          | 以 a 开头、以 b 结尾、长度 ≥ 2 的串         | 首尾固定，中间任意                         |
| $[a\text{-}zA\text{-}Z][a\text{-}zA\text{-}Z0\text{-}9]^*$ | C 语言的合法标识符                      | 与 §2.3 词法举例的规则一致：字母开头 + 字母数字串     |

> [!tip]+ 答题套路  
> 用自然语言描述时固定说三件事：**① 开头/结尾固定成什么 ② 中间由哪些字符组成、能不能交错 ③ 含不含空串（长度下限）**。

## 3. 语法分析

> [!note]+ 章节导引  
> **本章知识点之间的关系**：语法分析是编译最核心的阶段——把 Token 流组织成语法树。两大阵营：**自顶向下**（从根向叶推导，LL 分析）和**自底向上**（从叶向根归约，LR 分析）。LL 分析要求文法无左递归、无回溯（需提取公因子+求 FIRST/FOLLOW），LR 分析能力更强但状态更多。本章是编译面试的重中之重。
>
> **与上一章的关系**：词法分析提供 Token 流，语法分析消费 Token 流构建语法树。
>
> **与学科的关系**：LL/LR 分析是编译面试最常考的技术细节。

### 3.1 自顶向下 vs 自底向上 ⭐⭐⭐

|       | 自顶向下（LL）       | 自底向上（LR）          |
| ----- | -------------- | ----------------- |
| 方向    | 推导（从 S 到串）     | 归约（从串到 S）         |
| 分析树构建 | 从根到叶           | 从叶到根              |
| 文法要求  | 严格（无左递归、LL(1)） | 宽松（能处理更多文法）       |
| 典型方法  | 递归下降、LL(1)     | SLR、LR(1)、LALR(1) |

### 3.2 LL(1) 分析 ⭐⭐⭐

核心本质：**看到下一个输入符号，就能唯一确定选哪个候选式，不能有二选一的模糊情况**。

**LL(1) 条件**：对每个非终结符 $A$ 的两个候选式 $\alpha, \beta$：

1. $\text{FIRST}(\alpha) \cap \text{FIRST}(\beta) = \emptyset$  
   候选 $\alpha$ 这条路开头能出现的符号集合，和候选 $\beta$ 开头能出现的符号集合**不能重叠**。
2. 若 $\alpha \rightarrow \epsilon$，则 $\text{FIRST}(\beta) \cap \text{FOLLOW}(A) = \emptyset$  
   如果某条候选可以为空，那么另一条候选的开头符号，不能和 A 后面会出现的符号打架

**左递归消除**：$A \to A\alpha | \beta$ → $A \to \beta A'$, $A' \to \alpha A' | \epsilon$

### 3.3 LR 分析族 ⭐⭐⭐

| 方法          | 展望符号       | 状态数 | 能力                    |
| ----------- | ---------- | --- | --------------------- |
| **LR(0)**   | 无展望        | 少   | 最弱（冲突多）               |
| **SLR(1)**  | 用 FOLLOW 集 | 少   | 中等                    |
| **LALR(1)** | 合并同心项集     | 中   | **实际最常用**（yacc/bison） |
| **LR(1)**   | 精确展望       | 多   | 最强                    |

> [!tip]+ LR 分析的核心  
> LR 分析维护一个**状态栈**和**符号栈**，每次根据当前状态和下一个输入符号查 ACTION/GOTO 表决定移进还是归约。关键在于**如何判断应该归约**——SLR 用 FOLLOW 集判断，LR(1) 用精确展望判断。

### 3.4 人工编程实现语法分析（举例）⭐⭐

**不用 yacc/bison，手写分析器有两类主流做法：**

#### 自顶向下：递归子程序法（递归下降）

- **思想**：给每个非终结符写一个**函数**，函数体按该非终结符的候选式依次匹配输入——看到某个终结符就调用对应的子程序（match），看到非终结符就调用其函数
- **前提**：需先**消除左递归、提取公因子**，使文法适合自顶向下展开

**举例**：文法 $E \to E + T \mid T$（先消除左递归）：$E \to T\,E'$，$E' \to +T\,E' \mid \epsilon$

```
parse_E():
    parse_T();
    parse_E_prime();
parse_E_prime():
    if (lookahead == '+') {      // lookahead：当前读到的 Token
        match('+'); parse_T(); parse_E_prime();
    }                            // 否则 ε 分支，直接返回
parse_T():
    ...（同理，按 T 的候选式写）
```

> [!tip]+ 要点  
> 递归子程序法 = 把文法**直接翻译成嵌套函数**，每个候选式对应一段代码、每个终结符对应一次 match——实现简单、出错信息友好，是手写编译器的主流方式。

#### 自顶向下：LL(1) 分析法

- 用**预测分析表 + 显式栈**代替函数递归：对**栈顶非终结符 A** 和**当前输入 a**，查表 $M[A][a]$ 决定用哪个候选式展开（或用哪个产生式的推导）
- 表项为空 = 语法错误；这是"表驱动"版本，可统一处理所有非终结符（适合自动生成）

#### 自底向上：LR 分析（句柄识别问题）

- **核心难题**：每步该归约哪个符号串？——答案是**句柄（最左直接短语）**，归约顺序对应**最右推导的逆过程**
- **"右部相同的符号串都能组成句柄时，用哪一句柄"**：同一个符号串可能匹配多个产生式的右部（如串 $i$ 可由 $E \to i$、$T \to i$、$F \to i$ 之一归约），选错就无法归约回 $S$。判据是**最右推导**：哪个产生式是当前最右推导实际使用的，句柄就是"那个串 + 那条产生式"

**举例**：文法 $E \to E+T \mid T$，$T \to T*F \mid F$，$F \to (E) \mid i$，分析输入 $i*i+i$：

- 栈里先后出现可归约的 $i$（第一次来自 $F \to i$）——**句柄是第一个 $i$，用 $F \to i$ 归约**；而不是用 $E\to i$ 或 $T \to i$（那些不是最右推导中的实际步骤）
- LR 分析法靠**状态栈**区分：当前状态 + 输入决定是"移进"还是"归约、用哪条产生式"——**状态就是句柄识别的依据**

> [!tip]+ 面试一句话  
> "自顶向下是'展开'：递归子程序法（每非终结符一个函数）或 LL 查表（栈+预测分析表）；自底向上是'归约'：难点在**识别句柄**，且**右部相同的串可由多个产生式构成句柄时要选最右推导实际用的那一个**——LR 用状态栈解决。"

## 4. 语义分析与中间代码生成

> [!note]+ 章节导引  
> **本章知识点之间的关系**：语法分析只关心"结构合法不合法"，语义分析关心"含义对不对"。逻辑链：**属性文法**（为语法树添加语义信息，综合属性 vs 继承属性）→ **语法制导翻译**（在归约/推导时执行语义动作）→ **中间代码**（三地址码/四元式，与机器无关）→ **翻译文法**（插入动作符号的文法）。中间代码是前后端的分界线。
>
> **与上一章的关系**：语义分析在语法树基础上添加语义信息，是语法分析的延伸。
>
> **与学科的关系**：中间代码使编译器前后端分离，实现"一种前端+多个后端=多种目标机器"。

### 4.1 综合属性 vs 继承属性 ⭐⭐

|      | 综合属性        | 继承属性             |
| ---- | ----------- | ---------------- |
| 值来源  | **子节点**向上传递 | **父节点/兄弟节点**向下传递 |
| 计算时机 | 归约时（自底向上）   | 推导时（自顶向下）        |
| 典型   | 表达式的值、类型    | 变量声明中的类型         |

> [!tip]+ 面试一句话  
> 自底向上分析（LR）天然适合计算综合属性；自顶向下分析（LL）可以同时计算两种属性（父节点需要的综合属性可以由子节点通过返回值的方式返回给他）。

### 4.2 符号表：什么时候存储、什么时候查询 ⭐⭐

**符号表贯穿编译全过程**，核心动作只有两个：**填写（存储）** 和 **查询**。

| 阶段            | 主要动作               | 例子                       |
| ------------- | ------------------ | ------------------------ |
| **词法分析**      | **查询**保留字表         | 判断 "if" 是关键字还是标识符（最早的查询） |
| **语法分析**      | **存储**——声明出现时插入符号表 | 读到声明语句，把名字及其信息填入符号表      |
| **语义分析**      | **大量查询**           | 变量引用时查类型/作用域；做类型检查、作用域处理 |
| **中间代码生成**    | **查询**             | 生成三地址码时需要变量的类型、存储位置      |
| **目标代码生成/优化** | **查询**             | 查变量的存储分配、是否被使用（删死代码）     |

> [!tip]+ 一句话规律  
> "**声明时存储，引用时查询**。词法阶段查保留字表是最早的查询；语义分析是查询最密集的阶段（类型检查+作用域）；符号表的数据结构（散列表/树/栈式嵌套）决定了查询效率。"

### 4.3 指针的编译处理 ⭐⭐

指针的编译分四步：**类型检查 → 中间代码的间接寻址 → 目标代码的寻址模式 → 别名分析（服务于优化）**。

| 环节           | 编译做什么                                                                                         |
| ------------ | --------------------------------------------------------------------------------------------- |
| **类型检查**     | 指针是**带类型**的：`int *p` 与 `char *p` 不等价。赋值、比较、解引用都要检查指向类型是否一致（`void *` 除外）                       |
| **取地址 `&x`** | 生成"取 x 的地址"的中间代码，结果是**指针型临时变量**；要求 x 有确定的存储位置（**不能取寄存器变量或表达式结果的地址**）                          |
| **解引用 `*p`** | 分两种语境：**读** `y = *p` → 生成间接取值；**写** `*p = y` → 生成间接存值。左边是"地址"，右边是"值"                          |
| **指针运算**     | `p + i` 不是加 i 个字节，而是加 $i \times \text{sizeof(元素类型)}$——**按指向类型的大小缩放**（`int *` 的 `p+1` 前进 4 字节） |
| **目标代码**     | 用**寄存器间接寻址 / 变址寻址**实现：把 p 装入寄存器，再用 `LOAD R, 0(R)`；访问结构体成员时再叠加**偏移量**                          |
| **别名分析**     | 判断两条指针是否可能指向同一地址。互为别名时会**禁止**很多优化（复写传播、把变量缓存进寄存器）——这是指针让优化变难的根本原因                             |

> [!tip]+ 面试一句话  
> "指针的编译 = **类型检查 + 间接寻址**。类型决定搬几个字节和步长，`&`取门牌号、`*`按语境生成间接取或间接存，到目标代码退化成寄存器间接寻址和变址寻址。额外代价是**别名分析**——编译器不敢断定两个指针是否同址，于是很多优化只能放弃。"

### 4.4 不同作用域的同名变量，编译上如何实现 ⭐⭐

**问题**：C 里内层块可以定义与外层同名的变量——`{ int x = 1; { int x = 2; ... } }`，编译后必须让两者**互不干扰**。

| 机制            | 做法                                                                                                             |
| ------------- | -------------------------------------------------------------------------------------------------------------- |
| **栈式（嵌套）符号表** | 进入一个新**作用域/分程序**就在符号表里**压入一层**（或给表项打上作用域层次号），退出时**弹出**。查名字从**最内层向外层**查，**先找到的就是当前可见的那个**——这就是"名字屏蔽（shadowing）" |
| **各占存储位置**    | 同名变量是**两个不同实体**，各占各的存储（栈上不同偏移 / 不同活动记录），编译后靠**地址**区分而不是靠名字                                                     |
| **活动记录**      | 局部变量分配在各自的**活动记录（栈帧）**里，不同函数、同一函数的不同调用层次的同名变量天然分属不同栈帧                                                   |
| **重名消解（重命名）** | 优化/经典做法：编译内部把被遮蔽的变量**改写成唯一名**（如 `x#1`、`x#2`）或分配不同编号，之后就当两个普通变量处理                                               |

> [!tip]+ 为什么"同名不影响"  
> 编译期做完**作用域消解（名字解析）**之后，程序里**已经不存在"名字"**——只有地址和偏移量。所以"同名冲突"只存在于源码层面，目标代码里是两个不同地址的实体；这也是为什么局部变量名可以随便改，而全局变量的改名会影响链接（符号名变了）。

## 5. 运行时存储组织

> [!note]+ 章节导引  
> **本章知识点之间的关系**：程序运行需要内存空间来存变量、参数、返回地址等。逻辑链：**活动记录**（每次函数调用的栈帧）→ **静态 vs 动态分配**（编译时 vs 运行时确定大小）→ **Display 表**（快速访问外层作用域的机制）→ **堆管理**（动态分配的对象）。
>
> **与上一章的关系**：中间代码生成后，需要知道变量运行时的位置才能生成目标代码——这就是存储组织的任务。
>
> **与学科的关系**：活动记录是 OS 栈帧的具体实现，和 OS 的进程管理紧密关联。

### 5.1 活动记录 ⭐⭐⭐

| 组成      | 作用          |
| ------- | ----------- |
| 参数      | 实参值         |
| 返回地址    | 调用者的指令位置    |
| 动态链     | 指向调用者的活动记录  |
| Display | 外层活动记录的基地址表 |
| 局部变量    | 当前函数的局部数据   |


> [!tip]+ 面试一句话  
> 活动记录 = 函数调用的"工作台"——参数、返回地址、局部变量都在这里。每次调用创建新记录压栈，返回时弹栈。

### 5.2 全局变量与局部变量的内存分配 ⭐⭐

|              | 全局变量 / 静态变量                       | 局部（自动）变量                       |
| ------------ | --------------------------------- | ------------------------------ |
| **分配时机**     | **编译时**确定（静态分配），随程序装入就存在          | **运行时**每次进入函数时分配（动态分配）         |
| **所在区域**     | 静态数据区（`.data` 已初始化 / `.bss` 未初始化） | 运行栈上该函数的**活动记录（栈帧）**里   |
| **生存期**      | 整个程序运行期间                          | 本次函数调用期间（返回即失效）                |
| **定位方式**     | **绝对地址**（编译/链接期就能写死）              | **相对于栈帧指针的偏移**（SP/FP + offset） |
| **初值**       | 未显式初始化则**自动清零**                   | **不确定**（栈上的残留值）                |
| **能否用寄存器优化** | 难（可能被任意函数访问）                      | 容易（作用域封闭，可长期驻留寄存器）             |

> [!tip]+ 关键结论  
> **"静态分配 vs 动态分配"的分界不在"全局/局部"，而在"大小和位置能否在编译时确定"**。所以 `static` 局部变量虽写在函数内，也属**静态分配**；而变长数组、`malloc` 得到的空间属**动态分配**。局部变量用**偏移量寻址**而非绝对地址，这正是**递归调用时同名局部变量不冲突**的原因。

### 5.3 堆与栈：C 语言里存的内容有什么区别 ⭐⭐

| 维度       | **栈（stack）**                                  | **堆（heap）**                                        |
| -------- | --------------------------------------------- | -------------------------------------------------- |
| **存什么**  | 函数调用的**活动记录**：局部变量、参数、返回地址、保存的寄存器，以及整条调用链的上下文 | **运行期动态申请**的对象：`malloc`/`new` 得到的内存、链表/树等动态数据结构的结点 |
| **谁管理**  | **编译器**自动管理（进函数压栈、返回弹栈）                       | **程序员**手动管理（`malloc`/`free`，或 GC 回收）               |
| **分配效率** | 高——只需移动栈指针，**一条指令**                           | 低——要在空闲结构里查找合适的块                                   |
| **大小**   | 小且固定（Linux 默认约 8MB），**超了栈溢出**                 | 大、可增长（受虚拟内存限制），会**碎片化**                            |
| **增长方向** | 从高地址向**低**地址增长（x86 等常见架构）                     | 从低地址向**高**地址增长                                     |
| **生存期**  | 与函数调用绑定，**自动回收**                              | 由 `free` 决定，**忘记释放即内存泄漏**                          |
| **访问速度** | 快（连续、地址局部性好、命中 cache）                         | 较慢（分散、易缺页、cache 不友好）                               |
| **常见问题** | 递归太深、局部数组过大 → 栈溢出                             | 内存泄漏、悬垂指针、重复释放、碎片                                  |

> [!tip]+ 面试一句话  
> "栈是**函数调用用的临时空间**——编译器自动管，快、小、连续；堆是**运行期自由申请的空间**——程序员手动管，慢、大、离散。所以'局部变量在栈上、`malloc` 的在堆上'，堆的对象要通过指针访问。"

## 6. 代码优化与目标代码生成

> [!note]+ 章节导引  
> **本章知识点之间的关系**：优化是编译后端的核心——让程序跑得更快、占内存更少。逻辑链：**局部优化**（基本块内：常数合并、代数变换、复写传播、删除死代码）→ **全局优化**（循环优化：循环外提、强度削弱、归纳变量删除）→ **目标代码生成**（寄存器分配、指令选择）。
>
> **与上一章的关系**：优化和代码生成都基于中间代码和运行时存储信息。
>
> **与学科的关系**：代码优化是编译面试的次要考点，但常数合并和循环外提是常问的基本优化。

### 6.1 基本块与流图：局部优化在哪里做 ⭐⭐⭐

**基本块（basic block）**：**顺序执行、只有一个入口（第一条语句）和一个出口（最后一条语句）**的最大语句序列——**块中间没有跳转进入点，也没有中途跳转出去**。划分方法：把**跳转目标**和**跳转语句的下一条**标记为"首领"，相邻首领之间的语句就构成一个基本块。

**流图（控制流图）**：以基本块为结点、以可能的分支为有向边组成的图。

| 优化层次            | 作用范围                      | 典型技术                           |
| --------------- | ------------------------- | ------------------------------ |
| **局部优化**        | **单个基本块内部**——基本块就是局部优化的舞台 | 常数合并、代数变换、复写传播、删除死代码           |
| **循环优化**（属全局优化） | 整个循环体（跨基本块）               | 循环外提、强度削弱、归纳变量删除               |
| **全局优化**        | 整个流图 / 函数                 | 全局复写传播、公共子表达式消除、活跃变量分析、删除全局死代码 |

> [!tip]+ 一句话  
> "**局部优化的范围就是基本块**——因为块内没有跳转，控制流是**直线**的，可以在块内任意调整、合并、删除语句而不改变语义；一旦跨块，就必须先做**数据流分析**（如活跃变量分析）才能判断安全性，那属于循环/全局优化。"

### 6.2 常见优化技术 ⭐⭐

| 优化         | 层次 | 思想                                                              |
| ---------- | -- | --------------------------------------------------------------- |
| **常数合并**   | 局部 | 编译时算常量表达式                                                       |
| **复写传播**   | 局部 | 用 y 替换 x（x=y 后）<br />对复制语句`x=y`，在 y 的值未被改写的前提下，将后续对 x 的引用替换为 y； |
| **删除死代码**  | 局部 | 删除不可能执行的代码                                                      |
| **循环外提**   | 全局 | 把循环不变量（每次循环结果都不变的表达式）移到循环外                                      |
| **强度削弱**   | 全局 | 乘法→加法等                                                          |
| **归纳变量删除** | 全局 | 用基本归纳变量代替                                                       |

**举例**——六种技术的共同思路就三句话：**能在编译期算的不留到运行期、把贵的运算换成便宜的、同样的计算只做一次**。

**①–③ 局部优化**（都发生在一个基本块内）：

```
// ① 常数合并：编译期直接把常量表达式算完
int len = 2 * 1024 * 1024;        // → int len = 2097152;
if (3 > 5 || 1 == 1) ...          // → if (true) ...（进而整个分支被裁掉）

// ② 复写传播：x = y 之后，只要 y 没被改写，后续对 x 的引用全部换成 y
x = y;                            // 传播后：a = y + y;
a = x + x;                        // （原来的 x = y 没人再用 → 变成死代码，交给 ③）

// ③ 删除死代码——两个口径，面试常被追问
if (0) { slow(); }                // 口径一：不可达代码，控制流永远走不到 → 删
t = a * b;                        // 口径二：结果从未被使用的"无用代码"（狭义死代码）→ 删
                                  // 前提：a * b 没有副作用；含函数调用或可能出错就不能删
```

**④–⑥ 循环优化**（跨基本块，必须先做数据流分析才能保证安全）：

```
// ④ 循环外提：循环不变量（每次结果都一样的表达式）只算一次
for (i = 0; i < n; i++)          t = x * y;                 // 提到循环外
    a[i] = x * y + i;       →    for (i = 0; i < n; i++)
                                     a[i] = t + i;
// 前提：x、y 在循环体内没被改写；若循环可能一次都不执行，
// 而 x * y 可能出错（例如除零），还得先加 if (n > 0) 守卫

// ⑤ 强度削弱：把"贵"的运算换成"便宜"的
for (i = 0; i < n; i++)          for (p = a; p < a + n; p++)
    a[i] = 0;               →        *p = 0;               // 下标乘法 → 指针自增
// 同类：x * 2 → x + x，x * 4 → x << 2，x / 2 → x >> 1（仅无符号或已确定非负）

// ⑥ 归纳变量删除：i 和 j 都在随循环同步变化，只留一个
i = 0; j = 0;                    for (j = 0; j < 4 * n; j += 4)
for (; i < n; i++, j += 4)  →        a[j] = 0;
    a[j] = 0;                    // j = 4 * i，i 可以完全删掉
                                 //（4 * n 本身是循环不变量，会被 ④ 提出去）
```

⑤ 和 ⑥ 通常配套出现：**强度削弱会引入新的归纳变量（如 p、j），归纳变量删除再把这些多余的消掉**，最终循环里只剩一个自增变量。

> [!tip]+ 三个容易答错的点
>
> - **删死代码 ≠ 随便删**：只有**无副作用**的计算能删——纯算术可以，函数调用、可能触发异常的访存不行。
> - **循环外提有前提**：不变量在循环内没被改写，且搬出去不会引入循环本不会执行的错误（除零、空指针），必要时加 `if (n > 0)` 守卫。
> - **强度削弱只在等价时成立**：乘法换加法/移位一般安全，但`x / 2 → x >> 1`只对**无符号或已确定非负**的数成立。

### 6.3 如何让程序跑得更快：优化方法一览 ⭐⭐

按"动手的层次"从高到低：

| 层次              | 手段                                                                                               |
| --------------- | ------------------------------------------------------------------------------------------------ |
| **算法与数据结构**     | 换更优的算法/复杂度、选合适的容器、减少不必要的 I/O——**收益最大**                                                           |
| **源代码级**        | 减少函数调用开销（内联、少写调用频繁的小函数）、把循环不变量提到循环外、减少内存分配/释放次数、优先用局部变量（比全局快）、避免无谓拷贝（传引用、移动语义）、把大概率分支放前面（分支预测友好） |
| **编译级**（编译器自动做） | 常数合并、复写传播、删除死代码、公共子表达式消除；循环外提、强度削弱、归纳变量删除、循环展开；**寄存器分配**（热点变量放进寄存器）、指令调度（填流水线空隙）、内联展开            |
| **并行与硬件级**      | 多线程/多进程并行、SIMD 向量化、GPU 加速、提高缓存友好性（数据布局与访问顺序）、I/O 与计算重叠                                           |

> [!tip]+ 面试答题框架  
> 先给**一句话总纲**："优化按收益排序——**换算法（**降低时间复杂度，**收益最大） > 改数据布局和访存（**不改变算法复杂度，**减少内存访问开销） > 交给编译器优化（循环不变量、复写传播等） > 微调指令（**手工改汇编，收益最小）"，再挑 3～4 个具体手段展开（循环外提、寄存器分配、内联、缓存友好）。  
> 两个必须补的点：**① 优化必须以正确性为前提**；**② 先测量（profiling）找到热点再优化**，不能凭感觉。

### 6.4 寄存器分配的方法 ⭐⭐

**目标**：把"数量不限"的中间代码变量映射到"数量有限"的物理寄存器上；放不下的**溢出（spill）到栈**。这是后端最影响性能的问题——寄存器访问比访存快 1～2 个数量级。

| 方法                | 思想                                                                     | 特点                                             |
| ----------------- | ---------------------------------------------------------------------- | ---------------------------------------------- |
| **图着色法（Chaitin）** | 以变量为结点，**同时活跃（活跃区间重叠）**的两个变量之间连边，做 **k 着色**（k = 可用寄存器数），着色失败者溢出 | **经典、效果好**；本质是 NP 难问题，实际用启发式（优先溢出度数高、使用次数少的结点） |
| **线性扫描法**         | 把变量的**活跃区间**排序后线性扫描一遍，区间重叠就分配不同寄存器，不够则溢出                               | **快、实现简单**，JIT 场景常用（如早期 JVM 的 JIT）             |
| **使用计数 / 优先级法**   | 按**使用次数 × 循环深度**排序，把最"热"的变量优先放进寄存器                                     | 简单启发式，效果不如图着色                                  |
| **局部指派 + 窥孔**     | 在基本块内做简单指派（块内变量少，容易分配），再与全局分配配合                                        | 常作为整体方案的一环                                     |

**前置分析**：**活跃变量分析**（数据流分析的一种）——判断"在程序点 p 之后变量还会不会被用到"，得到变量的**活跃区间**；**同时活跃**的变量不能共用同一个寄存器。

> [!tip]+ 面试一句话  
> "寄存器分配的核心是**图着色**：把变量当结点，'同时活跃'就连边，然后用 k 种颜色（k 个寄存器）染色，染不上的就溢出到栈。前置步骤是**活跃变量分析**。此外还有线性扫描法，把变量的**活跃区间**排序后线性扫描一遍，区间重叠就分配不同寄存器，不够则溢出。使用计数法按**使用次数 × 循环深度**排序，把最"热"的变量优先放进寄存器，但不考虑活跃区间。局部指派+窥孔会在基本块内做简单指派，在出基本块时把变量全部存入内存，再在一小段相邻的指令窗口内判断是否有冗余的load/store能被删掉。"

| 人工语法分析              | 递归子程序（每非终结符一个函数）或 LL 查表展开；LR 靠状态栈识别句柄                   |
| 语言与文法               | 一对多：一种语言可由多种等价文法描述，一个文法只生成一种语言                          |
| 四种文法举例              | 0型左含非终结符(图灵机)→1型xUy→xuy(线性有界)→2型U→u(下推)→3型U→a或Wa(有限自动机) |
| 符号表时机               | 声明时存储、引用时查询；词法查保留字、语义分析查最勤                              |
| 从代码到可执行程序           | 预处理 → 编译（词法/语法/语义与中间代码/优化/目标代码生成）→ 汇编 → 链接              |
| 编译 vs 解释            | 编译先整体翻译再执行（快、不可移植）；解释边翻译边执行（慢、可移植、易调试）；JIT 折中           |
| 语法分析的定义与作用          | 按 CFG 判断 Token 序列是否合法并建立语法树，确定程序结构，是后续分析的基础             |
| CFG 的特点             | 左部单个非终结符（替换不看上下文）、可递归嵌套、PDA 识别、编程语言的文法；描述不了上下文有关约束      |
| 局部优化在哪做             | 基本块内（单入口单出口的直线指令序列）；跨块要先做数据流分析，属循环/全局优化                 |
| 寄存器分配               | 图着色（同时活跃连边 + k 着色，染不上就溢出）、线性扫描（按活跃区间）、使用计数；前置活跃变量分析     |
| 错误恢复                | 恐慌模式（丢字符到同步记号）、短语层次、出错产生式、全局纠正；无固定字符数（LL/LR 只看 1 个展望符）  |
| 全局 vs 局部变量          | 全局=静态分配（编译期定址、绝对地址、程序全程）；局部=动态分配（栈帧偏移、本次调用期）            |
| 堆 vs 栈              | 栈=函数调用的临时空间（编译器管、快小连续）；堆=malloc 的空间（程序员管、慢大离散、易泄漏）      |
| 同名变量怎么实现            | 栈式符号表按作用域压/弹，查找由内向外；目标代码里靠地址区分，名字在编译期被消解                |
| 指针的编译               | 类型检查 + 间接寻址（`*p` 的间接取/存）+ 指针运算按元素大小缩放 + 别名分析限制优化        |
| 正则 $a(a\lvert b)^*$ | 以 a 开头、后接任意个 a 或 b 的串                                   |
