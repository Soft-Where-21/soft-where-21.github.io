## 0. 编译过程总览

### 0.1 从源代码到可执行程序的完整流程 ⭐⭐⭐

**Q [⭐⭐⭐]【0.1.Q1】：从源代码到可执行程序要经过哪几步？（北航真题）**

A：四步：

| 步骤        | 工具  | 输入 → 输出          | 做什么                              |
| --------- | --- | ---------------- | -------------------------------- |
| **① 预处理** | cpp | `.c` → `.i`      | 展开 `#include`、宏替换、去注释、条件编译       |
| **② 编译**  | cc1 | `.i` → `.s`      | 词法→语法→语义→中间代码→优化→汇编代码（真正的"编译原理"） |
| **③ 汇编**  | as  | `.s` → `.o`      | 汇编指令 → 机器指令，生成可重定位目标文件           |
| **④ 链接**  | ld  | `.o` + 库 → 可执行文件 | 符号解析、重定位、合并段（分静态链接与动态链接）         |

两个必须点明的口径：**广义的"编译" = 预处理 + 编译 + 汇编 + 链接，狭义的"编译"只是第 ② 步**；被追问时再展开第 ② 步内部的五个阶段（词法、语法、语义与中间代码、优化、目标代码生成）。

**Q [⭐⭐]【0.1.Q2】：编译器内部有哪几个逻辑部分？前端和后端怎么划分？**

A：龙书把编译器分成**七个逻辑部分** = 五大阶段（词法分析、语法分析、语义分析与中间代码生成、代码优化、目标代码生成）+ **符号表管理** + **错误处理**，后两者**贯穿全过程**，不是独立的一遍。

**前端**（与源语言有关）：词法、语法、语义、中间代码生成；**后端**（与目标机器有关）：优化、目标代码生成。**中间代码是两者分界线**——一种前端配多个后端，就能把一种语言编译到多种机器。

### 0.2 词法分析 / 语法分析 / 语义分析：定义与作用 ⭐⭐⭐

**Q [⭐⭐⭐]【0.2.Q1】：词法分析、语法分析、语义分析分别在做什么？输入输出是什么？（北航真题）**

A：

| 阶段       | 输入 → 输出          | 做什么                                      | 典型错误                 |
| -------- | ---------------- | ---------------------------------------- | -------------------- |
| **词法分析** | 字符流 → Token 流    | 按**正则文法**把字符拼成"词素"，识别关键字、标识符、常数、运算符      | 非法字符、`1abc` 这类非法标识符   |
| **语法分析** | Token 流 → 语法树    | 按**上下文无关文法（CFG）**判断 Token 序列能否构成合法句子，构造语法树 | 括号不匹配、缺分号、`if` 缺 `else` |
| **语义分析** | 语法树 → 带语义信息的中间表示 | 检查**上下文有关**的约束（类型是否匹配、是否先声明后使用），并填符号表    | 类型不匹配、变量未声明、实参形参不符   |

一句话：**词法认"词"、语法认"句"、语义认"意思"**——前两者解决"写得对不对"，后者解决"说得通不通"。

**Q [⭐⭐]【0.2.Q2】：为什么词法分析要单独作为一个阶段，而不和语法分析合并？**

A：四条理由：① **简化设计**——Token 的模式用正则/DFA 就够，不必动用 CFG 这套更重的机制；② **提高效率**——DFA 线性扫描、不需要回溯，比语法分析快得多，先用便宜的手段把字符流压缩成 Token 流；③ **屏蔽字符细节**——空白、注释、换行这些"格式噪音"在词法阶段消化掉，语法分析只看 Token；④ **便于工具化与移植**——词法规则可以用 lex/flex 自动生成，规则改动不影响语法分析器。

### 0.3 编译执行 vs 解释执行 ⭐⭐

**Q [⭐⭐]【0.3.Q1】：编译执行和解释执行各有什么优劣？**

A：

| 维度     | 编译执行                      | 解释执行                       |
| ------ | ------------------------- | -------------------------- |
| 翻译时机   | 运行**前**一次性翻译成目标代码         | 运行**时**逐句翻译并立即执行           |
| 运行速度   | **快**（无翻译开销，可做全局优化）       | 慢（反复翻译，难做全局优化）             |
| 启动速度   | 慢（要先编译链接）                 | **快**（边读边执行）               |
| 可移植性   | 差（目标代码与机器/OS 相关，换平台要重编）   | **好**（有解释器就能跑同一份源码）        |
| 体积与内存  | 目标文件大，运行时不需要解释器           | 需要常驻解释器，源码即程序              |
| 调试与动态性 | 难（源码与目标码对应弱），不能边跑边改       | **易**（报错直接对应源码行），支持动态求值    |
| 代表     | C/C++、Go、Rust             | Python、Shell、早期 JavaScript |

**Q [⭐]【0.3.Q2】：什么叫"编译 + 解释"的折中？Python 的 `.pyc` 算编译吗？**

A：**字节码 + 虚拟机（JVM/CLR）**：先把源码编译成与平台无关的**字节码**，运行时由 **JIT** 把热点代码即时编译成机器码——兼得"可移植"和"运行快"。

⚠️ **Python 的 `.pyc` 只省掉了词法/语法分析（缓存字节码），执行时仍是逐条解释，所以 Python 依然是解释型语言**。

### 0.4 错误处理与错误恢复 ⭐⭐

**Q [⭐⭐]【0.4.Q1】：编译器发现错误后会处理几个字符？**

A：**没有固定的字符数**——取决于恢复策略。恐慌模式的做法是"**丢弃若干字符，直到遇到同步记号**"（如 `;`、`}`、语句结束），这个"若干"由**同步集**决定，可能 1 个字符，也可能一整行，**不是"固定处理 3 个字符"**。

如果问的是**分析器的向前看能力**：LL(1) 只看 **1 个** Token，LR 也只看 **1 个**展望符，只有 LR(k) 才看 k 个。

要点：错误恢复的目标不是"把程序改对"，而是**避免第一个错误引发连锁报错**，把错误尽量定位在一处。

**Q [⭐⭐]【0.4.Q2】：错误按阶段怎么分类？四种错误恢复策略是什么？**

A：错误分类——**词法错误**（非法字符）、**语法错误**（结构不合法）、**语义错误**（类型/作用域不符）；**逻辑错误编译期发现不了**。编译器发现错误后不会立刻停下，而是报告并设法继续，尽量一次报完所有错误。

| 恢复策略       | 做法                                       |
| ---------- | ---------------------------------------- |
| **恐慌模式恢复** | 丢弃输入符号，**直到遇到同步记号**（如 `;`、`}`）再继续分析      |
| **短语层次恢复** | 在出错点附近做最小修正（补一个分号、删一个多余的括号），然后继续         |
| **出错产生式**  | 预先为常见错误定义产生式，识别到错误就按"假装正确"的产生式继续         |
| **全局纠正**   | 找与输入编辑距离最小的合法串（理论上最优，代价过大，实际很少用）         |

## 1. 文法与语言

### 1.1 乔姆斯基分类 ⭐⭐⭐

**Q [⭐⭐⭐]【1.1.Q1】：乔姆斯基四型文法的名称、产生式约束和对应自动机是什么？**

A：

| 类型     | 名称               | 产生式约束                       | 对应自动机     | 典型        |
| ------ | ---------------- | --------------------------- | --------- | --------- |
| 0型     | 无限制文法            | 无限制                         | 图灵机       | /         |
| 1型     | 上下文有关文法          | $\lvert \alpha \rvert \leq \lvert \beta \rvert$ | 线性有界自动机   | /         |
| **2型** | **上下文无关文法（CFG）** | $A \to \beta$               | **下推自动机** | **编程语言**  |
| 3型     | 正则文法             | 右线性 $A \to wB$ 或 $A \to w$  | **有限自动机** | **Token** |

一句话：**编程语言用 2 型文法（CFG）描述，Token 用 3 型文法（正则）描述**；四种语言类的关系是 正则文法 ⊂ CFG ⊂ CSG ⊂ 无限制文法。

**Q [⭐⭐]【1.1.Q2】：四型文法的约束是层层加码的，具体加在哪一步？**

A：0 型最自由（左部**至少含一个非终结符**即可）→ 1 型限制"替换受上下文约束、长度不缩短"→ 2 型限制"**左部必须是单个非终结符**"→ 3 型再限制"**右部至多一个非终结符且在最右端**"。

**约束越严，对应的自动机越简单**：图灵机 → 线性有界自动机 → 下推自动机 → 有限自动机。

### 1.2 四种文法举例介绍 ⭐⭐⭐

**Q [⭐⭐⭐]【1.2.Q1】：给一组产生式（或一张图），怎么判断它是几型文法？**

A：三步判型法：

1. **看左部**：左部形状任意、只要求**至少含一个非终结符** → **0 型**；左部形如 $xUy$（带左右上下文）→ **1 型**；左部是**单个非终结符** $U$ → 继续看右部。
2. **看右部**：右部是**任意串**（可含多个非终结符、可为 ε）→ **2 型（CFG）**；右部形如 $a$ 或 $aW$（**至多一个非终结符且在最右端**）→ **3 型（正则）**。
3. **验"是否缩短"**：1 型要求 $xUy \leq xuy$（长度不缩短）；若形态像 1 型却会缩短（如 $A \to \epsilon$、$aB \to b$）→ 归 **0 型**。

记忆锚点：**0 任意 / 1 带上下文 / 2 单个非终结符在左 / 3 单个非终结符在右**。

**Q [⭐⭐]【1.2.Q2】：四种文法各举一个例子。**

A：

| 类型     | 名称            | 产生式形式                                     | 对应自动机       | 例子                                    |
| ------ | ------------- | ----------------------------------------- | ----------- | ------------------------------------- |
| **0型** | 短语结构文法（无限制文法） | **左部至少含一个非终结符**，右部可为空（ε），无其他限制            | 图灵机         | $aS \to b$、$A \to \epsilon$ 等任意形式     |
| **1型** | 上下文有关文法       | $xUy \to xuy$（长度不缩短；U 的替换受上下文 x、y 约束）      | 线性有界自动机     | $aAb \to aabb$（A 仅在前后是 a、b 时才替换）      |
| **2型** | 上下文无关文法       | $U \to u$（左部是**单个非终结符**，替换与上下文无关）          | （不确定的）下推自动机 | $E \to E+T \mid T$、$T \to n$；**编程语言** |
| **3型** | 正则文法          | $U \to a$ 或 $U \to aW$（右线性：右部至多一个非终结符且在**最右端**） | **有穷状态自动机** | $S \to aA$、$A \to b$；标识符、Token        |

### 1.3 短语 / 句柄 / 素短语 ⭐⭐⭐

**Q [⭐⭐⭐]【1.3.Q1】：短语、直接短语、句柄、素短语分别是什么？谁是哪种分析的归约对象？**

A：

| 概念        | 定义                  | 分析方法中的对应        |
| --------- | ------------------- | --------------- |
| **短语**    | 相对于某非终结符的推导结果       | /               |
| **直接短语**  | 一步推导得到的短语           | /               |
| **句柄**    | 最左直接短语              | **LR 分析归约的对象**  |
| **素短语**   | 至少含一个终结符且不含更小素短语的短语 | /               |
| **最左素短语** | 最左的素短语              | **算符优先分析归约的对象** |

三个容易错的点：**句柄 ≠ 所有直接短语**（只是最左的那一个）；**句柄 ≠ 素短语**（句柄可以不含终结符，素短语**必须至少含一个终结符**）；同一符号串可能成为多个句柄候选，只有**最右推导中实际使用的那条产生式**对应的串才是句柄。

**Q [⭐]【1.3.Q2】：如果多个产生式的右部相同、都能构成句柄，该用哪一个？**

A：句柄是"**最右推导中实际使用的那个产生式**所对应的串"。例如 $i$ 既可由 $E \to i$、$T \to i$、$F \to i$ 归约，分析 $i*i+i$ 时第一个 $i$ 必须用 $F \to i$——因为那才是当前最右推导的实际步骤，选错就归约不回 $S$。**LR 靠状态栈来区分**：当前状态 + 输入符号共同决定"移进还是归约、用哪条产生式"。

### 1.4 语言与文法的对应关系 ⭐⭐

**Q [⭐⭐]【1.4.Q1】：语言和文法是什么对应关系？为什么？**

A：**一种语言可以对应多种文法；一种文法只能描述一种语言**（一对多）。

- **一语言 → 多文法**：**等价文法**（产生式不同、非终结符命名不同、推导树不同）生成完全相同的句子集合。典型如二义性文法与非二义性文法描述**同一个表达式语言**：$E \to E+E \mid n$ 与 $E \to E+T \mid T,\ T \to n$ 描述同一语言，只是推导树不同。
- **一文法 → 唯一语言**：给定文法 $G$，它生成的语言 $L(G)$（所有从开始符推导出的终结符串集合）是**唯一确定**的。

所以"判定两个文法是否等价" = 判断它们生成的语言是否相同。

### 1.5 上下文无关文法（CFG）的特点 ⭐⭐⭐

**Q [⭐⭐⭐]【1.5.Q1】：上下文无关文法（CFG）有什么特点？（北航真题）**

A：**定义**：产生式形如 $A \to \beta$（左部**必须是单个非终结符** $A$，右部 $\beta$ 是任意符号串、可为 ε），即乔姆斯基 **2 型文法**。

| 特点               | 说明                                                          |
| ---------------- | ----------------------------------------------------------- |
| **左部单一，替换不看上下文** | 左部只能是一个非终结符；把它替换成 $\beta$ 时**不需要看左右邻居**——这就是"上下文无关"的含义     |
| **表达能力适中**       | 强于正则文法（能描述括号配对、嵌套结构），弱于上下文有关文法                              |
| **递归性**          | 产生式可自我嵌套（如 $E \to E+T$），天然描述**递归嵌套**的程序结构（括号、if-else、语句块）   |
| **识别工具**         | （不确定的）**下推自动机 PDA**——比有限自动机多一个**栈**，栈提供"记数 / 配对"能力          |
| **是编程语言的文法**     | 表达式、语句、函数定义都用 CFG 描述；绝大多数编程语言的语法是 CFG 的近似                  |
| **局限**           | 描述不了**上下文有关约束**（变量先声明后使用、类型匹配、形参实参一致）——这些交给**语义分析**        |

**Q [⭐⭐]【1.5.Q2】：CFG 描述不了什么？编程语言为什么选它，不选更复杂的文法？**

A：CFG 描述不了**上下文有关约束**：变量必须先声明后使用、类型必须匹配、实参形参要对得上——这些约束与"上下文"有关，而 CFG 的替换恰恰不看上下文。

选它的三个理由：① **表达力够用**——程序的嵌套结构本质是"配对"，PDA 的栈刚好够；② **分析效率高**——CFG 的 LL/LR 分析可以做到线性时间；③ **剩下的上下文约束交给语义分析**，比写进文法更灵活、报错也更准确。

## 2. 词法分析

### 2.1 正则 → NFA → DFA → 最小化 ⭐⭐⭐

**Q [⭐⭐⭐]【2.1.Q1】：从一个正则表达式到一个能跑的词法分析器，要经过哪几步？**

A：

| 步骤          | 方法                     | 目标       |
| ----------- | ---------------------- | -------- |
| 正则 → NFA    | **Thompson 构造法**       | 自动构造，不用人设计 |
| NFA → DFA   | **子集构造法**              | 消除不确定性   |
| DFA → 最小化 DFA | **Hopcroft 算法 / 分割法**  | 合并等价状态、减少状态数 |

一句话：**正则描述 Token，NFA 是过渡产物，DFA 才是最终可执行的形态**——词法分析器本质就是一个（最小化）DFA。

### 2.2 NFA 与 DFA 的介绍 ⭐⭐⭐

**Q [⭐⭐⭐]【2.2.Q1】：DFA 和 NFA 有什么区别？**

A：

|             | NFA（非确定有限自动机）                              | DFA（确定有限自动机）                 |
| ----------- | ------------------------------------------ | ---------------------------- |
| 状态转移        | 同一状态读同一输入可**转到多个状态**，允许 **ε 转移**（不读字符的跳转）  | 同一状态读同一输入**只能转到一个状态**，无 ε 转移 |
| **初态**      | 可以是**一个初态集合**                              | **唯一**                       |
| **空串（ε）输入** | **允许**（读空串就转移）                             | **不允许**                      |
| 路径          | 可能有多条路径——**只要存在一条**到达接受状态就接受               | 路径**唯一**——读完输入恰好停在接受状态才接受    |
| 构造难度        | **容易**（Thompson 构造法直接从正则得出）                | 较难（需要子集构造法）                  |
| 执行          | 需回溯 / 并行跟踪，慢                               | 每步查表 O(1)，**可直接照搬成程序**       |

**最常被追问的三条**：① 下一状态是否唯一（DFA 唯一，NFA 是集合）；② 初态（DFA 唯一，NFA 可为集合）；③ 空串输入（NFA 允许 ε 转移，DFA 不允许）。

**术语对应**：NFA = **不确定**的有穷自动机 = **非确定**有限自动机（nondeterministic finite automaton），"不确定"与"非确定"只是同一个词的不同译法，两种说法面试都认。

**Q [⭐⭐]【2.2.Q2】：既然 DFA 执行更快，为什么还要先构造 NFA？最终形态为什么是 DFA？**

A：因为两者各占一头——**NFA 好构造**（Thompson 构造法能从正则直接机械地得出，完全不用管确定化），**DFA 好执行**（每步查表 O(1)，路径唯一，可以直接照搬成程序）。

所以标准流程是：正则 →（Thompson）→ NFA →（子集构造法）→ DFA →（Hopcroft 最小化）；**唯一的代价是确定化时状态数可能指数增长**。

### 2.3 人工编程实现词法分析（举例）⭐⭐

**Q [⭐⭐]【2.3.Q1】：不用 lex/flex，怎么手写一个词法分析器？**

A：标准两步：

**① 先按词法规则（正则 / 3 型文法）画出状态转换图**。以"识别标识符、关键字、整数"为例：

- 状态 0（开始）：字母 → 状态 1；数字 → 状态 2；其他 → 报错
- 状态 1（标识符）：字母/数字 → 保持状态 1；其他字符 → 结束，**查关键字表**（是关键字就输出关键字，否则输出标识符）
- 状态 2（整数）：数字 → 保持状态 2；其他字符 → 结束，输出整数

**② 再照状态图写程序**——用"**状态变量 + 读字符循环**"手工模拟状态转移，等价于直接实现这个 DFA：

```
state = 0; token = "";
loop:
  c = getchar();
  switch (state):
    case 0:  isalpha(c) ? state = 1 : isdigit(c) ? state = 2 : error;
    case 1:  isalnum(c) ? token += c : (查关键字表输出; token = ""; state = 0; 回退 c);
    case 2:  isdigit(c) ? token += c : (输出整数; token = ""; state = 0; 回退 c);
```

两个易漏的细节：识别结束时**要把多读进来的那个字符回退**；标识符识别完**必须查关键字表**，否则 `if` 会被当成标识符。正则→NFA→DFA 这条链的意义正在于此：**先确定化，再照 DFA 写程序，就不会漏掉任何转移**。

### 2.4 正则文法、NFA、DFA 的转换关系 ⭐⭐

**Q [⭐⭐]【2.4.Q1】：正则文法一定能变成 NFA 吗？NFA 一定能变成 DFA 吗？**

A：**都能**——三者完全等价，都描述正则语言。

| 问题                | 答案                  | 方法                                  |
| ----------------- | ------------------- | ----------------------------------- |
| 正则文法一定能变成 NFA 吗？  | **能**               | 文法→NFA 构造法（非终结符作状态）                 |
| NFA 一定能变成 DFA 吗？   | **能**（NFA 与 DFA 等价） | **子集构造法**（确定化）                      |
| DFA 能继续化简吗？       | **能**               | 最小化（**分割法** / Hopcroft 算法，合并等价状态）   |

**3 型文法 → NFA 的构造法**：每个非终结符对应一个状态，开始符 S 为**初态**，另设**终态 F**；$A \to aB$ → 状态 A 经输入 a 转移到状态 B；$A \to a$ → 状态 A 经输入 a 转移到终态 F；$A \to \epsilon$ → 状态 A 经 ε 转移到终态 F。

### 2.5 读正则表达式：它表示什么语言 ⭐⭐

**Q [⭐⭐]【2.5.Q1】：$a(a\lvert b)^*$ 表示什么语言？描述一个正则表达式有什么固定套路？**

A：

| 正则表达式                                                      | 表示的语言                           | 说明                                |
| ---------------------------------------------------------- | ------------------------------- | --------------------------------- |
| $a(a\lvert b)^*$                                           | **以 a 开头、后面跟任意个 a 或 b 的串**      | 首字符固定为 a，其余任意（后缀可为空，故 "a" 本身也算）   |
| $(a\lvert b)^*$                                            | 所有由 a、b 组成的串（**含空串 ε**）         | 全字符表上的 Kleene 闭包                  |
| $a^*b^*$                                                   | 任意个 a 后跟任意个 b（**先 a 后 b，不能交错**） | 与 $(ab)^*$ 不同，后者只能是 abab… 这种交替形态  |
| $a(a\lvert b)^*b$                                          | 以 a 开头、以 b 结尾、长度 ≥ 2 的串         | 首尾固定，中间任意                         |
| $[a\text{-}zA\text{-}Z][a\text{-}zA\text{-}Z0\text{-}9]^*$ | C 语言的合法标识符                      | 字母开头 + 字母数字串（与 §2.3 的词法规则一致）      |

**答题套路**：用自然语言描述时固定说三件事——**① 开头/结尾固定成什么；② 中间由哪些字符组成、能不能交错；③ 含不含空串（长度下限）**。

## 3. 语法分析

### 3.1 自顶向下 vs 自底向上 ⭐⭐⭐

**Q [⭐⭐⭐]【3.1.Q1】：LL 分析法和 LR 分析法有什么区别？（北航真题）**

A：

|       | 自顶向下（LL）       | 自底向上（LR）          |
| ----- | -------------- | ----------------- |
| 方向    | **推导**（从开始符 S 到句子） | **归约**（从句子回到 S）         |
| 分析树构建 | 从根到叶           | 从叶到根              |
| 归约对象  | /              | **句柄**（最左直接短语）        |
| 文法要求  | 严格（**无左递归**、满足 LL(1)） | 宽松（能处理更多文法）       |
| 典型方法  | 递归下降、LL(1)     | SLR(1)、LALR(1)、LR(1) |

一句话：**LL 是"展开"**——看下一个符号就能唯一决定用哪条产生式（所以要消除左递归、提取公因子、算 FIRST/FOLLOW）；**LR 是"归约"**——用状态栈识别句柄，能力更强但状态更多。**实际编译器（yacc/bison）用的是 LALR(1)**。

### 3.2 LL(1) 分析 ⭐⭐⭐

**Q [⭐⭐⭐]【3.2.Q1】：LL(1) 的条件是什么？左递归怎么消除？**

A：核心本质：**看到下一个输入符号（1 个展望符），就能唯一确定选哪个候选式**，不能出现二选一的模糊情况。

对每个非终结符 $A$ 的任意两个候选式 $\alpha, \beta$：

1. $\text{FIRST}(\alpha) \cap \text{FIRST}(\beta) = \emptyset$——两条候选式**开头的符号集不能重叠**；
2. 若 $\alpha \Rightarrow \epsilon$，则 $\text{FIRST}(\beta) \cap \text{FOLLOW}(A) = \emptyset$——某条候选能为空时，另一条候选的开头符号不能和 $A$ **后面会出现的符号**打架。

**左递归消除**：$A \to A\alpha \mid \beta$ 改写成 $A \to \beta A'$，$A' \to \alpha A' \mid \epsilon$。

### 3.3 LR 分析族 ⭐⭐⭐

**Q [⭐⭐⭐]【3.3.Q1】：LR(0)、SLR(1)、LALR(1)、LR(1) 有什么区别？实际最常用哪个？**

A：

| 方法          | 展望符号       | 状态数 | 能力                    |
| ----------- | ---------- | --- | --------------------- |
| **LR(0)**   | 无展望        | 少   | 最弱（冲突多）               |
| **SLR(1)**  | 用 FOLLOW 集判断 | 少   | 中等                    |
| **LALR(1)** | 合并同心项集     | 中   | **实际最常用**（yacc/bison） |
| **LR(1)**   | 精确展望       | 多   | 最强                    |

LR 分析维护一个**状态栈**和一个**符号栈**，每次根据当前状态和下一个输入符号查 ACTION/GOTO 表决定移进还是归约；**关键在于怎么判断该归约**——SLR 用 FOLLOW 集，LR(1) 用精确展望，LALR(1) 则是把同心项集合并起来，用状态数的让步换回可用的分析表。

### 3.4 人工编程实现语法分析（举例）⭐⭐

**Q [⭐⭐]【3.4.Q1】：不用 yacc/bison，手写语法分析器有哪两类做法？**

A：**自顶向下两类**：

- **递归子程序法（递归下降）**：给每个非终结符写一个**函数**，函数体按候选式依次匹配输入——遇到终结符就 `match`，遇到非终结符就调用其函数。**前提是先消除左递归、提取公因子**。以 $E \to E+T \mid T$ 消除左递归得 $E \to T E'$，$E' \to +T E' \mid \epsilon$ 为例：

```
parse_E():          parse_E_prime():
    parse_T();          if (lookahead == '+') { match('+'); parse_T(); parse_E_prime(); }
    parse_E_prime();    // 否则走 ε 分支，直接返回
```

- **LL(1) 查表法**：用**预测分析表 + 显式栈**代替函数递归，对"栈顶非终结符 A + 当前输入 a"查 $M[A][a]$ 决定展开哪条产生式；表项为空即语法错误。这是"表驱动"版本，适合自动生成。

**自底向上**：LR 分析，靠**状态栈**识别句柄（见 3.4.Q2）。

**Q [⭐⭐]【3.4.Q2】：自底向上分析怎么判断该归约哪个串？右部相同的串都能构成句柄时用哪一个？**

A：**核心难题就是句柄识别**——每步该归约哪个符号串？答案是**句柄（最左直接短语）**，归约顺序恰好对应**最右推导的逆过程**。

同一个符号串可能匹配多个产生式的右部（如 $i$ 可由 $E \to i$、$T \to i$、$F \to i$ 归约），选错就归约不回 $S$。**判据是最右推导**：只有最右推导中实际使用的那条产生式对应的串才是句柄。例如文法 $E \to E+T \mid T$、$T \to T*F \mid F$、$F \to (E) \mid i$ 分析 $i*i+i$ 时，第一个 $i$ 要用 $F \to i$ 归约，而不是 $E \to i$ 或 $T \to i$。**LR 靠状态栈区分**：当前状态 + 输入符号决定是"移进"还是"归约、用哪条产生式"。

## 4. 语义分析与中间代码生成

### 4.1 综合属性 vs 继承属性 ⭐⭐

**Q [⭐⭐]【4.1.Q1】：综合属性和继承属性有什么区别？**

A：

|      | 综合属性        | 继承属性             |
| ---- | ----------- | ---------------- |
| 值来源  | **子节点**向上传递 | **父节点 / 兄弟节点**向下传递 |
| 计算时机 | 归约时（自底向上）   | 推导时（自顶向下）        |
| 典型   | 表达式的值、类型    | 变量声明中的类型         |

**自底向上分析（LR）天然适合计算综合属性**；自顶向下分析（LL）也能同时算两种属性——父节点需要的综合属性可以由子节点通过返回值传上去。

### 4.2 符号表：什么时候存储、什么时候查询 ⭐⭐

**Q [⭐⭐]【4.2.Q1】：符号表在编译的哪些阶段被存储、被查询？**

A：符号表贯穿编译全过程，核心动作只有**填写（存储）**和**查询**两个。

| 阶段            | 主要动作                | 例子                       |
| ------------- | ------------------- | ------------------------ |
| **词法分析**      | **查询**保留字表          | 判断 "if" 是关键字还是标识符（最早的查询） |
| **语法分析**      | **存储**——声明出现时插入符号表  | 读到声明语句，把名字及其信息填入符号表      |
| **语义分析**      | **大量查询**（最密集的阶段）    | 变量引用时查类型/作用域，做类型检查、作用域处理 |
| **中间代码生成**    | **查询**              | 生成三地址码时需要变量的类型、存储位置      |
| **目标代码生成/优化** | **查询**              | 查变量的存储分配、是否还被使用（删死代码）    |

一句话规律：**声明时存储，引用时查询**；词法阶段查保留字表是最早的查询，语义分析是查询最密集的阶段；符号表用什么数据结构（散列表 / 树 / 栈式嵌套）直接决定查询效率。

### 4.3 指针的编译处理 ⭐⭐

**Q [⭐⭐]【4.3.Q1】：指针在编译时是怎么处理的？**

A：分四步——**类型检查 → 中间代码的间接寻址 → 目标代码的寻址模式 → 别名分析（服务于优化）**。

| 环节           | 编译做什么                                                                                                   |
| ------------ | ------------------------------------------------------------------------------------------------------- |
| **类型检查**     | 指针是**带类型**的：`int *p` 与 `char *p` 不等价。赋值、比较、解引用都要检查指向类型是否一致（`void *` 除外）                                 |
| **取地址 `&x`** | 生成"取 x 的地址"的中间代码，结果是**指针型临时变量**；要求 x 有确定的存储位置（**不能取寄存器变量或表达式结果的地址**）                                    |
| **解引用 `*p`** | 分两种语境：**读** `y = *p` 生成间接取值；**写** `*p = y` 生成间接存值。左边是"地址"，右边是"值"                                          |
| **指针运算**     | `p + i` 不是加 i 个字节，而是加 $i \times \text{sizeof(元素类型)}$——**按指向类型的大小缩放**（`int *` 的 `p+1` 前进 4 字节）        |
| **目标代码**     | 用**寄存器间接寻址 / 变址寻址**实现：把 p 装入寄存器，再用 `LOAD R, 0(R)`；访问结构体成员时再叠加**偏移量**                                   |
| **别名分析**     | 判断两条指针是否可能指向同一地址。互为别名时会**禁止**很多优化（复写传播、把变量缓存进寄存器）——这是指针让优化变难的根本原因                                      |

一句话：**指针的编译 = 类型检查 + 间接寻址**；类型决定搬几个字节和步长，`&` 取门牌号、`*` 按语境生成间接取或间接存，到目标代码退化成寄存器间接寻址和变址寻址。

**Q [⭐]【4.3.Q2】：什么叫别名分析？它为什么让优化变难？**

A：**别名分析**判断两条指针是否可能指向同一地址。难点在于编译器**证明不了**它们不同，只能保守处理：

```c
int f(int *p, int *q) {
    int x = *p;      // 第一次读
    *q = 100;        // 往 q 那户写
    return x + *p;   // 第二次读 *p —— 能复用第一次的结果吗？
}
```

若 `p`、`q` 可能同址（调用方可能写 `f(&v, &v)`），那次 `*q = 100` 就已经改掉了 `*p`，第二次必须重新去内存读，`x` 也不能安心留在寄存器里。编译器证明不了不相交，于是**复写传播、寄存器缓存、循环不变量外提等一整批优化都只能放弃**。

对策：C 的 **`restrict`** 关键字由程序员声明"这两个指针不指向同一处"，编译器就敢放开优化。

### 4.4 不同作用域的同名变量，编译上如何实现 ⭐⭐

**Q [⭐⭐]【4.4.Q1】：C 里内层作用域可以定义与外层同名的变量，编译上怎么实现？**

A：内层块写 `{ int x = 1; { int x = 2; ... } }`，编译后必须让两者互不干扰，靠四个机制：

| 机制            | 做法                                                                                          |
| ------------- | ------------------------------------------------------------------------------------------- |
| **栈式（嵌套）符号表** | 进入一个新**作用域 / 分程序**就**压入一层**（或给表项打作用域层次号），退出时**弹出**；查名字从**最内层向外层**查，**先找到的就是当前可见的**——这就是"名字屏蔽（shadowing）" |
| **各占存储位置**    | 同名变量是**两个不同实体**，各占各的存储（栈上不同偏移 / 不同活动记录），编译后靠**地址**区分而不是靠名字                                   |
| **活动记录**      | 局部变量分配在各自的**活动记录（栈帧）**里，不同函数、同一函数的不同调用层次的同名变量天然分属不同栈帧                                        |
| **重名消解（重命名）** | 优化 / 经典做法：编译内部把被遮蔽的变量**改写成唯一名**（如 `x#1`、`x#2`），之后就当两个普通变量处理                                |

**为什么"同名不影响"**：编译期做完**作用域消解（名字解析）**之后，程序里**已经不存在"名字"**，只有地址和偏移量。所以"同名冲突"只存在于源码层面；这也是为什么局部变量名可以随便改，而**全局变量改名会影响链接**（符号名变了）。

## 5. 运行时存储组织

### 5.1 活动记录 ⭐⭐⭐

**Q [⭐⭐⭐]【5.1.Q1】：活动记录（栈帧）里包含哪些内容？**

A：

| 组成      | 作用          |
| ------- | ----------- |
| 参数      | 实参值         |
| 返回地址    | 调用者的指令位置    |
| 动态链     | 指向调用者的活动记录  |
| Display | 外层活动记录的基地址表 |
| 局部变量    | 当前函数的局部数据   |

一句话：**活动记录 = 函数调用的"工作台"**——每次调用创建新记录压栈，返回时弹栈。它正是 OS 里"栈帧"的编译视角，也是 5.2 里"局部变量用栈帧偏移寻址"的落脚点。

**Q [⭐]【5.1.Q2】：Display 表是做什么的？**

A：Display 是一张**外层活动记录的基地址表**——按作用域层次存着各层当前活动记录的起始地址。有了它，访问外层作用域的变量可以**直接一步定位**，而不必沿**动态链**一层层往上爬（嵌套层次深时差距明显）。它和动态链的区别：**动态链跟着调用关系走，Display 跟着作用域层次走**。

### 5.2 全局变量与局部变量的内存分配 ⭐⭐

**Q [⭐⭐]【5.2.Q1】：全局变量和局部变量在内存分配上有什么区别？**

A：

|              | 全局变量 / 静态变量                       | 局部（自动）变量                       |
| ------------ | --------------------------------- | ------------------------------ |
| **分配时机**     | **编译时**确定（静态分配），随程序装入就存在          | **运行时**每次进入函数时分配（动态分配）         |
| **所在区域**     | 静态数据区（`.data` 已初始化 / `.bss` 未初始化） | 运行栈上该函数的**活动记录（栈帧）**里          |
| **生存期**      | 整个程序运行期间                          | 本次函数调用期间（返回即失效）                |
| **定位方式**     | **绝对地址**（编译 / 链接期就能写死）            | **相对于栈帧指针的偏移**（SP/FP + offset） |
| **初值**       | 未显式初始化则**自动清零**                   | **不确定**（栈上的残留值）                |
| **能否用寄存器优化** | 难（可能被任意函数访问）                      | 容易（作用域封闭，可长期驻留寄存器）             |

**关键结论**：**"静态分配 vs 动态分配"的分界不在"全局 / 局部"，而在"大小和位置能否在编译时确定"**。局部变量用**偏移量寻址**而非绝对地址，这正是**递归调用时同名局部变量不冲突**的原因。

**Q [⭐]【5.2.Q2】：`static` 局部变量属于静态分配还是动态分配？**

A：**静态分配**。它虽然写在函数体内，但存放在**静态数据区**，程序装入时就分配好、生存期贯穿整个程序，只是**可见性**被限制在函数内。同理，变长数组和 `malloc` 得到的空间属**动态分配**——判断依据始终是"大小和位置能不能在编译时定下来"。

### 5.3 堆与栈：C 语言里存的内容有什么区别 ⭐⭐

**Q [⭐⭐]【5.3.Q1】：C 语言里堆和栈存的内容有什么区别？**

A：

| 维度       | **栈（stack）**                              | **堆（heap）**                              |
| -------- | ----------------------------------------- | ---------------------------------------- |
| **存什么**  | 函数调用的**活动记录**：局部变量、参数、返回地址、保存的寄存器，以及整条调用链的上下文 | **运行期动态申请**的对象：`malloc`/`new` 得到的内存、链表 / 树等动态数据结构的结点 |
| **谁管理**  | **编译器**自动管理（进函数压栈、返回弹栈）                   | **程序员**手动管理（`malloc`/`free`，或 GC 回收）     |
| **分配效率** | 高——只需移动栈指针，**一条指令**                        | 低——要在空闲结构里查找合适的块                         |
| **大小**   | 小且固定（Linux 默认约 8MB），**超了栈溢出**             | 大、可增长（受虚拟内存限制），会**碎片化**                  |
| **增长方向** | 从高地址向**低**地址增长（x86 等常见架构）                 | 从低地址向**高**地址增长                            |
| **生存期**  | 与函数调用绑定，**自动回收**                          | 由 `free` 决定，**忘记释放即内存泄漏**                |
| **访问速度** | 快（连续、地址局部性好、命中 cache）                     | 较慢（分散、易缺页、cache 不友好）                     |
| **常见问题** | 递归太深、局部数组过大 → 栈溢出                         | 内存泄漏、悬垂指针、重复释放、碎片                        |

一句话：**栈是函数调用用的临时空间**（编译器自动管，快、小、连续）；**堆是运行期自由申请的空间**（程序员手动管，慢、大、离散），所以堆上的对象要通过指针访问。

## 6. 代码优化与目标代码生成

### 6.1 基本块与流图：局部优化在哪里做 ⭐⭐⭐

**Q [⭐⭐⭐]【6.1.Q1】：基本块是什么？怎么划分？局部优化在哪里做？**

A：**基本块（basic block）** 是**顺序执行、只有一个入口（第一条语句）和一个出口（最后一条语句）** 的最大语句序列——**块中间既没有跳转进入点，也没有中途跳转出去**。**划分方法**：把**跳转目标**和**跳转语句的下一条**标记为"首领"，相邻首领之间的语句就构成一个基本块。**流图（控制流图）** 则是以基本块为结点、以可能的分支为有向边组成的图。

**局部优化就在单个基本块内做**——因为块内没有跳转、控制流是**直线**的，可以任意调整、合并、删除语句而不改变语义；**一旦跨块，就必须先做数据流分析**（如活跃变量分析）才能判断安全性，那属于循环 / 全局优化。

**Q [⭐⭐]【6.1.Q2】：优化分哪几个层次？各管多大范围？**

A：

| 优化层次            | 作用范围                      | 典型技术                           |
| --------------- | ------------------------- | ------------------------------ |
| **局部优化**        | **单个基本块内部**——基本块就是局部优化的舞台 | 常数合并、代数变换、复写传播、删除死代码           |
| **循环优化**（属全局优化） | 整个循环体（跨基本块）               | 循环外提、强度削弱、归纳变量删除               |
| **全局优化**        | 整个流图 / 函数                 | 全局复写传播、公共子表达式消除、活跃变量分析、删除全局死代码 |

### 6.2 常见优化技术 ⭐⭐

**Q [⭐⭐]【6.2.Q1】：六种常见优化技术是什么？分别在哪个层次？**

A：

| 优化         | 层次 | 思想                                       |
| ---------- | -- | ---------------------------------------- |
| **常数合并**   | 局部 | 编译时直接算常量表达式                              |
| **复写传播**   | 局部 | 对复制语句 `x = y`，在 y 未被改写的前提下，把后续对 x 的引用替换为 y |
| **删除死代码**  | 局部 | 删掉不可达代码 / 结果从未被使用的无用计算                   |
| **循环外提**   | 全局 | 把**循环不变量**（每次循环结果都不变的表达式）提到循环外           |
| **强度削弱**   | 全局 | 把"贵"的运算换成"便宜"的（乘法→加法 / 移位）               |
| **归纳变量删除** | 全局 | 循环里多个变量同步变化时，只保留基本归纳变量                   |

**Q [⭐⭐]【6.2.Q2】：这六种优化各举一个例子？有哪些前提和易错点？**

A：共同思路就三句话：**能在编译期算的不留到运行期、把贵的换成便宜的、同样的计算只做一次**。

**①–③ 局部优化**（都在一个基本块内）：

```
// ① 常数合并
int len = 2 * 1024 * 1024;   // → int len = 2097152;
if (3 > 5 || 1 == 1) ...     // → if (true) ...（进而整个分支被裁掉）

// ② 复写传播：x = y 后，y 没被改写就把后面的 x 全换成 y
x = y;                       // → a = y + y;（原 x = y 没人再用，变成死代码）
a = x + x;

// ③ 删除死代码——两个口径
if (0) { slow(); }           // 口径一：不可达代码，控制流永远走不到 → 删
t = a * b;                   // 口径二：结果从未被使用的无用计算 → 删
                             // 前提：无副作用（含函数调用或可能出错就不能删）
```

**④–⑥ 循环优化**（跨基本块，必须先做数据流分析）：

```
// ④ 循环外提：不变量只算一次
for (i = 0; i < n; i++)          t = x * y;
    a[i] = x * y + i;     →      for (i = 0; i < n; i++) a[i] = t + i;

// ⑤ 强度削弱：贵的换便宜的
for (i = 0; i < n; i++)          for (p = a; p < a + n; p++)
    a[i] = 0;             →          *p = 0;      // 下标乘法 → 指针自增
// 同类：x * 2 → x + x，x * 4 → x << 2，x / 2 → x >> 1（仅无符号或已确定非负）

// ⑥ 归纳变量删除：i 与 j 同步变化（j = 4*i），只留一个
i = 0; j = 0;                    for (j = 0; j < 4 * n; j += 4)
for (; i < n; i++, j += 4)  →        a[j] = 0;
    a[j] = 0;
```

⑤ 和 ⑥ 通常**配套出现**：强度削弱会引入新的归纳变量（如 p、j），归纳变量删除再把这些多余的消掉，最终循环里只剩一个自增变量。

**三个容易答错的点**：① **删死代码 ≠ 随便删**——只有无副作用的计算能删，函数调用、可能触发异常的访存不行；② **循环外提有前提**——不变量在循环内没被改写，且搬出去不会引入循环本不会执行的错误（除零、空指针），必要时加 `if (n > 0)` 守卫；③ **强度削弱只在等价时成立**——乘法换加法 / 移位一般安全，但 `x / 2 → x >> 1` 只对**无符号或已确定非负**的数成立。

### 6.3 如何让程序跑得更快：优化方法一览 ⭐⭐

**Q [⭐⭐]【6.3.Q1】：想让一个程序跑得更快，有哪些优化方法？**

A：按"动手的层次"从高到低：

| 层次              | 手段                                                                                               |
| --------------- | ------------------------------------------------------------------------------------------------ |
| **算法与数据结构**     | 换更优的算法 / 复杂度、选合适的容器、减少不必要的 I/O——**收益最大**                                                          |
| **源代码级**        | 减少函数调用开销（内联、少写调用频繁的小函数）、把循环不变量提到循环外、减少内存分配 / 释放次数、优先用局部变量、避免无谓拷贝（传引用、移动语义）、把大概率分支放前面 |
| **编译级**（编译器自动做） | 常数合并、复写传播、删除死代码、公共子表达式消除；循环外提、强度削弱、归纳变量删除、循环展开；**寄存器分配**、指令调度、内联展开                           |
| **并行与硬件级**      | 多线程 / 多进程并行、SIMD 向量化、GPU 加速、提高缓存友好性（数据布局与访问顺序）、I/O 与计算重叠                                        |

**答题框架**：先给总纲——"优化按收益排序：**换算法 > 改数据布局和访存 > 交给编译器优化 > 微调指令**"，再挑 3～4 个具体手段展开（循环外提、寄存器分配、内联、缓存友好）。两个必须补的点：**① 优化必须以正确性为前提；② 先测（profiling）找到热点再优化**，不能凭感觉。

### 6.4 寄存器分配的方法 ⭐⭐

**Q [⭐⭐]【6.4.Q1】：寄存器分配有哪些方法？**

A：**目标**是把"数量不限"的中间代码变量映射到"数量有限"的物理寄存器上，放不下的**溢出（spill）到栈**——这是后端最影响性能的问题，寄存器访问比访存快 1～2 个数量级。

| 方法                | 思想                                                              | 特点                                    |
| ----------------- | --------------------------------------------------------------- | ------------------------------------- |
| **图着色法（Chaitin）** | 以变量为结点，**同时活跃**的两个变量之间连边，做 **k 着色**（k = 可用寄存器数），着色失败者溢出         | **经典、效果好**；本质是 NP 难问题，实际用启发式（优先溢出度数高、使用次数少的结点） |
| **线性扫描法**         | 把变量的**活跃区间**排序后线性扫描一遍，区间重叠就分配不同寄存器，不够则溢出                         | **快、实现简单**，JIT 场景常用                   |
| **使用计数 / 优先级法**   | 按**使用次数 × 循环深度**排序，把最"热"的变量优先放进寄存器                              | 简单启发式，不如图着色                           |
| **局部指派 + 窥孔**     | 基本块内做简单指派（块内变量少，容易分配），出块时把变量存回内存，再在相邻指令窗口内删掉冗余的 load/store | 常作为整体方案的一环                            |

**Q [⭐]【6.4.Q2】：为什么寄存器分配之前要先做活跃变量分析？**

A：因为**"能不能共用寄存器"完全由活跃区间决定**。**活跃变量分析**（数据流分析的一种）判断"在程序点 p 之后这个变量还会不会被用到"，据此得到每个变量的**活跃区间**：**同时活跃的变量不能共用同一个寄存器**——这正是图着色里"连边"的依据，也是线性扫描里"区间重叠就换寄存器、不够就溢出"的依据。没有它就不知道该给谁分寄存器、该把谁溢出到栈。
