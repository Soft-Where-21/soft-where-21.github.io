## 1. OS 概论

### 1.1 四大特征 ⭐⭐

**Q [⭐⭐]【1.1.Q1】：操作系统有哪四大特征？它们之间是什么关系？**

A：**并发、共享、虚拟、异步**，四者是一条因果链：

| 特征     | 含义              | 一句话                   |
| ------ | --------------- | --------------------- |
| **并发** | 多个程序宏观上同时运行     | **最基本特征**，引出后面所有问题    |
| **共享** | 系统资源被多个进程共同使用   | 分互斥共享与同时访问            |
| **虚拟** | 一个物理实体映射为多个逻辑实体 | CPU→多个"虚拟 CPU"；内存→虚拟内存 |
| **异步** | 进程以不可预知的速度推进    | 并发 + 共享的必然结果          |

因果链：**并发 → 必须共享资源 → 为共享而虚拟化 → 并发导致异步**。其中**并发与共享是两个最基本的特征，二者互为存在条件**（没有并发就无所谓共享，没有共享机制并发就跑不对）。

### 1.2 中断与异常 ⭐⭐

**Q [⭐⭐]【1.2.Q1】：中断和异常有什么区别？为什么说"操作系统是中断驱动的"？**

A：

| 类型       | 触发       | 特点   | 举例             |
| -------- | -------- | ---- | -------------- |
| **同步异常** | 程序执行本身导致 | 可重现  | 除零、缺页、**系统调用** |
| **异步中断** | 外部硬件产生   | 不可预测 | I/O 完成、时钟、键盘中断 |

**系统调用属于同步异常**（更准确说叫"陷阱"）——用户程序主动执行 `syscall` 指令，从用户态切到内核态，这是**用户程序请求 OS 服务的唯一正规途径**。

**"OS 是中断驱动的"**：没有中断，OS 把 CPU 交给用户程序后就再也拿不回来（用户程序死循环也不会自己让出），既无法做进程切换，也无法响应 I/O 完成和时钟。时钟中断是内核"定期收权"的手段。

### 1.3 宏内核 vs 微内核 ⭐⭐

**Q [⭐⭐]【1.3.Q1】：宏内核和微内核有什么区别？各自的代表系统是什么？**

A：

|      | 宏内核              | 微内核                 |
| ---- | ---------------- | ------------------- |
| 核心思想 | 几乎所有功能都放进内核态     | 内核只留最核心的功能          |
| 优点   | 性能好（模块间调用，少切换）   | 可靠、可移植、灵活、易于扩展      |
| 缺点   | 庞大、一处出错可能全崩      | 频繁用户态↔内核态切换，通信开销大   |
| 代表   | Linux、Windows NT | QNX、Minix、HarmonyOS |

一句话：**宏内核用"性能"换"可靠性"，微内核用"可靠性"换"性能"**；实际系统多是混合形态（如 Windows、macOS 把驱动放在内核外跑）。

### 1.4 时钟周期与时钟频率 ⭐⭐

**Q [⭐⭐]【1.4.Q1】：什么是时钟周期和时钟频率？主频越高 CPU 就越快吗？**

A：

| 概念           | 定义                      | 关系            |
| ------------ | ----------------------- | ------------- |
| **时钟周期**     | 时钟脉冲的倒数，**计算机中最小的周期单位** | 主频 = 1 / 时钟周期 |
| **时钟频率（主频）** | 每秒的时钟脉冲数，单位 Hz          | 频率越高，工作速度越快   |

**主频高 ≠ 更快**：程序执行时间 = **指令条数 × CPI × 时钟周期**。主频只决定最后一项，还要看指令条数（编译器、算法）和 **CPI**（每条指令平均消耗的时钟周期数，受流水线、Cache 命中率影响）。

## 2. 进程管理

### 2.1 进程状态与转换 ⭐⭐⭐

**Q [⭐⭐⭐]【2.1.Q1】：进程有哪些状态？它们之间如何转换？（北航真题）**

A：基本三态 = **就绪、运行、阻塞**。

```
         调度选中              时间片用完 / 被抢占
  就绪 ──────────→ 运行 ──────────→ 就绪
   ↑                  │
   │                  │ 等待 I/O 或资源
   │                  ↓
   └──── 阻塞 ←───────┘
      事件完成（不是直接到运行！）
```

| 转换     | 触发原因             |
| ------ | ---------------- |
| 就绪 → 运行 | **调度程序选中**       |
| 运行 → 就绪 | **时间片到 / 被高优先级抢占** |
| 运行 → 阻塞 | **主动请求 I/O 或等待资源**（进程自己发起） |
| 阻塞 → 就绪 | **等待的事件完成**（不能直接到运行） |

**Q [⭐⭐⭐]【2.1.Q2】：时间片到了进程还没执行完，变成什么状态？（题单）**

A：变成**就绪态**（运行 → 就绪），排回就绪队列尾部等下一次调度。要点是"没执行完"不影响判断：

- **运行 → 就绪**：被动失去 CPU（时间片到、被抢占），**程序本身还能继续跑**；
- **运行 → 阻塞**：**进程自己**主动发起（等 I/O、等信号量），拿不到 CPU 也跑不了。

### 2.2 进程 vs 线程 ⭐⭐⭐

**Q [⭐⭐⭐]【2.2.Q1】：进程和线程有什么区别？（北航真题）**

A：**核心区分：进程是资源分配的基本单位，线程是 CPU 调度的基本单位。**

| 维度   | 进程                   | 线程                |
| ---- | -------------------- | ----------------- |
| 资源拥有 | 拥有独立地址空间             | **共享**所属进程的资源     |
| 切换开销 | 大（要切地址空间、TLB、Cache）  | 小（只切寄存器、栈、PC）    |
| 通信   | 需要 IPC 机制            | 直接读写共享内存（堆、全局变量）  |
| 崩溃影响 | 一个进程崩溃不影响其他进程        | **一个线程崩溃 → 整个进程崩溃** |

补充：线程私有的部分是**栈、寄存器、程序计数器**；共享的是**堆、全局变量、代码段、打开的文件**。

**Q [⭐⭐⭐]【2.2.Q2】：为什么要引入线程？**

A：四条理由：

1. **降低并发代价**：进程创建 / 撤销 / 切换都要带着整个地址空间和 PCB，太重；线程只带自己的寄存器、栈和 PC → 创建快、切换快。
2. **共享方便**：同一进程内的线程天然共享堆、全局变量、代码段和打开的文件，**不必再走 IPC** 就能交换大量数据。
3. **提高并行度**：多核时代，一个进程内的多个线程可以真正同时在多个核上跑（内核级线程）。
4. **拆分职责**：把"计算"与"I/O"、前台响应与后台处理拆到不同线程，编程模型更自然。

一句话：**进程太重、通信太贵、又没法在单进程内并行 → 把调度单位从进程细化成线程，资源归进程、调度归线程。**

**Q [⭐⭐]【2.2.Q3】：用户级线程和内核级线程有什么区别？Linux 的线程是怎么实现的？**

A：

|      | 用户级线程（ULT）          | 内核级线程（KLT）    |
| ---- | ------------------- | ------------- |
| 管理者  | 用户空间的线程库            | 操作系统内核        |
| 切换速度 | 快（不需要陷入内核）          | 慢（要用户态↔内核态切换） |
| 阻塞问题 | **一个线程阻塞 → 整个进程阻塞** | 只有该线程阻塞       |
| 多处理器 | 无法利用多核并行            | 可以多核并行        |

**Linux 的线程**：本质是"轻量级进程"（LWP），用 `clone()` 系统调用创建，共享进程地址空间但有自己的栈；`pthread` 库只是对它的封装。

### 2.3 进程与程序的区别 ⭐⭐

**Q [⭐⭐]【2.3.Q1】：进程和程序有什么区别？（题单）**

A：

| 维度   | 进程                                | 程序               |
| ---- | --------------------------------- | ---------------- |
| 本质   | 程序及其数据在计算机上的**一次运行活动**，**动态**概念   | 有序指令的集合，**静态**概念 |
| 组成   | 程序段 + 数据段 + **PCB**（进程控制块）        | 只是指令（+ 数据）       |
| 生命周期 | 有创建 → 运行 → 消亡的过程，**暂存**           | 可以长期保存在磁盘上       |
| 数量关系 | 一个程序可以对应**多个**进程                  | 一个进程也可以顺序执行多个程序  |

一句话：**进程 = 程序 + 数据 + PCB，是"正在跑的程序"**；程序是磁盘上的静态指令集合——**程序是菜谱，进程是照菜谱做菜的过程**。

## 3. 同步与互斥

### 3.1 临界区 ⭐⭐⭐

**Q [⭐⭐⭐]【3.1.Q1】：什么是临界区？临界区的代码结构是怎样的？（北航真题）**

A：**临界区（Critical Section）= 进程中访问共享资源的那段代码**（读写共享变量、用打印机、改文件）。目标：**任何时刻最多只有一个进程处于临界区**，同时不阻塞无关进程。

```
while (true) {
    进入区   // 检查能否进入、设置访问标志（互斥逻辑写在这里）
    临界区   // 访问共享资源，同一时刻只允许一个进程执行
    退出区   // 恢复标志，允许其他进程进入
    剩余区
}
```

关键：**互斥的代码写在进入区和退出区**，不在临界区里面；临界区本身只是"必须串行执行的那几行"。信号量、锁、管程都是实现这一目标的工具。

**Q [⭐⭐]【3.1.Q2】：一个合格的临界区方案要满足哪四条原则？**

A：

| 原则   | 含义               | 记忆口诀    |
| ---- | ---------------- | ------- |
| 空闲让进 | 资源空闲时允许进入        | 有空就进    |
| 忙则等待 | 已有进程在临界区时，其他进程等待 | 有人就等    |
| 有限等待 | 不能永远等下去，避免饥饿     | 不许死等    |
| 让权等待 | 等不进去就释放 CPU      | 等就让出 CPU |

**Q [⭐⭐]【3.1.Q3】：互斥和同步有什么区别？**

A：两者都是并发控制，但**方向相反**：

- **互斥**：多个进程**争用同一资源**，要求"同一时刻只能一个用"（我用了你就不能）。典型：打印机、共享变量。
- **同步**：多个进程**本来就有先后依赖**，要求"按指定次序推进"（我先生产你才能消费）。典型：生产者-消费者、先写后读。

**互斥是同步的一种特例**（把共享资源看成"必须先占后用"的事件）。临界区四原则解决的是互斥；信号量的"同步用法"（S = 0，先 V 后 P）解决的是同步。

### 3.2 信号量 ⭐⭐⭐

**Q [⭐⭐]【3.2.Q1】：什么是信号量？P、V 操作分别做什么？**

A：**信号量 = 一个整型变量 + 两个原子操作 P/V**（原语，执行时不可被打断）。

- **P（wait / 申请）**：`S = S - 1`；若 `S < 0`，则**阻塞**当前进程，把它挂到该信号量的等待队列。
- **V（signal / 释放）**：`S = S + 1`；若 `S <= 0`，说明还有进程在等，**唤醒**等待队列里的一个进程。

`S` 的物理含义：**S > 0 表示可用资源数，S < 0 时其绝对值表示正在等待的进程数**。

**Q [⭐⭐⭐]【3.2.Q2】：信号量的三种用法分别怎么设初值？生产者-消费者问题的 P 操作顺序为什么不能反？**

A：

| 用途       | 初始值 | 操作顺序      | 场景       |
| -------- | --- | --------- | -------- |
| **互斥**   | S=1 | P → 临界区 → V | 保护共享变量   |
| **同步**   | S=0 | 先 V 后 P    | 保证先后顺序   |
| **资源计数** | S=N | P → 用资源 → V | 限制并发数量   |

**生产者-消费者**：三个信号量 —— `mutex = 1`（互斥访问缓冲区）、`empty = N`（空位数）、`full = 0`（产品数）。生产者：`P(empty); P(mutex); 放入; V(mutex); V(full);`，消费者对称。

**P 操作必须先 P 资源信号量、再 P 互斥信号量**：若先 `P(mutex)` 再 `P(empty)`，缓冲区满时生产者会**握着 mutex 去等 empty**，消费者又拿不到 mutex 无法取走产品 → **死锁**。

### 3.3 死锁 ⭐⭐⭐

**Q [⭐⭐⭐]【3.3.Q1】：死锁的四个必要条件是什么？分别怎么破坏？（题单）**

A：

| 条件     | 含义         | 破坏方法          |
| ------ | ---------- | ------------- |
| 互斥     | 资源不能共享     | 很难破坏（很多资源天然互斥） |
| 请求且占有  | 拿着资源又申请新的  | **一次性申请所有资源** |
| 不可剥夺   | 已获得的资源不能被抢 | 允许抢占（用完再还）    |
| 环路等待   | 形成循环等待链    | **资源有序分配**（按序申请） |

记忆口诀：**互斥 → 占有 → 不剥夺 → 环路**，四个同时成立才会死锁，缺一个就不成立。

**Q [⭐⭐]【3.3.Q2】：死锁的处理策略有哪几种？"预防"和"避免"有什么区别？**

A：四种策略：

1. **预防**（静态）：破坏四个必要条件之一，让死锁**不可能发生**，代价是资源利用率低。
2. **避免**（动态）：每次分配前判断系统是否仍**安全**（银行家算法），不安全就不分配。
3. **检测 + 解除**：允许死锁发生，定期用资源分配图找环路，找到就撤销 / 抢占 / 回滚。
4. **鸵鸟算法**：不管。Unix / Linux 的实际做法，因为死锁概率低而预防代价太高。

**区别**：预防是**事前破坏条件**、约束一直生效；避免是**事中判断状态**、只在分配时检查，约束更松但每次都要算。

**Q [⭐⭐⭐]【3.3.Q3】：介绍银行家算法，实际场景下是否使用？（题单）**

A：**过程**：进程申请资源时**试探性地先分配**，然后做安全性检查——看剩余资源能否支撑**某个**进程跑完；能则假设它归还资源、继续检查下一个；若**所有进程都能跑完**，则系统**安全**，正式分配；否则回滚这次试探分配，让申请者等待。

**注意口径**：**不安全 ≠ 死锁**——不安全状态只是"可能死锁"，死锁一定发生在不安全状态里。

**实际是否使用**：理论优雅，但要求"进程总数、每类资源的最大需求量事先已知且不变"，且每次分配都要跑一遍安全性算法（开销随进程数平方增长）。**现代通用 OS 基本不采用**，只在**嵌入式 / 实时系统 / 数据库事务**这类资源需求可预知的场景有变体；Linux / Unix 实际是"死锁不管" + 少数场景加锁超时。

**Q [⭐⭐]【3.3.Q4】：死锁、饥饿、活锁有什么区别？**

A：**死锁 = 大家都卡住不动**（互相占有对方要的资源，谁都不动）；**饥饿 = 一直轮不到**（别人总插队，自己永远等不到，但系统整体在推进）；**活锁 = 一直在动但推进不了**（不断重试、不断放弃，状态来回抖动）。死锁是"不动"，饥饿是"轮不上"，活锁是"动了白动"。

### 3.4 管程 ⭐⭐

**Q [⭐⭐]【3.4.Q1】：什么是管程？它比裸信号量好在哪？**

A：**管程（Monitor）= 把共享变量和作用于它的操作封装在一个模块里，并保证同一时刻只允许一个进程在管程内活动**。

| 特性 | 说明                                    |
| -- | ------------------------------------- |
| 封装 | 共享数据只能通过管程内的过程访问，外部不能直接改              |
| 互斥 | **由编译器自动加锁**：进程进入管程即获得互斥，退出即释放        |
| 同步 | 用**条件变量** + `wait` / `signal` 实现等待与唤醒 |
| 优点 | 同步互斥交给编译器，程序员不易写错（比裸信号量安全得多）          |

**一句话**：管程的作用是"一次只允许一个进程进入管程内，便于控制和管理临界区，实现资源共享与进程互斥"。Java 的 `synchronized` + `wait()/notify()`、C# 的 `lock` 都是管程的实现。

### 3.5 进程同步的意义 ⭐⭐

**Q [⭐⭐]【3.5.Q1】：进程同步的意义是什么？为什么需要它？（题单）**

A：三点：

1. **保证结果可再现**：并发进程若不控制相对推进速度，结果会取决于调度时机 → 产生"与时间有关的错误"（两个进程同时 `count++` 会丢失更新）。
2. **保证互斥**：共享资源（打印机、全局变量、文件）同一时刻只被一个进程使用。
3. **保证先后顺序**：有依赖关系的操作必须按序执行（先生产后消费、先写后读、先赋值后使用）。

一句话：**同步把"并发"从不可预测变成可控，是并发程序正确性的前提。**

## 4. CPU 调度

### 4.1 调度算法对比 ⭐⭐⭐

**Q [⭐⭐⭐]【4.1.Q1】：说出五种进程调度算法，Windows 和 Linux 分别采用哪一种？（北航真题）**

A：**先答稳的五个**：**FCFS（先来先服务）、SJF（最短作业优先）、RR（时间片轮转）、Priority（优先级调度）、MFQ（多级反馈队列）**。

追问的延伸一起准备：**SRTF** = SJF 的抢占版；**HRRF** = 高响应比优先，用来治 SJF / SRTF 的饥饿；**MLQ** = 多级队列（队列之间不反馈）；**RMS / EDF** = 实时调度。

- **Windows**：**优先级抢占式 + 多级反馈队列**（32 个优先级，交互线程获得更高优先级与更长时间片）。
- **Linux**：**CFS（完全公平调度）**，不在固定时间片上轮转，而是按权重分配 CPU 时间，谁实际占用得少谁先跑。

**Q [⭐⭐⭐]【4.1.Q2】：这些调度算法的英文全称、中文名和优缺点分别是什么？（题单）**

A：

| 缩写           | 英文全称                                       | 中文名        | 抢占？   | 核心思想                   | 优点                 | 缺点                        |
| ------------ | ------------------------------------------ | ---------- | ----- | ---------------------- | ------------------ | ------------------------- |
| **FCFS**     | First Come First Served                    | 先来先服务      | 否     | 按到达顺序服务                | 简单、公平、无饥饿          | **短作业等很久**（护航效应）          |
| **SJF**      | Shortest Job First                         | 最短作业优先     | 否     | 先跑服务时间最短的              | **平均周转时间最小**       | 长作业饥饿；需预知运行时间             |
| **SRTF**     | Shortest Remaining Time First              | 最短剩余时间优先   | **是** | 比较"剩余时间"，谁短谁上（SJF 抢占版） | **平均等待时间最优**       | 长作业**饥饿更严重**；频繁比较，开销大     |
| **HRRF**     | Highest Response Ratio First（也写作 HRRN）     | 高响应比优先     | 否     | 选响应比最大的                | **兼顾长短作业，长作业不会饿死** | 每次调度要算全部进程的响应比，开销大        |
| **RR**       | Round Robin                                | 时间片轮转      | 是     | 每人一个时间片                | 公平、响应好             | 时间片大小难定                   |
| **Priority** | Priority Scheduling                        | 优先级调度      | 是 / 否均可 | 优先级高的先获得 CPU           | 可区分紧急任务、支持实时       | 低优先级进程**饥饿**              |
| **MFQ**      | Multi-level Feedback Queue                 | 多级反馈队列     | 是     | 多队列 + 反馈降级             | **兼顾各类进程**         | 实现复杂                      |
| **MLQ**      | Multi-level Queue                          | 多级队列       | 是     | 队列固定不反馈                | 简单、可区分类型           | 低优先级队列易饿死                 |
| **RMS**      | Rate Monotonic Scheduling                  | 速率单调调度     | 是     | 周期越短优先级越高（实时）          | 静态可判定              | 只适合周期任务                   |
| **EDF**      | Earliest Deadline First                    | 最早截止期优先    | 是     | 截止期最近的最先跑（实时）          | 利用率可达 100%         | 负载突变时行为不可预测               |

**Q [⭐⭐]【4.1.Q3】：高响应比优先（HRRF）的响应比怎么算？为什么它不会饿死？**

A：每次调度前计算就绪队列中每个进程的**响应比**，选最大的投入运行：

**响应比 =（等待时间 + 要求服务时间）/ 要求服务时间 = 1 + 等待时间 / 要求服务时间**

- **等待越久 → 响应比越大**：长作业的优先级随等待自动升高，**不会饿死**（相对 SJF / SRTF 的核心优势）；
- **服务时间越短 → 响应比越大**：短作业依然优先，保留了 SJF 的高效率。

所以它是 **FCFS 与 SJF 的折中**；代价是每次调度都要把所有就绪进程的响应比算一遍，实际系统极少直接使用。

**Q [⭐⭐]【4.1.Q4】：多级反馈队列（MFQ）是怎么设计的？什么是优先级反转？**

A：**MFQ 的设计逻辑**：① 多个就绪队列，优先级**逐级降低**、时间片**逐级加倍**；② 新进程先进入最高优先级队列，用完时间片就**降级**；③ I/O 型进程还没用完时间片就阻塞了，自然留在高层；计算型进程逐渐下沉。→ **短作业和 I/O 型进程得到快速响应**，这是现代通用 OS 的主流做法。

**优先级反转**：高优先级进程在等一个**低优先级进程持有的锁**，此时中间优先级的进程就绪、抢占了低优先级进程的 CPU，导致高优先级进程被"中间层"间接卡住。**解决方案：优先级继承**——低优先级进程持锁期间临时提升到"等待这个锁的最高优先级"，释放锁后恢复原优先级。

### 4.2 抢占式 vs 非抢占式 ⭐⭐

**Q [⭐⭐]【4.2.Q1】：抢占式和非抢占式调度，哪个开销大？为什么？（题单）**

A：**抢占式开销更大**，三个原因：

1. **切换次数多**：时间片到、更高优先级进程就绪、中断到来都能触发切换；非抢占式只在进程**主动放弃 CPU**（阻塞 / 结束）时才切。
2. **每次都要保存和恢复完整现场**：保存 CPU 环境（PC、通用寄存器、PSW、栈指针）→ 陷入内核 → 更新 PCB → 选新进程 → **切换页表并刷新 TLB / Cache** → 恢复现场 → 返回用户态。
3. **隐性代价（真正的大头）**：频繁切换不断破坏 **Cache 和 TLB 的命中率**，新进程第一次访存几乎全是缺失。

非抢占式开销小、实现简单，但一个死循环或长任务就能卡住整个系统，响应差。**换来的是更好的响应性和公平性。**

### 4.3 时间片轮转与响应时间 ⭐⭐⭐

**Q [⭐⭐⭐]【4.3.Q1】：用时间片轮转调度，如果开了很多进程，会不会影响用户的响应时间？怎么解决？（题单）**

A：**会影响。** 设就绪队列有 $n$ 个进程、时间片为 $q$，一个进程两次获得 CPU 之间大约要等 $(n-1)q$ —— **响应时间随进程数线性增长**。进程开得越多：

- 每个进程的等待被拉长，用户感觉"卡"；
- 上下文切换本身也吃 CPU，时间片越小时切换开销占比越高（有效算力大幅下降）。

**解决办法（按重要性）**：

1. **多级反馈队列（MFQ）**：交互型 / 短作业放在高优先级、小时间片的队列，计算型进程逐渐下沉 → 用户直接感受到的响应最快（现代通用 OS 的主流做法）。
2. **动态调整时间片**：按系统负载和进程类型调整 $q$（Linux 的 CFS 干脆改成按权重分配 CPU 时间，而不是固定轮转）。
3. **优先级调度**：给交互进程更高优先级，抢占批处理任务。
4. **分组轮转 / 限制并发**：把进程分组分时复用，缩短单个就绪队列的长度。

## 5. 内存管理

### 5.1 分页管理 ⭐⭐

**Q [⭐⭐]【5.1.Q1】：从连续分配到分页经历了什么？每个阶段解决或遗留了什么问题？**

A：

| 阶段       | 做法                                  | 遗留的问题                                                      |
| -------- | ----------------------------------- | ---------------------------------------------------------- |
| **连续分配** | 每个进程占用一段**连续**内存                    | ① 进程地址不隔离 ② 内存使用效率低（碎片）③ 大量换入换出 ④ 程序运行的**地址不确定**（每次装入位置不同） |
| **分段**   | 按逻辑单位划分，虚拟地址映射物理地址                  | 解决 ① 地址隔离和 ④ 地址不确定；仍有**外碎片**                               |
| **分页**   | 地址空间切成大小**固定**的页，做到哪一页就装入哪一页，否则留在硬盘 | 分配单位小 → 内存使用效率高，碎片只剩**内碎片（不足一页）**                          |

一句话：**分页的思想是"把内存切小、按需装"**——页小且固定，所以既没有外碎片，也天然支持后来的虚拟内存。

**Q [⭐⭐]【5.1.Q2】：分页的地址转换过程是什么？为什么要两次访存？**

A：**逻辑地址 = 页号 + 页内偏移** → 用页号查页表得到**页框号** → **物理地址 = 页框号 + 页内偏移**（偏移量不变）。

**两次访存**：第一次访问内存读**页表项**，第二次才用得到的物理地址**取数据**。每次访存都要翻倍 → 于是引入 **TLB** 加速。

### 5.2 TLB 与多级页表 ⭐⭐⭐

**Q [⭐⭐⭐]【5.2.Q1】：什么是 TLB？它解决了什么问题？（北航真题）**

A：**TLB（Translation Lookaside Buffer，快表）= 页表项的高速缓存**，通常做在 MMU 里，容量很小但极快。

- **解决的问题**：分页的"两次访存"（先查页表、再取数据）让访存开销翻倍。TLB 把最近用过的页表项缓存起来，**命中时只需 1 次访存**就能完成地址转换，典型命中率 99% 以上。
- **依据**：局部性原理——页号访问同样有明显的时间局部性。
- **缺失时**：需要访问内存中的页表，把页表项**填入 TLB**（MIPS 这类架构由软件填充并主动清 TLB；x86 由硬件完成）。

**Q [⭐⭐]【5.2.Q2】：页表太大怎么办？为什么多级页表更省空间？**

A：用**多级页表**（如两级、四级）。原因在于**页表本身要占用连续内存**：32 位地址空间、4KB 页、4B 页表项时，一级页表就要 100 万个表项 × 4B ≈ 4MB **连续空间**，每个进程一份，浪费巨大。

多级页表把页表也分页：顶级页表只占一页，**没被用到的二级页表根本不需要创建**（懒创建），一个只用了少量地址空间的进程只需很小的页表。代价是**寻址级数变多**（缺一次 TLB 就要多访存几次），所以更需要 TLB 命中。

### 5.3 分页 vs 分段 ⭐⭐

**Q [⭐⭐]【5.3.Q1】：分页和分段有什么区别？**

A：

|       | 分页             | 分段             |
| ----- | -------------- | -------------- |
| 划分依据  | **物理大小**（系统行为） | **逻辑关系**（用户可见） |
| 大小    | 固定             | **可变**         |
| 共享 / 保护 | 困难             | **方便**（一整个逻辑模块） |
| 碎片    | 内碎片            | 外碎片            |

一句话：**页是给机器看的（物理单位），段是给人看的（逻辑单位）**；段页式则外层分段、内层分页，兼有两者的结构特点。

### 5.4 虚拟存储 ⭐⭐⭐

**Q [⭐⭐⭐]【5.4.Q1】：什么是虚拟内存？为什么要用虚拟内存？（北航真题）**

A：**核心动机**：常规内存管理要求程序**全部装入**内存才能运行 → 内存不够用。

**虚拟内存**：像 Cache 一样，**把内存当成磁盘的"缓存"，只加载当前需要的部分**（按需调页 demand paging）。

**它的意义**：

1. **扩大可用内存**：通过虚拟技术把**外部存储设备的一部分空间**划分出来，作为内存不足时临时存放数据的缓存区（交换区 / 页面文件）。
2. **让"程序比内存大"也能跑**：程序不必全部装入，只装入当前用到的部分，其余留在磁盘按需调入。电脑上运行的程序都要经由内存执行，若程序占用内存很大或很多，内存会被耗尽，此时就靠虚拟内存顶上去。
3. **容量与并发的解耦**：多道程序的并发数不再被物理内存大小硬性限制。
4. **地址隔离（附带好处）**：每个进程拥有独立、连续、从 0 开始的逻辑地址空间，互不干扰。

**Q [⭐⭐]【5.4.Q2】：虚拟内存能成立的理论依据是什么？**

A：**局部性原理**：

- **时间局部性**：刚被访问的，不久之后可能再被访问（循环、热点数据）；
- **空间局部性**：刚被访问的位置附近，可能马上被访问（顺序访问数组）。

正因为程序在一段时间内只集中访问一小部分地址，才敢"只装一部分、其余放磁盘"。

**Q [⭐⭐⭐]【5.4.Q3】：页面置换算法有哪些？（题单）**

A：

| 算法            | 英文全称                     | 中文名        | 思想            | 特点                                      |
| ------------- | ------------------------ | ---------- | ------------- | --------------------------------------- |
| **OPT**       | Optimal Page Replacement | 最佳置换算法     | 替换最远将来才用的     | 理论最优（缺页最少），**无法实现**，只作评价基准              |
| **FIFO**      | First In First Out       | 先进先出       | 替换最早进入的       | 简单，但性能差，会出现 **Belady 异常**               |
| **LRU**       | Least Recently Used      | 最近最久未使用    | 替换最久未访问的      | **最实用**，性能接近 OPT；属**堆栈类算法**，无 Belady 异常 |
| **LFU**       | Least Frequently Used    | 最不经常使用     | 替换访问**次数最少**的 | 按频次淘汰；早期高频页长期占位，很少单独使用                  |
| **Clock**     | Clock / Second Chance    | 时钟置换（二次机会） | FIFO + 访问位    | LRU 的**近似**，开销远小于 LRU，是实际系统的主流          |
| **改进型 Clock** | Enhanced Second Chance   | 改进型时钟置换    | 访问位 + **修改位** | 优先淘汰"未访问且未修改"的页，**减少写回磁盘的 I/O**         |

**Q [⭐⭐]【5.4.Q4】：什么是 Belady 异常？哪些算法会有？**

A：**给进程多分物理块，缺页率反而升高**，这叫 Belady 异常。

- **会出现**：FIFO（以及基于它的 Clock / 二次机会类算法）；
- **不会出现**：LRU、OPT —— 它们满足**堆栈性质**（物理块数增加时，任一时刻的内存页集合是原集合的子集，缺页集合单调收缩）。

**Q [⭐]【5.4.Q5】：虚拟内存和 Cache 有什么区别？**

A：**Cache 解决"速度"差距，虚拟存储解决"容量"限制**。Cache 由**硬件**管理、对程序员透明；虚拟存储由 **OS + 硬件（MMU）**共同管理，且要处理缺页、置换、写回。两者都基于局部性原理，但**缺失代价差约 1000 倍**（缺页要访问磁盘）。

### 5.5 逻辑地址 vs 物理地址 ⭐⭐

**Q [⭐⭐]【5.5.Q1】：逻辑地址和物理地址有什么区别？程序员编程用的是哪个？（题单）**

A：

| 概念                        | 含义                       | 谁在用                     |
| ------------------------- | ------------------------ | ----------------------- |
| **逻辑地址**（相对地址 / 虚拟地址）     | 从 0 开始的连续地址空间，是程序内部使用的地址 | **程序员编程 / 编译链接 / 进程自身** |
| **物理地址**（绝对地址）            | 内存单元的真实硬件地址              | **硬件访存（经 MMU 转换之后）**    |

**转换过程**：逻辑地址 →（MMU 查页表，命中 TLB 则加速）→ 物理地址。程序**只能看到和使用逻辑地址**，物理地址对用户程序完全透明——这正是**进程隔离与地址保护的基础**。

### 5.6 页式存储管理的优劣 ⭐⭐⭐

**Q [⭐⭐⭐]【5.6.Q1】：页式存储管理有什么优点和缺点？（题单）**

A：

|        | 内容                                                                                                                                |
| ------ | --------------------------------------------------------------------------------------------------------------------------------- |
| **优点** | ① **无外碎片**，内存利用率高；② 页大小固定 → 内存分配 / 回收简单（空闲页用位示图管理）；③ 支持**离散分配**与**按需调页**，是虚拟内存的实现基础；④ 便于实现访问保护（页表项带读写 / 权限位）；⑤ 内存与程序逻辑解耦，程序不必连续存放 |
| **缺点** | ① 有**页内碎片**（最后一页用不满，平均浪费半页）；② **页表本身占内存**（地址空间大时需多级页表）；③ 一次访存需**两次访问内存**（查页表 + 取数据），要靠 TLB 加速；④ 按**物理**单位划分、与程序逻辑无关，**不利于共享和保护**；⑤ 需要额外硬件（MMU、TLB）和缺页处理软件开销 |

**Q [⭐⭐⭐]【5.6.Q2】：分页产生内碎片还是外碎片？分段呢？（题单）**

A：**分页 → 内碎片**：内存被切成固定大小的页框，任何浪费都只可能是"最后一页没装满"；因为页框大小统一，不会留下零散的、装不下任何页的空洞，所以**没有外碎片**。

**分段 → 外碎片**：段的大小可变，反复分配 / 回收后会在段与段之间留下装不下新段的空闲区。

一句话：**分页只有内碎片、分段只有外碎片；段页式兼有两者的结构特点**（外层分段、内层分页）。

### 5.7 内存泄漏的原因 ⭐⭐⭐

**Q [⭐⭐⭐]【5.7.Q1】：内存泄漏的原因有哪些？怎么避免？（题单）**

A：**内存泄漏 = 程序向系统申请了内存（通常是堆）却不再释放，同时也没有任何指针能再指向它**——既用不到，也回收不了。

**常见原因**：

1. **忘记释放**：`malloc` / `new` 之后漏了 `free` / `delete`（尤其提前 `return`、异常抛出等分支）。
2. **指针丢失**：指针被重新赋值或离开作用域，堆块失去唯一引用（链表删节点只断链、没释放）。
3. **申请与释放不匹配**：`new[]` 配 `delete`、`malloc` 配 `delete`，释放不完整或行为未定义。
4. **容器只增不减**：动态数组、哈希表、缓存只往里塞、从不淘汰。
5. **多态基类析构函数未声明为虚**：`delete` 基类指针只调用基类析构，派生类成员没释放。
6. **循环引用**：引用计数型智能指针互相持有，计数永远归不了零。

**后果**：常驻内存持续增长 → 换页增多、系统变慢，最终被 OOM 杀掉。**避免**：用 Valgrind / AddressSanitizer 检测；C++ 用 **RAII + 智能指针**；缓存设淘汰策略；长时间服务定期重启。

### 5.8 Cache 的替换策略 ⭐⭐⭐

**Q [⭐⭐⭐]【5.8.Q1】：Cache 的替换策略有哪些？（题单）**

A：Cache（或 TLB、页框）已满又发生缺失时，决定替换掉哪一块：

| 策略             | 思想                   | 特点                                        |
| -------------- | -------------------- | ----------------------------------------- |
| **随机（Random）** | 任意挑一块                | 硬件最简单，命中率不稳定                              |
| **FIFO**       | 替换最早调入的              | 简单，但可能踢掉马上还要用的块                           |
| **LRU**        | 替换**最久未被访问**的        | 命中率最高，但要精确维护访问顺序，硬件代价大                    |
| **LFU**        | 替换访问**次数最少**的        | 适合热点稳定的场景，易被"历史高频"过时数据干扰                  |
| **近似 LRU**     | **Clock / 二次机会**、NRU | **实际主流**：每块一个访问位，替换时若访问位为 1 就清 0 并给它第二次机会 |

**Q [⭐⭐]【5.8.Q2】：写直达和写回有什么区别？**

A：**写直达（Write Through）**：每次写都同时写 Cache 和内存，简单、一致性好，但访存次数多、慢；**写回（Write Back）**：只写 Cache，等这一块**被替换时**才写回内存，配合 **dirty 位**标记"改过没写回"。写回效率高，但存在**缓存一致性问题**（多核 / DMA 场景下内存和其他 Cache 可能拿到旧值）。

## 6. I/O 与磁盘管理

### 6.1 磁盘调度 ⭐⭐

**Q [⭐⭐]【6.1.Q1】：磁盘调度算法有哪些？各自的缺点是什么？**

A：

| 算法         | 思想     | 优缺点            |
| ---------- | ------ | -------------- |
| FCFS       | 按请求顺序  | 公平，但平均寻道长      |
| SSTF       | 最短寻道优先 | 局部最优，但远处请求可能**饥饿** |
| SCAN（电梯）   | 来回扫描   | 不饥饿，但两端刚访问过的磁道要等一圈 |
| C-SCAN     | 只单向扫描  | 更均匀，回程不服务      |

调度的目标是**减少寻道时间**（机械磁盘上寻道是最慢的一环）。

### 6.2 DMA ⭐⭐⭐

**Q [⭐⭐⭐]【6.2.Q1】：DMA 的全称是什么？它解决了什么问题？（题单）**

A：**DMA = Direct Memory Access（直接存储器访问）**。

**要解决的问题**：在"程序直接控制（轮询）"和"中断方式"下，数据都要在**设备 ↔ CPU 寄存器 ↔ 内存**之间倒腾，**每个字节都要 CPU 经手**——轮询把 CPU 锁死在等待里，中断方式虽然不用忙等，但每传一个数据块就要中断一次 CPU。CPU 的性能全被搬运工活计吃掉了。

**做法**：给设备配一个 **DMA 控制器（DMAC）**。CPU 只在传输**开始前**把源地址、目的地址、传送字节数（和方向）写进 DMAC 的寄存器；之后**数据在设备和内存之间直接成块传送、不经过 CPU**；整批传完后 DMAC 发**一次中断**通知 CPU 收工。

| I/O 方式     | CPU 参与程度             | 数据通路                   |
| ---------- | -------------------- | ---------------------- |
| 程序直接控制（轮询） | 全程忙等                 | 设备 → CPU → 内存          |
| 中断方式       | 每传一块就中断一次            | 设备 → CPU → 内存          |
| **DMA**    | 只在开头设参数、结尾收中断        | **设备 ↔ 内存（数据不经过 CPU）** |
| 通道方式       | 更少（专用 I/O 处理机执行通道程序） | 设备 ↔ 内存                |

**Q [⭐⭐]【6.2.Q2】：DMA 和通道方式有什么区别？**

A：**通道的粒度更大**：一条通道一次可以完成**多个** I/O 操作（执行一串通道程序），一部 DMA 一次一般只完成**一个**传输；一条通道可以轮流控制**多个**外设，一个 DMA 同一时刻一般只控制 **1 台**外设。所以"轮询 → 中断 → DMA → 通道"是 CPU 参与度递减的演进链。

## 7. 文件系统

### 7.1 文件物理结构 ⭐⭐

**Q [⭐⭐]【7.1.Q1】：文件的物理结构有哪几种？各自顺序读、随机读和碎片情况如何？**

A：

| 结构                             | 顺序读   | 随机读      | 碎片      |
| ------------------------------ | ----- | -------- | ------- |
| **连续分配**                       | 极快    | 极快       | **外碎片** |
| **链接分配**（每块末尾存下一块块号）           | 跟指针，慢 | **不能**   | 无       |
| **FAT**（FAT[i]=j 表示 i 的下一块是 j） | 较快    | 需遍历 FAT  | 无       |
| **索引分配**（开辟索引块存所有数据块的块号）       | 快     | **直接定位** | 无       |

**Q [⭐]【7.1.Q2】：索引块放不下怎么办？**

A：两种扩展：**多级索引**（类似多级页表，索引块再指向索引块）和**混合索引**——Unix inode 就是后者：**10 个直接指针 + 1 个间接 + 1 个二级间接 + 1 个三级间接**，小文件用直接指针就够（快），大文件层层加深。

## 8. 进程间通信

### 8.1 进程间通信的方式 ⭐⭐⭐

**Q [⭐⭐⭐]【8.1.Q1】：进程之间通信的方式有哪些？（北航真题）**

A：**标准答案（先报这一串）**：管道 → 命名管道 → 消息队列 → 共享内存 → 信号量 → 信号 → Socket。被问"几种"时，答**管道、消息队列、共享内存、信号量、Socket** 五类最稳，再补"信号"和"命名管道"。

| 方式         | 特点               | 适用场景   |
| ---------- | ---------------- | ------ |
| **管道**     | 半双工，**只限亲缘进程**   | 父子进程   |
| **命名管道**   | 有路径名，**无亲缘限制**   | 任意进程   |
| **消息队列**   | 消息的链表，有格式        | 结构化消息  |
| **共享内存**   | **最快**的 IPC（零拷贝） | 大量数据传输 |
| **信号量**    | 计数器，同步 / 互斥      | 配合共享内存 |
| **信号**     | 异步通知             | 异常处理   |
| **Socket** | 可跨网络通信           | 网络通信   |

**Q [⭐⭐]【8.1.Q2】：为什么共享内存最快？信号和信号量有什么区别？**

A：**共享内存最快**：同一块物理内存被映射进多个进程的地址空间，读写**不经过内核**、不需要数据拷贝（零拷贝）；代价是**它自己不管同步**，必须额外配一个信号量或锁。

**信号 vs 信号量**：**信号（signal）是"通知"**，异步打断进程、本身不携带数据（内容只有编号），像"敲一下门"；**信号量（semaphore）是"计数器"**，专门做同步互斥，不传递信息，像"发号码牌"。前者是异步事件机制，后者是同步原语。

### 8.2 Windows 与 Linux 的 IPC 对照 ⭐⭐⭐

**Q [⭐⭐⭐]【8.2.Q1】：Windows 和 Linux 下进程间通信的手段分别有哪些？（题单）**

A：

| 手段      | Linux                                         | Windows                         |
| ------- | --------------------------------------------- | ------------------------------- |
| 管道      | `pipe()`（匿名）、FIFO（`mkfifo`）                   | 匿名管道、**命名管道 Named Pipe**（可跨机器）  |
| 消息队列    | System V `msgget` / POSIX `mq_open`           | 消息队列、窗口消息（`PostMessage`）        |
| 共享内存    | System V `shmget` / POSIX `shm_open` + `mmap` | **文件映射 File Mapping**           |
| 信号量 / 锁 | System V、POSIX 信号量                            | Semaphore / Mutex / Event 等内核对象 |
| 信号      | `signal` / `sigaction`                        | 无完全等价的 POSIX 信号（用 APC、事件对象替代）   |
| 套接字     | BSD Socket、Unix Domain Socket                 | Winsock                         |
| 其他      | `eventfd`、域套接字                                | 邮槽 Mailslot、剪贴板、DDE、COM         |

一句话：**Linux 更贴近 POSIX（管道、信号、System V IPC），Windows 更依赖内核对象（事件、互斥体、文件映射）**；要一份跨平台通用答案，说 **Socket** 最稳。

## 9. 实验与拓展

### 9.1 简要介绍自己的 OS 实验课做了什么 ⭐⭐⭐

**Q [⭐⭐⭐]【9.1.Q1】：简要介绍你自己的 OS 实验课做了什么？（题单）**

A：**一句话概括**：用了一个学期，在一台"模拟出来的 MIPS 电脑"上，从开机第一条指令开始，一步步做出一个能跑的小操作系统——内存、进程、系统调用、文件系统、命令行都是自己写出来的。

**这门实验在干什么**：课程给的是一份叫 **MOS** 的实验框架（参考 MIT 的 JOS 思路）。硬件用 **QEMU 模拟 MIPS CPU**，代码在 Linux 下写，用 Makefile 编译、Git 交作业，配自动评测。最有意思的设计是**增量式**：每个 Lab 只加几百行代码，能单独跑、单独测，但**从 Lab1 写的代码会一路用到 Lab6**，最后拼成一个完整能跑的系统——不是六道互不相干的题，而是**一直在养同一个东西长大**。

| Lab      | 一句话       | 具体做了什么                                                                                                        |
| -------- | --------- | ------------------------------------------------------------------------------------------------------------- |
| **Lab0** | 熟悉工具      | 用熟 Linux、Git、Makefile、Vim，学会写基本的 shell 脚本                                                                     |
| **Lab1** | 让"电脑"开机成功 | 搞清楚"硬件要等软件、软件又要硬件载入"这个死循环怎么破；弄明白程序会放到内存什么位置、地址怎么定的；写最底层的代码让内核启动，并实现内核版 `printf`                |
| **Lab2** | 管内存       | 一边管**物理内存**（哪些块空着、谁在用），一边管**虚拟内存**（让每个程序都以为自己独占一大片连续内存）；写地址对照表，还要处理 CPU 里那张"常用地址缓存表"的失效与重填 |
| **Lab3** | 让别人的程序跑起来 | 建一张"进程表"记录每个程序的运行状态；把用户程序加载进内存并跑起来；做**时钟中断**——每隔一小段时间强行把控制权从程序手里收回内核，内核趁机决定下一个跑谁        |
| **Lab4** | 给用户程序开一扇门 | 用户程序不许碰硬件、也不许看别人的内存，想干活只能走内核开的"门"（系统调用）；实现进程之间通信；实现 `fork`，并用**写时复制**让复制又快又省内存          |
| **Lab5** | 把数据存下来    | 内存一断电就没了，所以数据要落到磁盘上：做了一个简单文件系统，能读磁盘、按名字找文件、读写；并把文件、控制台、管道三类东西统一成一种接口管理                     |
| **Lab6** | 造一个命令行    | 先实现管道（一个程序的输出直接接进另一个程序的输入），再写一个最简 shell：解析命令、启动程序、处理管道和重定向                            |

此外还有**挑战性任务**（课程留给"拔高"的一层）：我做的是把 shell 再增强一版，支持**环境变量、命令历史、行编辑**。

**30 秒口述版**："我们的操作系统实验是在模拟出来的 MIPS 平台上，用一个学期从零做一个能跑的小系统。它是增量式的：Lab1 让内核能启动、能打印，Lab2 管内存，Lab3 做出进程和时钟中断（靠它实现进程切换），Lab4 做系统调用和 `fork`，Lab5 做文件系统，Lab6 做管道和 shell，最后拼成一个完整能运行的操作系统。因为代码是一路累加下来的，所以对'一个操作系统怎么从一块裸板长出来'体会比较深。"

**Q [⭐⭐]【9.1.Q2】：OS 实验常见的追问有哪些？**

A：四条预案：

1. **为什么要做时钟中断？** —— 没有它，内核把 CPU 交给用户程序之后就再也拿不回来了。时钟中断是内核"定期收权"的手段，也是进程能切换的前提。
2. **`fork` 为什么要用写时复制？** —— 直接整块复制又慢又浪费内存。先让父子进程共用同一份内存、标成只读，谁要写谁触发一次异常、只复制那一页——又快又省。
3. **虚拟内存解决了什么？** —— 让每个程序都以为自己独占一大片连续内存（好写程序），同时互相隔离（安全），还顺带让"程序比内存大"也能跑。
4. **印象最深的一个坑？** —— 说个真实的，比如磁盘读写时数据还留在缓存里、设备那头已经更新导致的不一致。

> [!warning]+ 面试提醒
> 这题**一定要用自己的话讲**，按"我想做出一个什么东西 → 中间卡在哪 → 我怎么解决的"来讲，比背 Lab 清单有效得多。面试官一般会顺着追问某一个 Lab 的细节，**把 Lab2（内存）和 Lab3（进程与时钟中断）弄熟收益最大**。

### 9.2 高级语言编程 ⭐⭐

**Q [⭐⭐]【9.2.Q1】：如何在自己的 OS 和 CPU 上进行高级语言编程？（题单）**

A：这题在问：**从"内核能跑"到"能用 C / 高级语言写程序"，中间还缺哪几环？** 三块缺一不可：

1. **CPU 硬件必须满足基础运行要求**：高级语言编译后生成常规机器指令，CPU 必须完整支持**算术运算、内存访问、程序跳转**等基础指令；还必须具备**用户态与内核态切换、中断和异常处理机制**，否则无法支撑程序运行、权限隔离和错误处理。
2. **OS 必须提供程序运行的基础环境**：首先需要可执行的**文件加载器**，能解析编译后的程序文件，把代码、数据映射到进程的虚拟内存空间；其次需要完善的**系统调用接口**（内存申请、读写、程序退出都依赖它）；最后需要**进程管理与内存管理机制**，为每个程序分配独立地址空间、用户栈和页表。
3. **配套工具链与运行库必须适配平台**：需要适配自制 CPU 架构的**编译器、汇编器、链接器**，能把高级语言代码编译链接成该 CPU 可识别的可执行文件；还必须移植 **C 标准库**（实现 `printf`、`malloc` 等）；最后依靠**交叉编译**，在主机上编译出适配自制软硬件平台的程序。

一句话：**能在自己的 OS 上写高级语言 = CPU 具备完整指令和权限、中断机制 + OS 提供加载器和系统调用 + 有能生成该 CPU 指令的编译器 / 汇编器 / 链接器并移植了 C 标准库。**
