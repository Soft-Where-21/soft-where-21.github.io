# 操作系统（OS） - 保研面试知识点总结

> [!info]+ 复习策略  
> OS 的核心逻辑是"管理硬件资源，为上层提供抽象"。所有知识点都围绕这个主线展开——进程管理（CPU 抽象）、内存管理（存储抽象）、文件管理（磁盘抽象）、设备管理（I/O 抽象）。面试时遇到任何 OS 问题，先想"它解决什么资源管理问题"，再展开细节。
>
> 重点标注：⭐⭐⭐⭐ 面试极高频 | ⭐⭐⭐ 高频 | ⭐⭐ 中频 | ⭐ 补充
>
> 北航软院面试高频考点：**进程与线程区别、进程调度算法、进程通信、虚拟内存、临界区**

---

> [!abstract]+ 学科总览  
> OS 按"管理的资源"分成几大模块，每个模块解决一种硬件的抽象与管理：
>
> - **概论**：OS 的定位和整体架构（宏内核 vs 微内核），以及 OS 运行的驱动力（中断与异常）。
> - **进程管理**：CPU 的抽象。OS 用"进程"让每个程序以为自己独占 CPU，用"线程"细化并发粒度。这是面试最核心的部分。
> - **同步与互斥**：并发的"副作用"——多个进程访问共享资源会产生冲突，需要同步机制解决。信号量、管程、经典同步问题、死锁都在这里。
> - **CPU 调度**：有了进程就要决定"谁先用 CPU"——调度算法是进程管理的延伸。
> - **内存管理**：存储的抽象。从分区→分页→分段→段页式→虚拟存储，每次升级都在解决前一个的问题（碎片、保护、容量）。
> - **I/O 与磁盘**：设备的抽象。I/O 控制方式从轮询→中断→DMA→通道逐步解放 CPU。
> - **文件系统**：磁盘数据的抽象。把磁盘块组织成文件和目录，提供"按名存取"。
>
> 暗线：**OS 的每个模块 = 管理一种硬件 + 提供一种抽象**。进程=CPU 抽象，内存=存储抽象，文件=磁盘抽象，I/O=设备抽象。

---

## 1. OS 概论

> [!note]+ 章节导引  
> **本章知识点之间的关系**：概论建立 OS 的"世界观"——OS 是什么、有什么特征、怎么发展来的、怎么组织代码。逻辑链：**OS 定义**（管理硬件+服务应用）→ **四大特征**（并发→共享→虚拟→异步，因果链）→ **发展史**（每次升级解决"浪费"）→ **中断与异常**（OS 运行的驱动力）→ **内核结构**（宏内核 vs 微内核）。
>
> **与上一章的关系**：无（起点）。
>
> **与学科的关系**：本章建立 OS 的全局视角，后续每个模块都是"管理一种资源"的具体实现。

### 1.1 四大特征（层层递进）

> [!tip]+ 因果链  
> **并发**（最基本特征）→ 需要**共享**资源 → 为了共享必须**虚拟化**→ 并发导致**异步**执行

| 特征     | 含义              | 一句话                   |
| ------ | --------------- | --------------------- |
| **并发** | 多个程序宏观同时运行      | **最基本特征**，引出后面所有问题    |
| **共享** | 系统资源被多个进程共同使用   | 互斥共享 vs 同时访问          |
| **虚拟** | 一个物理实体映射为多个逻辑实体 | CPU→多个"虚拟CPU"；内存→虚拟内存 |
| **异步** | 进程以不可预知的速度推进    | 并发+共享的必然结果            |

其中**并发和共享是两个最基本的特征，二者互为存在条件**。

### 1.2 中断与异常 ⭐⭐⭐

**OS 是中断驱动的**——没有中断，OS 就无法获得控制权。

| 类型       | 触发       | 特点   | 举例             |
| -------- | -------- | ---- | -------------- |
| **同步异常** | 程序执行本身导致 | 可重现  | 除零、缺页、系统调用     |
| **异步中断** | 外部硬件产生   | 不可预测 | I/O 完成、时钟、键盘中断 |

> [!tip]+ 系统调用 = 同步异常  
> 用户程序主动触发 `syscall` 指令，从用户态切换到内核态——这是用户程序请求 OS 服务的唯一正规途径。

### 1.3 宏内核 vs 微内核 ⭐⭐⭐

|      | 宏内核              | 微内核                 |
| ---- | ---------------- | ------------------- |
| 核心思想 | 所有功能都放进内核        | 内核只留最核心功能           |
| 优点   | 性能好（少切换）         | 可靠、可移植、灵活           |
| 缺点   | 庞大、一崩全崩          | 频繁用户态↔内核态切换，慢       |
| 代表   | Linux、Windows NT | QNX、Minix、HarmonyOS |

### 1.4 时钟周期与时钟频率 ⭐⭐

| 概念           | 定义                      | 关系            |
| ------------ | ----------------------- | ------------- |
| **时钟周期**     | 时钟脉冲的倒数，**计算机中最小的周期单位** | 主频 = 1 / 时钟周期 |
| **时钟频率（主频）** | 每秒的时钟脉冲数，单位 Hz          | 频率越高，工作速度越快   |

> [!tip]+ 面试一句话  
> 时钟周期是 CPU 的最小节拍单位，主频是它的倒数。但主频高 ≠ 更快：实际性能还取决于 **CPI**（每条指令消耗的时钟周期数）和指令条数。

## 2. 进程管理

> [!note]+ 章节导引  
> **本章知识点之间的关系**：进程是 OS 最核心的抽象。逻辑链：**为什么需要进程**（程序是静态的，需要跟踪执行状态）→ **进程的组成**（PCB+程序段+数据段）→ **进程的状态**（三态转换）→ **进程 vs 线程**（进程太重，线程更轻）→ **线程实现**（用户级 vs 内核级）。进程是资源分配单位，线程是调度单位——这个区分是面试必考。
>
> **与上一章的关系**：进程是 OS "管理 CPU"的核心数据结构，OS 通过进程让多个程序"同时"运行。
>
> **与学科的关系**：进程是后续同步（第3章）和调度（第4章）的基础。

### 2.1 进程状态 ⭐⭐⭐⭐

```
         调度选中              时间片用完/被抢占
  就绪 ──────────→ 运行 ──────────→ 就绪
   ↑                  │
   │                  │ 等待I/O/资源
   │                  ↓
   └──── 阻塞 ←──────┘
        事件完成        等待事件发生
```

> [!tip]+ 关键转换（面试常考）
>
> - 就绪→运行：**调度程序选中**
> - 运行→就绪：**时间片到 / 被高优先级抢占**
> - 运行→阻塞：**主动请求I/O或等待资源**（进程自己发起，不是被动的）
> - 阻塞→就绪：**等待的事件完成**（不是直接到运行！）

### 2.2 进程 vs 线程 ⭐⭐⭐⭐（面试极高频）

> [!tip]+ 核心区分  
> **进程是资源分配的基本单位，线程是 CPU 调度的基本单位**

| 维度   | 进程                   | 线程                |
| ---- | -------------------- | ----------------- |
| 资源拥有 | 拥有独立地址空间             | **共享**所属进程的资源     |
| 切换开销 | 大（需切换地址空间、TLB、Cache） | 小（只需切换寄存器、栈）      |
| 通信   | 需要IPC机制              | 直接读写共享内存          |
| 崩溃影响 | 一个进程崩溃不影响其他          | **一个线程崩溃→整个进程崩溃** |

**线程实现**：

|      | 用户级线程（ULT）        | 内核级线程（KLT）     |
| ---- | ----------------- | -------------- |
| 管理者  | 用户空间的线程库          | 操作系统内核         |
| 切换速度 | 快（不需要陷入内核）        | 慢（需要用户态↔内核态切换） |
| 阻塞问题 | **一个线程阻塞→整个进程阻塞** | 只有该线程阻塞        |
| 多处理器 | 无法利用多核并行          | 可以多核并行         |

> [!tip]+ Linux 的线程  
> Linux 中线程本质是"轻量级进程"（LWP），通过 `clone()` 系统调用创建，共享进程地址空间但有自己的栈。

**为什么要引入线程** ⭐⭐⭐⭐：

1. **降低并发代价**：进程是资源分配单位，创建/撤销/切换都要带着整个地址空间和 PCB，太重；线程只带自己的寄存器、栈和程序计数器 → **创建快、切换快**。
2. **共享方便**：同一进程内的线程天然共享堆、全局变量、代码段和打开的文件，**不必再走 IPC** 就能交换大量数据。
3. **提高并行度**：多核时代，一个进程内的多个线程可以真正在多个核上同时跑（内核级线程）。
4. **拆分职责**：把"计算"和"I/O"、前台响应和后台处理拆到不同线程，编程模型更自然。

> [!tip]+ 一句话  
> 进程太重、通信太贵、又没法在单进程内并行 —— 于是把"调度单位"从进程细化成线程，**资源归进程，调度归线程**。

### 2.3 进程与程序的区别 ⭐⭐⭐

| 维度   | 进程                              | 程序               |
| ---- | ------------------------------- | ---------------- |
| 本质   | 程序及其数据在计算机上的**一次运行活动**，**动态**概念 | 有序指令的集合，**静态**概念 |
| 组成   | 程序段 + 数据段 + **PCB**（进程控制块）      | 只是指令（+ 数据）       |
| 生命周期 | 有创建→运行→消亡的过程，**暂存**             | 可以长期保存在磁盘上       |
| 数量关系 | 一个程序可以对应**多个**进程                | 一个进程也可以顺序执行多个程序  |

> [!tip]+ 面试一句话  
> 进程 = 程序 + 数据 + PCB，是"正在跑的程序"；程序是磁盘上的静态指令集合。程序是菜谱，进程是照菜谱做菜的过程。

## 3. 同步与互斥

> [!note]+ 章节导引  
> **本章知识点之间的关系**：并发带来了不确定性——多个进程访问共享资源，结果取决于推进速度。逻辑链：**问题起源**（互斥 vs 同步）→ **临界区原则**（进入临界区的四个条件）→ **实现方法演进**（软件→硬件自旋锁→信号量→管程）→ **经典问题**（生产者-消费者、读者-写者、哲学家进餐）→ **死锁**（并发的最坏结果）。
>
> **与上一章的关系**：第2章定义了进程，本章解决"多个进程如何正确协作"的问题。
>
> **与学科的关系**：同步机制是并发编程的基础，信号量和锁在所有编程语言中都有对应实现。

### 3.1 临界区原则 ⭐⭐⭐⭐

**什么是临界区**：**临界区（Critical Section）** = 进程中**访问共享资源**的那段代码（读写共享变量、用打印机、改文件）。目标：确保**任何时刻最多只有一个进程处于临界区**，同时不阻塞无关进程。

典型的并发代码结构：

```
while (true) {
    进入区   // 检查能否进入，设置访问标志（互斥逻辑写在这里）
    临界区   // 访问共享资源，同一时刻只允许一个进程执行
    退出区   // 恢复标志，允许其他进程进入
    剩余区
}
```

> [!tip]+ 关键点  
> 互斥的代码写在**进入区**和**退出区**，不在临界区里面；临界区本身是"必须串行执行的那几行"。信号量、锁、管程都是为实现这一目标提供的工具。判断一个"进入临界区"的方案是否合格，看下面四条原则。

| 原则   | 含义               | 记忆口诀    |
| ---- | ---------------- | ------- |
| 空闲让进 | 资源空闲时允许进入        | 有空就进    |
| 忙则等待 | 已有进程在临界区时，其他进程等待 | 有人在等    |
| 有限等待 | 不能永远等下去，避免饥饿     | 不许死等    |
| 让权等待 | 等不进去就释放 CPU      | 等就让出CPU |

### 3.2 信号量 ⭐⭐⭐⭐

**信号量** = 整型变量 + P/V 原子操作

**三种用法**：

| 用途       | 初始值 | 操作      | 场景     |
| -------- | --- | ------- | ------ |
| **互斥**   | S=1 | P→临界区→V | 保护共享变量 |
| **同步**   | S=0 | 先V后P    | 保证先后顺序 |
| **资源计数** | S=N | P→用资源→V | 限制并发数量 |

> [!tip]+ 生产者-消费者问题  
> 三个信号量：`mutex=1`（互斥）、`empty=N`（空位）、`full=0`（产品）。  
> **P操作顺序必须先P资源信号量再P互斥信号量**（否则死锁！）

### 3.3 死锁 ⭐⭐⭐⭐（面试高频）

**四个必要条件**：

| 条件    | 含义         | 破坏方法          |
| ----- | ---------- | ------------- |
| 互斥    | 资源不能共享     | 很难破坏          |
| 请求且占有 | 拿着资源又申请新的  | **一次性申请所有资源** |
| 不可剥夺  | 已获得的资源不能被抢 | 允许抢占          |
| 环路等待  | 形成循环等待链    | **资源有序分配**    |

> [!tip]+ 记忆口诀  
> 互斥→占有→不剥夺→环路。预防 = 破坏其中之一；避免 = 不让系统进入不安全状态。

**死锁处理策略**：预防（破坏条件，代价大）→ 避免（银行家算法）→ 检测+解除 → 鸵鸟算法（Unix/Linux 实际做法）

**银行家算法**：每次分配前模拟分配，检查是否仍安全。**不安全 ≠ 死锁**，但死锁一定在不安全状态。

> [!tip]+ 银行家算法的过程  
> 进程申请资源时**试探性地分配**，然后做安全性检查：看剩余资源能否支撑**某个**进程执行完毕——能则模拟它归还资源、继续检查下一个进程；若**所有进程都能跑完**则系统**安全**，正式分配；否则回滚这次试探分配，让申请者等待。
>
> **实际是否使用**：理论上优雅（避免死锁而非事后处理），但它要求"进程总数、每类资源的最大需求量事先已知且不变"，且每次分配都要跑一遍安全性算法（开销随进程数平方增长）。现代通用 OS 基本不采用，只在**嵌入式 / 实时系统 / 数据库事务**这类资源需求可预知的场景有变体。Linux/Unix 的实际策略是"死锁不管"（鸵鸟算法）+ 少数场景加锁超时。

> [!tip]+ 死锁 vs 饥饿 vs 活锁  
> 死锁 = 都在等谁也不动；饥饿 = 一直轮不到；活锁 = 不断尝试但推进不了。

### 3.4 管程 ⭐⭐⭐

**管程（Monitor）** = 把**共享变量**和**作用于它的操作**封装在一个模块/类里，并保证**同一时刻只允许一个进程在管程内活动**。

| 特性 | 说明                                    |
| -- | ------------------------------------- |
| 封装 | 共享数据只能通过管程内的过程访问，外部不能直接改              |
| 互斥 | **由编译器自动加锁**：进程进入管程即获得互斥，退出即释放        |
| 同步 | 用**条件变量** + `wait` / `signal` 实现等待与唤醒 |
| 优点 | 同步互斥交给编译器，程序员不易写错（比裸信号量安全）            |

> [!tip]+ 面试一句话  
> 管程的作用：一次只允许一个进程进入管程内，便于控制和管理临界区，实现资源共享与进程互斥。Java 的 `synchronized` + `wait()/notify()`、C# 的 `lock` 都是管程的实现。

### 3.5 进程同步的意义 ⭐⭐⭐

- **保证结果可再现**：并发进程共享资源时，若不控制相对推进速度，结果会取决于调度时机 → 产生"与时间有关的错误"（如两个进程同时 `count++`，出现丢失更新）。
- **保证互斥**：共享资源（打印机、全局变量、文件）同一时刻只被一个进程使用。
- **保证先后顺序**：有依赖关系的操作必须按序执行（先生产后消费、先写后读、先赋值后使用）。
- **一句话**：同步把"并发"从**不可预测**变成**可控**，是并发程序正确性的前提。

## 4. CPU 调度

> [!note]+ 章节导引  
> **本章知识点之间的关系**：有了进程就要决定"谁先用 CPU"。逻辑链：**调度层次**（高/中/低级）→ **批处理调度**（FCFS→SJF→SRTF→HRRF，追求吞吐量）→ **交互式调度**（RR→优先级→MFQ，追求响应时间）→ **实时调度**（RMS→EDF，追求确定性）→ **优先级反转**问题及其解决。
>
> **与上一章的关系**：调度决定哪个进程/线程获得 CPU，是进程管理的延伸。
>
> **与学科的关系**：调度算法是 OS 性能的关键，MFQ 是实际系统的主流方案。

### 4.1 调度算法对比 ⭐⭐⭐⭐

**① 缩写 → 英文全称 → 中文名** ⭐⭐

| 缩写           | 英文全称                                   | 中文名      | 抢占？    |
| ------------ | -------------------------------------- | -------- | ------ |
| **FCFS**     | First Come First Served                | 先来先服务    | 非抢占    |
| **SJF**      | Shortest Job First                     | 最短作业优先   | 非抢占    |
| **SRTF**     | Shortest Remaining Time First          | 最短剩余时间优先 | **抢占** |
| **HRRF**     | Highest Response Ratio First（也写作 HRRN） | 高响应比优先   | 非抢占    |
| **RR**       | Round Robin                            | 时间片轮转    | 抢占     |
| **Priority** | Priority Scheduling                    | 优先级调度    | 是/否均可  |
| **MFQ**      | Multi-level Feedback Queue             | 多级反馈队列   | 抢占     |
| **MLQ**      | Multi-level Queue                      | 多级队列     | 抢占     |
| **RMS**      | Rate Monotonic Scheduling              | 速率单调调度   | 抢占     |
| **EDF**      | Earliest Deadline First                | 最早截止期优先  | 抢占     |

> [!tip]+ HRRF 的两个写法  
> **HRRF**（Highest Response Ratio **First**）和 **HRRN**（Highest Response Ratio **Next**）是同一个算法的两种叫法，都译作"高响应比优先"，遇到哪个都认识就行。

**② 算法对比**

| 算法           | 抢占？   | 核心思想                   | 优点                 | 缺点                        |
| ------------ | ----- | ---------------------- | ------------------ | ------------------------- |
| **FCFS**     | 否     | 先来先服务                  | 简单、公平、无饥饿          | **短作业等很久**（护航效应）          |
| **SJF**      | 否     | 最短作业优先                 | **平均周转时间最小**       | 长作业饥饿；需预知运行时间             |
| **SRTF**     | 是     | 最短**剩余**时间优先（SJF 的抢占版） | **平均等待时间最优**       | 长作业**饥饿更严重**；频繁比较剩余时间，开销大 |
| **HRRF**     | 否     | 高响应比优先                 | **兼顾长短作业，长作业不会饿死** | 每次调度要算全部进程的响应比，开销大        |
| **RR**       | 是     | 时间片轮转                  | 公平、响应好             | 时间片大小难定                   |
| **Priority** | 是/否均可 | 优先级高的先获得 CPU           | 可区分紧急任务、支持实时       | 低优先级进程**饥饿**              |
| **MFQ**      | 是     | 多队列+反馈                 | **兼顾各类进程**         | 实现复杂                      |

> [!tip]+ 面试问"五种进程调度算法"怎么答  
> 先答稳的五个：**FCFS（先来先服务）、SJF（最短作业优先）、RR（时间片轮转）、Priority（优先级）、MFQ（多级反馈队列）**。  
> 追问的延伸一起准备：**SRTF** = SJF 的抢占版；**HRRF** = 高响应比优先，用来治 SJF/SRTF 的饥饿；**MLQ** = 多级队列（队列之间不反馈）；**RMS / EDF** = 实时调度。

**HRRF 详解** ⭐⭐⭐

> [!tip]+ HRRF：Highest Response Ratio First（高响应比优先）  
> 每次调度前，计算就绪队列中每个进程的**响应比**，选最大的投入运行：
>
> **响应比 = (等待时间 + 要求服务时间) / 要求服务时间 = 1 + 等待时间 / 要求服务时间**
>
> - **等待越久 → 响应比越大**：长作业的优先级会随等待自动升高，**不会饿死**（相对 SJF / SRTF 的核心优势）；
> - **服务时间越短 → 响应比越大**：短作业依然优先，保留了 SJF 的高效率。
> - 因此它是 **FCFS 与 SJF 的折中**：兼顾长短作业。代价是每次调度都要把所有就绪进程的响应比算一遍，开销较大，实际系统极少直接使用。

**MFQ 的设计逻辑** ⭐⭐⭐⭐：

1. 多个就绪队列，优先级**逐级降低**，时间片**逐级加倍**
2. 新进程进入最高优先级队列，用完时间片降级
3. I/O 型进程自然留在高层；计算型进程逐渐下沉
4. → **短作业 / I/O 型进程得到快速响应**

> [!tip]+ 优先级反转  
> 高优先级等低优先级进程持有的锁，此时中间优先级进程就绪，抢占了低优先级进程的 CPU → 解决方案：**优先级继承**（低优先级拿到锁期间临时提升到等待这个锁的最高优先级，释放锁后恢复到原来优先级）。

### 4.2 抢占式 vs 非抢占式：哪个开销大？ ⭐⭐⭐

**抢占式开销更大。** 三个原因：

1. **切换次数多**：时间片到、更高优先级进程就绪、中断到来都能触发切换；非抢占式只在进程**主动放弃 CPU**（阻塞 / 结束）时切换。
2. **每次都要保存和恢复完整现场**：保存 CPU 环境（PC、通用寄存器、PSW、栈指针）→ 陷入内核 → 更新 PCB → 选新进程 → 切换页表并刷新 TLB / Cache → 恢复现场 → 返回用户态。
3. **隐性代价（真正的大头）**：频繁切换会不断破坏 **Cache 和 TLB 的命中率**，新进程第一次访存几乎全是缺失。

**非抢占式**：切换时机少、开销小、实现简单，但一个死循环或长任务就能卡住整个系统，响应差。

> [!tip]+ 面试一句话  
> 抢占式开销大——切换频繁，且每次都要中断、保存 CPU 环境、换页表、恢复现场，还要付出 Cache/TLB 失效的代价；换来的是更好的响应性和公平性。

### 4.3 时间片轮转：进程很多时会怎样？ ⭐⭐⭐⭐

**会影响响应时间。** 设就绪队列有 $n$ 个进程、时间片为 $q$，一个进程两次获得 CPU 之间大约要等 $(n-1)q$ —— **响应时间随进程数线性增长**。进程开得越多：

- 每个进程的等待被拉长，用户感觉"卡"；
- 上下文切换本身也吃 CPU，时间片越小时切换开销占比越高（有效算力大幅下降）。

**解决办法**：

1. **多级反馈队列（MFQ）**：交互型 / 短作业放在高优先级、小时间片的队列，计算型进程逐渐下沉 → 用户直接感受到的响应最快（现代通用 OS 的主流做法）。
2. **动态调整时间片**：按系统负载和进程类型调整 $q$（Linux 的 CFS 干脆改成按权重分配 CPU 时间，而不是固定轮转）。
3. **优先级调度**：给交互进程更高优先级，抢占批处理任务。
4. **分组轮转 / 限制并发**：把进程分组分时复用，缩短单个就绪队列的长度。

> [!tip]+ 面试一句话  
> RR 的等待时间约为 (n−1)×q，进程越多响应越差；解法是分层——用 MFQ 让交互任务走高层小时间片，别让它们和计算型进程排在同一条队里。

## 5. 内存管理

> [!note]+ 章节导引  
> **本章知识点之间的关系**：内存管理是"解决碎片"的演进史。逻辑链：**固定分区**（内碎片）→ **可变分区**（外碎片，First/Next/Best/Worst Fit）→ **分页**（消除外碎片，内碎片≤1页）→ **分段**（按逻辑划分，方便共享保护）→ **段页式**（两者结合）→ **虚拟存储**（只加载需要的部分，解决容量限制）。每次升级都是前一个方案"不够好"时的改进。
>
> **与上一章的关系**：内存管理是独立模块，但和进程管理通过"进程需要内存空间"连接。
>
> **与学科的关系**：分页和虚拟存储是面试最高频的部分，尤其是 TLB 和页面置换。

### 5.1 分页管理 ⭐⭐⭐⭐

**演进：从连续分配到分页**

| 阶段       | 做法                                  | 遗留的问题                                                      |
| -------- | ----------------------------------- | ---------------------------------------------------------- |
| **连续分配** | 每个进程占用一段**连续**内存                    | ① 进程地址不隔离 ② 内存使用效率低（碎片）③ 大量换入换出 ④ 程序运行的**地址不确定**（每次装入位置不同） |
| **分段**   | 按逻辑单位划分，虚拟地址映射物理地址                  | 解决 ① 地址隔离和 ④ 地址不确定；仍有**外碎片**                               |
| **分页**   | 地址空间切成大小**固定**的页，做到哪一页就装入哪一页，否则留在硬盘 | 分配单位小 → 内存使用效率高，碎片只剩**内碎片（不足一页）**                          |

> [!tip]+ 一句话  
> 分页的思想是"**把内存切小，按需装**"——页小且固定，所以既没有外碎片，也天然支持后来的虚拟内存。

**地址转换**：逻辑地址 = 页号 | 页内偏移 → 查页表得页框号 → 物理地址 = 页框号 | 页内偏移

**代价**：每次访存需**两次内存访问**（查页表+访数据）→ 需要 **TLB** 加速

### 5.2 TLB 与多级页表 ⭐⭐⭐⭐

| 问题   | 解决方案             | 关键                   |
| ---- | ---------------- | -------------------- |
| 页表太慢 | **TLB**（页表的高速缓存） | 命中时 1 次访存，典型命中率 99%+ |
| 页表太大 | **多级页表**         | 只放当前需要的页表项，需更多 TLB   |

### 5.3 分页 vs 分段 ⭐⭐⭐

|       | 分页             | 分段             |
| ----- | -------------- | -------------- |
| 划分依据  | **物理大小**（系统行为） | **逻辑关系**（用户可见） |
| 大小    | 固定             | **可变**         |
| 共享/保护 | 困难             | **方便**         |
| 碎片    | 内碎片            | 外碎片            |

### 5.4 虚拟存储 ⭐⭐⭐⭐（面试极高频）

**核心动机**：常规内存管理要求程序**全部装入**→ 内存不够用！

**虚拟存储**：像 Cache 一样，把内存当磁盘的"缓存"——**只加载当前需要的部分**。

**虚拟内存的意义** ⭐⭐⭐⭐：

1. **扩大可用内存**：通过虚拟技术把**外部存储设备的一部分空间**划分出来，作为内存不足时临时存放数据的缓存区（交换区 / 页面文件）。
2. **让"程序比内存大"也能跑**：程序不必全部装入内存，只装入当前用到的部分，其余留在磁盘按需调入（按需调页 demand paging）。电脑上运行的程序都要经由内存执行，若程序占用内存很大或很多，内存会被耗尽，此时就靠虚拟内存顶上去。
3. **容量与并发的解耦**：多道程序的并发数不再被物理内存大小硬性限制。
4. **地址隔离（附带好处）**：每个进程拥有独立、连续、从 0 开始的逻辑地址空间，互不干扰。

> [!tip]+ 一句话  
> 虚拟内存 = 把磁盘当成内存的二级缓存，"按需调页 + 页面置换"使物理内存不足时程序依然能跑；顺带给了每个进程一个独立连续的地址空间。

**局部性原理**（理论根基）⭐⭐⭐⭐：

- **时间局部性**：刚访问的，不久可能再访问（循环、热点数据）
- **空间局部性**：刚访问的附近，可能也被访问（顺序访问数组）

**页面置换算法** ⭐⭐⭐⭐：

| 算法            | 英文全称                     | 中文名        | 思想            | 特点                                      |
| ------------- | ------------------------ | ---------- | ------------- | --------------------------------------- |
| **OPT**       | Optimal Page Replacement | 最佳置换算法     | 替换最远将来才用的     | 理论最优（缺页最少），**无法实现**，只作评价基准              |
| **FIFO**      | First In First Out       | 先进先出       | 替换最早进入的       | 简单，但性能差，会出现 **Belady 异常**               |
| **LRU**       | Least Recently Used      | 最近最久未使用    | 替换最久未访问的      | **最实用**，性能接近 OPT；属**堆栈类算法**，无 Belady 异常 |
| **LFU**       | Least Frequently Used    | 最不经常使用     | 替换访问**次数最少**的 | 按频次淘汰；早期高频页长期占位，很少单独使用                  |
| **Clock**     | Clock / Second Chance    | 时钟置换（二次机会） | FIFO + 访问位    | LRU 的**近似**，开销远小于 LRU，是实际系统的主流          |
| **改进型 Clock** | Enhanced Second Chance   | 改进型时钟置换    | 访问位 + **修改位** | 优先淘汰"未访问且未修改"的页，**减少写回磁盘的 I/O**         |

> [!tip]+ Belady 异常  
> **给进程多分物理块，缺页率反而升高**，这叫 Belady 异常（只发生在 FIFO 这类算法上）。
>
> - **会出现**：FIFO（以及基于它的 Clock / 二次机会类算法）。
> - **不会出现**：LRU、OPT —— 它们满足**堆栈性质**（物理块数增加时，任一时刻的内存页集合是原集合的子集，缺页集合单调收缩）。

> [!tip]+ 虚拟内存 vs Cache  
> Cache 解决**速度**差距；虚拟存储解决**容量**限制。Cache 硬件管理；虚拟存储 OS+硬件管理。缺失代价差 1000 倍。

### 5.5 逻辑地址 vs 物理地址 ⭐⭐⭐

| 概念                    | 含义                       | 谁在用                     |
| --------------------- | ------------------------ | ----------------------- |
| **逻辑地址**（相对地址 / 虚拟地址） | 从 0 开始的连续地址空间，是程序内部使用的地址 | **程序员编程 / 编译链接 / 进程自身** |
| **物理地址**（绝对地址）        | 内存单元的真实硬件地址              | **硬件访存（经 MMU 转换之后）**    |

**转换过程**：逻辑地址 →（MMU 查页表，命中 TLB 则加速）→ 物理地址。

程序**只能看到和使用逻辑地址**，物理地址对用户程序完全透明——这正是进程隔离与地址保护的基础。

> [!tip]+ 面试一句话  
> 程序员编程用的地址是逻辑地址（相对地址），从 0 开始、连续可移植；CPU 真正访存用的是物理地址，两者之间由 MMU 通过页表映射。

### 5.6 页式存储管理的优劣 ⭐⭐⭐⭐

|        | 内容                                                                                                                                                                            |
| ------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **优点** | ① **无外碎片**，内存利用率高；② 页大小固定 → 内存分配/回收简单（空闲页用位示图管理即可）；③ 支持**离散分配**与**按需调页**，是虚拟内存的实现基础；④ 便于实现访问保护（页表项带读写/权限位）；⑤ 内存与程序逻辑解耦，程序不必连续存放                                               |
| **缺点** | ① 有**页内碎片**（最后一页用不满的部分，平均浪费半页）；② **页表本身占内存**（地址空间大时需多级页表或反置页表）；③ 一次访存需**两次访问内存**（查页表 + 取数据），要靠 TLB 加速；④ 按**物理**单位划分、与程序逻辑无关，**不利于共享和保护**（分段更自然）；⑤ 需要额外的硬件支持（MMU、TLB）和缺页处理软件开销 |

**分页产生内碎片还是外碎片？** → **内碎片**。内存被切成固定大小的页框，任何浪费都只可能是"最后一页没装满"。**外碎片**是可变分区和分段的问题。

> [!tip]+ 面试一句话  
> 分页只有内碎片、没有外碎片；分段只有外碎片、没有内碎片；段页式兼有两者的结构特点（外层分段、内层分页）。

### 5.7 内存泄漏的原因 ⭐⭐⭐

**内存泄漏** = 程序向系统**申请了内存（通常是堆）却不再释放**，同时也没有任何指针能再指向它 —— 这块内存既用不到，也回收不了。

**常见原因**：

1. **忘记释放**：`malloc` / `new` 之后漏了 `free` / `delete`（尤其提前 `return`、异常抛出等分支）。
2. **指针丢失**：指针被重新赋值或离开作用域，堆块失去唯一引用（链表删节点时只断了链、没释放）。
3. **申请与释放不匹配**：`new[]` 配 `delete`、`malloc` 配 `delete`，释放不完整或行为未定义。
4. **容器只增不减**：动态数组、哈希表、缓存只往里塞、从不淘汰（逻辑泄漏）。
5. **多态基类析构函数未声明为虚**：`delete` 基类指针只调用基类析构，派生类成员没释放。
6. **循环引用**：引用计数型智能指针互相持有，计数永远归不了零。

**后果**：进程常驻内存持续增长 → 换页增多、系统变慢，最终被 OOM 杀掉。  
**发现与避免**：Valgrind / AddressSanitizer 等工具检测；C++ 用 **RAII + 智能指针**；缓存设淘汰策略；长时间服务定期重启。

> [!tip]+ 面试一句话  
> 泄漏的本质是"申请了，但已经没人能再释放它"——要么忘了 free，要么指针丢了，要么循环引用。工程上靠 RAII / 智能指针从根上避免。

### 5.8 Cache 的替换策略 ⭐⭐⭐

当 Cache（或 TLB、页框）已满、又发生缺失时，决定替换掉哪一块：

| 策略             | 思想                   | 特点                                        |
| -------------- | -------------------- | ----------------------------------------- |
| **随机（Random）** | 任意挑一块                | 硬件最简单，命中率不稳定                              |
| **FIFO**       | 替换最早调入的              | 简单，但可能踢掉马上还要用的块                           |
| **LRU**        | 替换**最久未被访问**的        | 命中率最高，但要精确维护访问顺序，硬件代价大                    |
| **LFU**        | 替换访问**次数最少**的        | 适合热点稳定的场景，易被"历史高频"过时数据干扰                  |
| **近似 LRU**     | **Clock / 二次机会**、NRU | **实际主流**：每块一个访问位，替换时若访问位为 1 就清 0 并给它第二次机会 |

**写策略**（常连着问）：**写直达 Write Through**（每次都写内存，简单、一致性好、访存多）vs **写回 Write Back**（只在被替换时才写回，配合 **dirty 位**，效率高但有缓存一致性问题）。

> [!tip]+ 面试一句话  
> Cache 替换的依据是局部性：LRU 最理想但太贵，实际用 Clock 这类近似 LRU，Clock是环形的NRU；写策略主流是写回 + dirty 位。

## 6. I/O 与磁盘管理

> [!note]+ 章节导引  
> **本章知识点之间的关系**：I/O 管理的目标是"让 CPU 尽量少参与 I/O"。逻辑链：**程序直接控制**（CPU 轮询，最浪费）→ **中断方式**（I/O 完成后通知 CPU）→ **DMA**（数据直接在设备和内存间传送，CPU 只在开始和结束介入）→ **通道方式**（专用 I/O 处理机）。磁盘调度则优化寻道时间。
>
> **与上一章的关系**：I/O 是进程等待的重要原因（进程从运行→阻塞，通常等的就是 I/O）。
>
> **与学科的关系**：DMA 是高性能 I/O 的标配，磁盘调度是数据库和文件系统的基础。

### 6.1 磁盘调度 ⭐⭐⭐

| 算法       | 思想     | 优缺点           |
| -------- | ------ | ------------- |
| FCFS     | 按请求顺序  | 公平但寻道长        |
| SSTF     | 最短寻道优先 | 局部最优但可能**饥饿** |
| SCAN（电梯） | 来回扫描   | 不饥饿           |
| C-SCAN   | 只单向扫描  | 更均匀           |

### 6.2 DMA 是什么，解决了什么问题 ⭐⭐⭐⭐

**DMA = Direct Memory Access（直接存储器访问）**。

**它解决的问题**：在"程序直接控制"和"中断方式"下，数据都要在**设备 ↔ CPU 寄存器 ↔ 内存**之间倒腾，**每个字节/字都要 CPU 经手**——轮询是把 CPU 锁死在等待里，中断方式虽然不用忙等，但每传一个数据块就要中断一次 CPU。CPU 的性能全被搬运工活计吃掉了。

**DMA 的做法**：给设备配一个 **DMA 控制器（DMAC）**。CPU 只在传输**开始前**把源地址、目的地址、传送字节数（和方向）写进 DMAC 的寄存器，之后**数据在设备和内存之间直接成块传送，不经过 CPU**；整批传完后 DMAC 发一次**中断**通知 CPU 收工。

| I/O 方式     | CPU 参与程度             | 数据通路                   |
| ---------- | -------------------- | ---------------------- |
| 程序直接控制（轮询） | 全程忙等                 | 设备 → CPU → 内存          |
| 中断方式       | 每传一块就中断一次            | 设备 → CPU → 内存          |
| **DMA**    | 只在开头设参数、结尾收中断        | **设备 ↔ 内存（数据不经过 CPU）** |
| 通道方式       | 更少（专用 I/O 处理机执行通道程序） | 设备 ↔ 内存                |

> [!tip]+ 面试一句话  
> DMA 的全称是 Direct Memory Access，让外设和内存之间直接成块地传数据、不占用 CPU，只在开始（设置参数）和结束（响应中断）时惊动 CPU，把 CPU 从逐字节搬运中解放出来。
>
> 通道一次可完成多个IO，DMA一次只能完成一个；一条通道可以轮流控制多个外设，一个DMA一般同一时刻只能控制1台

## 7. 文件系统

> [!note]+ 章节导引  
> **本章知识点之间的关系**：文件系统回答"磁盘上的数据怎么组织"。逻辑链：**文件逻辑结构**（用户怎么看：记录式/流式）→ **文件物理结构**（磁盘怎么存：连续/链接/FAT/索引）→ **目录结构**（怎么找到文件：一级→两级→树形→无环图）。
>
> **与上一章的关系**：文件系统建立在磁盘管理之上，是磁盘数据的逻辑组织。
>
> **与学科的关系**：文件物理结构是面试重点——索引分配（Unix inode）是数据库 B+ 树的前身。

### 7.1 文件物理结构对比 ⭐⭐⭐

| 结构                             | 顺序读   | 随机读      | 碎片      |
| ------------------------------ | ----- | -------- | ------- |
| **连续分配**                       | 极快    | 极快       | **外碎片** |
| **链接分配，每块末尾存下一块块号**            | 跟指针，慢 | **不能**   | 无       |
| **FAT，FAT表中FAT[i]=j表示i的下一块是j** | 较快    | 需遍历FAT   | 无       |
| **索引分配，开辟索引块存放所有数据块的块号**       | 快     | **直接定位** | 无       |

> [!tip]+ 索引分配的扩展  
> 索引块放不下怎么办？→ 多级索引（类似多级页表）、混合索引（Unix inode：10 直接 + 1 间接 + 1 二级间接 + 1 三级间接）

## 8. 进程间通信（IPC） ⭐⭐⭐⭐

### 8.1 进程间通信的方式 ⭐⭐⭐⭐

**标准答案（先报这一串）**：管道 → 命名管道 → 消息队列 → 共享内存 → 信号量 → 信号 → Socket。被问「几种」时，答**管道、消息队列、共享内存、信号量、Socket** 这五类最稳，再补「信号」和「命名管道」。

| 方式         | 特点               | 适用场景   |
| ---------- | ---------------- | ------ |
| **管道**     | 半双工，**只限亲缘进程**   | 父子进程   |
| **命名管道**   | 有路径名，**无亲缘限制**   | 任意进程   |
| **消息队列**   | 消息的链表，有格式        | 结构化消息  |
| **共享内存**   | **最快**的 IPC（零拷贝） | 大量数据传输 |
| **信号量**    | 计数器，同步/互斥        | 配合共享内存 |
| **信号**     | 异步通知             | 异常处理   |
| **Socket** | 可跨网络通信           | 网络通信   |

> [!tip]+ 面试一句话  
> 共享内存最快（直接读写），管道最简单（亲缘进程），Socket 最通用（跨网络）。

> [!warning]+ 三个易混点
> - **管道 vs 命名管道**：匿名管道只存在于内存中，只能给父子这类亲缘进程用；命名管道（FIFO）在文件系统里有个名字，任意进程都能打开。
> - **信号 vs 信号量**：信号（signal）是"通知"，异步打断进程、本身不带数据；信号量（semaphore）是"计数器"，专门做同步互斥，不传递信息。
> - **共享内存为什么最快**：同一块物理内存被映射进多个进程的地址空间，读写不经过内核，零拷贝；代价是**它自己不管同步**，必须额外配一个信号量或锁。

### 8.2 Windows 与 Linux 的 IPC 手段对照 ⭐⭐⭐

| 手段      | Linux                                         | Windows                         |
| ------- | --------------------------------------------- | ------------------------------- |
| 管道      | `pipe()`（匿名）、FIFO（`mkfifo`）                   | 匿名管道、**命名管道 Named Pipe**（可跨机器）  |
| 消息队列    | System V `msgget` / POSIX `mq_open`           | 消息队列、窗口消息（`PostMessage`）        |
| 共享内存    | System V `shmget` / POSIX `shm_open` + `mmap` | **文件映射 File Mapping**           |
| 信号量 / 锁 | System V、POSIX 信号量                            | Semaphore / Mutex / Event 等内核对象 |
| 信号      | `signal` / `sigaction`                        | 无完全等价的 POSIX 信号（用 APC、事件对象替代）   |
| 套接字     | BSD Socket、Unix Domain Socket                 | Winsock                         |
| 其他      | `eventfd`、域套接字                                | 邮槽 Mailslot、剪贴板、DDE、COM         |

> [!tip]+ 面试一句话  
> Linux 更贴近 POSIX（管道、信号、System V IPC），Windows 更依赖内核对象（事件、互斥体、文件映射）；要一份跨平台通用答案，说 **Socket** 最稳。

## 9. 实验与拓展问题

> [!note]+ 章节导引  
> 本章收录两类"非教科书"问题：一是**让你介绍自己的 OS 实验**（面试官用来判断你是不是真的动过手），二是**偏硬件与工程实现**的开放题。前者必须用**自己的话**讲。

### 9.1 简要介绍自己的 OS 实验课做了什么 ⭐⭐⭐⭐

> [!note]+ 一句话概括  
> 用了一个学期，在一台"模拟出来的 MIPS 电脑"上，从开机第一条指令开始，一步步做出一个能跑的小操作系统——内存、进程、系统调用、文件系统、命令行，都是自己写出来的。

**这门实验在干什么**

课程给的是一份叫 MOS 的实验框架（参考了 MIT 的教学系统 JOS 的思路）。硬件不用真机，用 **QEMU 模拟出一个 MIPS 的 CPU**；代码在 Linux 下写，用 Makefile 组织编译、Git 交作业，配了自动评测。

最有意思的设计是**"增量式"**：每个 Lab 只加几百行代码，能单独跑、单独测，但后面的建立在前面的基础上——**从 Lab1 写的代码会一路用到 Lab6**，最后拼成一个完整能跑的系统。所以它不是六道互不相干的题，而是**一直在养同一个东西长大**。

**六个 Lab，用大白话说**

| Lab      | 一句话       | 具体做了什么                                                                                                          |
| -------- | --------- | --------------------------------------------------------------------------------------------------------------- |
| **Lab0** | 熟悉工具      | 用熟 Linux、Git、Makefile、Vim，学会写基本的 shell 脚本                                                                       |
| **Lab1** | 让"电脑"开机成功 | 搞清楚"硬件要等软件、软件又要硬件载入"这个死循环是怎么破的；弄明白程序会被放到内存的什么位置、地址是怎么定的；写最底层的代码，让内核能启动起来，并实现一个能在屏幕上打印的内核版 `printf`              |
| **Lab2** | 管内存       | 一边管**物理内存**（哪些内存块空着、谁在用），一边管**虚拟内存**（让每个程序都以为自己独占一大片连续内存）；写地址对照表，还要处理 CPU 里那张"常用地址缓存表"的失效与重填                    |
| **Lab3** | 让别人的程序跑起来 | 建一张"进程表"记录每个程序的运行状态；把用户程序加载进内存并真正跑起来；再做一个**时钟中断**——每隔一小段时间强行把控制权从程序手里收回内核，内核趁机决定下一个跑谁。**这就是"多个程序轮流用 CPU"的实现基础** |
| **Lab4** | 给用户程序开一扇门 | 用户程序不许碰硬件、也不许看别人的内存，想干活只能走内核开的"门"（系统调用）；实现进程之间通信；实现 `fork`（复制出一个新进程），并用**写时复制**让复制又快又省内存                        |
| **Lab5** | 把数据存下来    | 内存一断电就没了，所以数据得落到磁盘上。这里做了一个简单的文件系统：能读磁盘、能按名字找到文件、能读写；并把文件、控制台、管道三类东西统一成一种接口管理                                    |
| **Lab6** | 造一个命令行    | 先实现管道（一个程序的输出直接接进另一个程序的输入），再写一个最简 shell：能解析你敲的命令、能启动程序、能处理管道和重定向。到这一步，前面几部分串起来就是个真能用的系统了                        |

除了这六个，还有**挑战性任务**（课程设计里留给"拔高"的一层）。我做的是把 shell 再增强一版，支持**环境变量**、**命令历史**和**行编辑**。

**30 秒口述版**（面试直接说这段）

"我们的操作系统实验是在模拟出来的 MIPS 平台上，用一个学期从零做一个能跑的小系统。它是增量式的：Lab1 让内核能启动、能打印，Lab2 管内存，Lab3 做出进程和时钟中断（靠它实现进程切换），Lab4 做系统调用和 `fork`，Lab5 做文件系统，Lab6 做管道和 shell，最后拼成一个完整能运行的操作系统。因为代码是一路累加下来的，所以对'一个操作系统怎么从一块裸板长出来'，体会比较深。"

**可能被追问，提前准备好这几条**

- **为什么要做时钟中断？** —— 没有它，内核把 CPU 交给用户程序之后就再也拿不回来了。时钟中断是内核"定期收权"的手段，也是进程能切换的前提。
- **`fork` 为什么要用写时复制？** —— 直接整块复制又慢又浪费内存。先让父子进程共用同一份内存、标成只读，谁要写谁再触发一次异常、只复制那一页——又快又省。
- **虚拟内存解决了什么？** —— 让每个程序都以为自己独占一大片连续内存（好写程序），同时把它们互相隔开（安全），还顺带让"程序比内存大"也能跑。
- **印象最深的一个坑？** —— 说个真实的，比如磁盘读写时数据还留在缓存里、设备那头已经更新导致的不一致。

> [!warning]+ 面试提醒  
> 这题**一定要用自己的话讲**，按"我想做出一个什么东西 → 中间卡在哪 → 我怎么解决的"来讲，比背 Lab 清单有效得多。面试官一般会顺着追问某一个 Lab 的细节，**把 Lab2（内存）和 Lab3（进程与时钟中断）弄熟收益最大**。

### 9.2 如何在自己的 OS 和 CPU 上进行高级语言编程 ⭐⭐

这题在问：**从"内核能跑"到"能用 C/高级语言写程序"，中间还缺哪几环？**

1. CPU硬件必须满足**基础运行要求**  
   高级语言编译后会生成常规机器指令，CPU必须完整支持**算数运算、内存访问、程序跳转**等基础指令。同时必须具备**用户态与内核态切换、中断和异常处理机制**，否则无法支撑程序正常运行、权限隔离和错误处理。
2. 操作系统必须提供**程序运行基础环境**  
   首先需要可执行**文件加载器**，能够解析编译后的程序文件，将代码、数据映射到进程的虚拟内存空间。其次需要完善的**系统调用接口**，高级语言的内存申请、读写、程序退出等功能，都依赖系统调用完成。最后需要**进程管理和内存管理机制**，为每个程序分配独立地址空间、用户栈和页表，保证程序独立运行。
3. 配套**工具链**与**运行库**必须适配平台  
   需要适配自制CPU架构的**编译器、汇编器、链接器**，能够将高级语言代码编译、链接为当前CPU可识别的可执行文件。同时必须移植**C标准库**，实现printf、malloc等通用函数。最后依靠交叉编译，在主机上编译出适配自制软硬件平台的程序。

> [!tip]+ 面试一句话  
> 能在自己的 OS 上写高级语言 = CPU具备完整指令和权限、中断机制 + OS提供**加载器和系统调用** + 有能生成该 CPU 指令的**编译器/汇编器/链接器** 并 移植了 **C 标准库**；这三块缺任何一块，语言都跑不起来。

## 附：OS 面试速查表

| 问题                 | 一句话回答                                                                         |
| ------------------ | ----------------------------------------------------------------------------- |
| 进程 vs 线程           | 进程是资源分配单位，线程是调度单位；线程共享进程资源                                                    |
| 进程状态转换             | 就绪→运行(调度) 运行→就绪(时间片) 运行→阻塞(等I/O) 阻塞→就绪(事件完成)                                  |
| IPC 方式             | 管道、消息队列、共享内存、信号量、信号、Socket                                                    |
| 临界区原则              | 空闲让进、忙则等待、有限等待、让权等待                                                           |
| 死锁四条件              | 互斥、请求占有、不可剥夺、环路等待                                                             |
| 银行家算法              | 分配前验证安全性，不安全则不分配                                                              |
| 页面置换               | OPT（最佳）→ LRU（最近最久未使用）→ Clock（时钟/二次机会）→ FIFO（先进先出），性能递减；FIFO 有 Belady 异常       |
| 虚拟内存原理             | 局部性→按需调页→缺页中断→页面置换                                                            |
| 分页 vs 分段           | 页=物理单位(固定) 段=逻辑单位(可变)                                                         |
| 调度算法               | FCFS、SJF、SRTF、HRRF、RR、优先级、MFQ（含 MLQ / RMS / EDF）                              |
| 算法全称               | FCFS 先来先服务 / SJF 最短作业优先 / SRTF 最短剩余时间优先 / HRRF 高响应比优先 / RR 时间片轮转 / MFQ 多级反馈队列 |
| Windows / Linux 调度 | Windows = 优先级抢占式多级反馈队列；Linux = CFS 完全公平调度                                     |
| 进程 vs 程序           | 进程 = 程序 + 数据 + PCB，动态；程序 = 静态指令集合                                             |
| 为什么引入线程            | 进程太重、IPC 太贵、单进程无法多核并行 → 资源归进程、调度归线程                                           |
| 什么是临界区             | 进程中访问共享资源的代码段，需保证同一时刻仅一个进程在内                                                  |
| 管程                 | 一次只允许一个进程进入，封装共享变量 + 由编译器自动保证互斥                                               |
| 进程同步的意义            | 让并发的推进顺序可控：结果可再现、资源互斥、操作有序                                                    |
| 抢占 vs 非抢占          | 抢占式开销大：中断→保存 CPU 环境→换页表→恢复，且 Cache/TLB 失效                                     |
| 时间片轮转与响应           | 等待 ≈ (n−1)×q，进程越多越慢 → 用 MFQ / 动态时间片 / 优先级解决                                   |
| 逻辑地址 vs 物理地址       | 程序员用逻辑地址；MMU 经页表（TLB 加速）转成物理地址                                                |
| 分页的碎片              | 只有内碎片，没有外碎片（分段只有外碎片）                                                          |
| 页式存储的优劣            | 优：无外碎片、分配简单、支持虚拟内存；劣：内碎片、页表占内存、两次访存、不利于共享                                     |
| 内存泄漏原因             | 忘 free、指针丢失、申请释放不匹配、容器只增不减、基类析构非虚、循环引用                                        |
| Cache 替换策略         | 随机、FIFO、LRU、LFU、Clock（近似 LRU）；写策略：写回 + dirty 位                                |
| DMA                | Direct Memory Access，设备↔内存直接成块传送，CPU 只在首尾介入                                   |
