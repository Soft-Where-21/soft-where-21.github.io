## 1. 数据库基础与关系模型

### 1.1 三级模式 + 二级映像 ⭐⭐⭐

**Q [⭐⭐⭐]【1.1.Q1】：数据库的三级模式结构是什么？各有多少个？**

A：数据库的体系结构分三层，**只有模式与内模式各一个，外模式可以有多个**：

| 层次 | 对应 | 数量 |
| --- | --- | --- |
| **外模式**（用户模式） | 用户视图，用户能看到和使用的局部数据 | 多个 |
| **模式**（概念模式） | 全体数据的逻辑结构 | **1 个** |
| **内模式**（存储模式） | 数据在物理存储上的组织方式 | **1 个** |

**Q [⭐⭐⭐]【1.1.Q2】：什么是二级映像？它保证了哪两个独立性？**

A：三级模式之间靠两级映像连接：

- **外模式/模式映像** → 保证**逻辑独立性**：修改全局逻辑结构（模式）时，只需改映像，用户程序与外模式不用动；
- **模式/内模式映像** → 保证**物理独立性**：修改物理存储方式（内模式）时，只需改映像，逻辑结构不用动。

**一句话**：两级映像的意义就是"**改下层不影响上层**"，让数据和程序解耦。

### 1.2 关系代数 ⭐⭐⭐

**Q [⭐⭐⭐]【1.2.Q1】：关系代数有哪些常用运算？分别对应 SQL 的什么？**

A：关系代数是 SQL 的数学基础，SQL 是它的工程化实现：

| 运算 | 符号 | SQL 对应 | 说明 |
| --- | --- | --- | --- |
| 选择 | $\sigma$ | WHERE | **行**过滤（按条件挑元组） |
| 投影 | $\pi$ | SELECT | **列**过滤（挑出若干属性） |
| 连接 | $\bowtie$ | JOIN | 按条件合并两表 |
| 自然连接 | $\bowtie$ | NATURAL JOIN | 同名列等值连接 + 去掉重复列 |
| 除 | $\div$ | / | "包含"类查询（如"选修了全部课程的学生"） |

> 记忆：**选择管行、投影管列、连接管表间合并、除管"全都"**。

### 1.3 数据库的完整性约束 ⭐⭐⭐

**Q [⭐⭐⭐]【1.3.Q1】：数据库的完整性约束有哪几类？分别约束什么、怎么实现？**

A：共四类，**前三类是关系模型固有的，第四类由应用语义附加**：

| 类型 | 约束对象 | 含义 | SQL 实现 |
| --- | --- | --- | --- |
| **实体完整性** | 行（元组） | 主属性（主码）不能为 NULL 且不能重复，能唯一标识每行 | `PRIMARY KEY` |
| **域完整性** | 列（属性） | 字段的值域、数据类型及有效规则等约束 | 数据类型、`NOT NULL`、`CHECK`、`DEFAULT` |
| **参照完整性** | 表与表之间 | 外码取值必须是所参照表中已存在的主码值（或为 NULL） | `FOREIGN KEY` |
| **用户定义完整性** | 业务语义 | 针对具体应用的补充规则，如课程分数既要为整数又要在 $[0,100]$ 内 | `CHECK`、断言、触发器 |

**Q [⭐⭐⭐]【1.3.Q2】：实体完整性和参照完整性有什么细节？外码可以为 NULL 吗？**

A：

- **实体完整性只约束主属性**：主码不能为 NULL、不能重复——它保证每行"可被唯一指认"；
- **参照完整性约束的是外码**：外码的值要么在**被参照表中真实存在**（对应某个主码值），要么为 **NULL**（表示"暂未确定"）；
- **外键是手段，参照完整性是目的**——它防止出现"指向不存在记录的悬空引用"；
- 前三类约束由 DBMS **自动检查**，用户定义完整性则由应用语义决定，DBMS 只提供表达机制。

### 1.4 E-R 模型与 E-R 图合并 ⭐⭐

**Q [⭐⭐]【1.4.Q1】：E-R 图的三要素是什么？联系有哪几种类型？**

A：**实体**（矩形）、**属性**（椭圆）、**联系**（菱形）。联系按参与数量分为三种：

- **一对一 $1:1$**：如"班级—班长"；
- **一对多 $1:n$**：如"班级—学生"；
- **多对多 $m:n$**：如"学生—课程"（需要单独的关系表来存）。

**Q [⭐⭐]【1.4.Q2】：数据库设计的流程是怎样的？**

A：**需求分析** → **概念结构设计**（局部 E-R 图 → 合并 → 全局 E-R 图）→ **逻辑结构设计**（E-R 图转关系模式）→ **物理设计**（选存储结构与索引）。

**Q [⭐⭐]【1.4.Q3】：E-R 图合并时需要注意哪些冲突？**

A：多个局部 E-R 图合成全局 E-R 图时，必须消除**三类冲突**：

| 冲突类型 | 表现 | 解决 |
| --- | --- | --- |
| **属性冲突** | 同一属性的类型、取值范围、单位或精度不一致（如"年龄" vs "出生日期"） | 统一约定后改写 |
| **命名冲突** | 同名异义（不同实体中同名属性含义不同）或异名同义（不同名字指同一属性） | 改名或统一命名 |
| **结构冲突** | 同一对象在不同局部图中抽象层次不同（一处是实体、另一处是属性），或联系类型不同 | 统一抽象层次与联系类型 |

**Q [⭐⭐]【1.4.Q4】：E-R 图合并之后如何优化？**

A：合并完成后做两类化简：

- **实体合并**：能合并的实体尽量合并，减少实体个数；
- **联系简化**：消除**冗余联系**（能由其他联系推出的联系）；
- 原则：**实体个数尽量少、联系尽量少、属性分配合理**。

## 2. SQL 与查询优化

### 2.1 SQL 执行顺序 ⭐⭐⭐

**Q [⭐⭐⭐]【2.1.Q1】：SQL 的逻辑执行顺序是什么？**

A：

```text
FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY
```

注意这是**逻辑执行顺序**，不是书写顺序——所以 `SELECT` 里定义的别名不能在 `WHERE` 中用，但可以在 `ORDER BY` 中用。

**Q [⭐⭐⭐]【2.1.Q2】：WHERE 和 HAVING 有什么区别？**

A：

- **WHERE 在分组前过滤行**，作用对象是单行，**不能用聚合函数**；
- **HAVING 在分组后过滤组**，作用对象是分组结果，**可以用聚合函数**（如 `HAVING COUNT(*) > 3`）；
- 一句话：**WHERE 筛行、HAVING 筛组**，需要按聚合结果筛选时必须用 HAVING。

### 2.2 查询优化 ⭐⭐

**Q [⭐⭐]【2.2.Q1】：什么是代数优化？常用手段有哪些？**

A：代数优化是**逻辑层**的优化，依据**关系代数的等价变换规则**改写查询，与物理存取方式无关。常用手段：

- **选择下推**：把选择尽早做（尽量靠近叶节点），先过滤掉大量数据；
- **投影下推**：只保留后面用得到的列，减少中间结果宽度；
- **连接重排序**：调整连接次序，先做结果小的连接。

**Q [⭐⭐]【2.2.Q2】：什么是物理优化？主要做哪些选择？**

A：物理优化在代数优化之后进行，为逻辑执行计划**选择具体的执行算法**：

- **单表扫描方式**：索引扫描 vs 全表扫描；
- **连接算法**：嵌套循环连接 / 排序归并连接 / 哈希连接；
- 依据是数据量、索引情况与选择率，目标是 I/O 与 CPU 代价最小。

### 2.3 SQL 的四种语言 ⭐⭐

**Q [⭐⭐]【2.3.Q1】：SQL 分为哪几类语言？各自的代表语句是什么？**

A：

| 分类 | 全称 | 作用 | 典型语句 |
| --- | --- | --- | --- |
| **DDL** | Data Definition Language（数据定义语言） | 定义、修改、删除数据库对象 | `CREATE`、`ALTER`、`DROP`、`TRUNCATE` |
| **DML** | Data Manipulation Language（数据操作语言） | 对表中**数据**的增删改查 | `SELECT`、`INSERT`、`UPDATE`、`DELETE` |
| **DCL** | Data Control Language（数据控制语言） | 权限控制与用户管理 | `GRANT`、`REVOKE` |
| **TCL** | Transaction Control Language（事务控制语言） | 事务的提交与回滚 | `COMMIT`、`ROLLBACK`、`SAVEPOINT` |

> 有的教材把 `SELECT` 单列为 **DQL（查询语言）**，面试时提一句即可。

**Q [⭐⭐]【2.3.Q2】：TRUNCATE 和 DELETE 有什么区别？**

A：

- **`TRUNCATE` 属于 DDL**：隐式提交、**不能回滚**，一次性清空整表数据但保留表结构，速度快；
- **`DELETE` 属于 DML**：**可以回滚**，可带 `WHERE` 条件删部分行，逐行删除并写日志，速度慢；
- 记忆点：**DDL 是隐式提交的**——这是二者最常被考的差别。

## 3. 关系数据理论与范式

### 3.1 三大范式 ⭐⭐⭐

**Q [⭐⭐⭐]【3.1.Q1】：第一、二、三范式的定义分别是什么？（北航真题）**

A：设关系模式 $R$，逐级递进：

- **1NF（第一范式）**：$R$ 的**每个属性都是不可再分的原子值**——不能是集合、记录或重复组。这是关系模式的最基本要求；
- **2NF（第二范式）**：满足 1NF，且**每个非主属性都完全函数依赖于候选码**（不存在对码的部分函数依赖）。即码为组合码时，非主属性不能只依赖其中一部分；
- **3NF（第三范式）**：满足 2NF，且**每个非主属性都不传递依赖于候选码**（不存在 $X \to Y$、$Y \to Z$、$Y \not\to X$ 的链）。

> 一句话：**1NF 保证"值原子"，2NF 保证"非主属性依赖整个码"，3NF 保证"非主属性不绕道依赖码"。**

**Q [⭐⭐⭐]【3.1.Q2】：什么是部分函数依赖？**

A：$X \to Y$，但 $X$ 的**某个真子集也能决定** $Y$。典型场景：码是**组合码**，而非主属性只依赖其中一部分——例如"（学号，课程号）→ 姓名"，姓名其实只依赖学号，这就是部分依赖。

**Q [⭐⭐⭐]【3.1.Q3】：什么是传递函数依赖？**

A：$X \to Y$、$Y \to Z$，且 $Y \not\to X$——非主属性通过**中间属性间接依赖**候选码。例如"学号 → 系名，系名 → 系主任"，系主任传递依赖于学号。

**Q [⭐⭐]【3.1.Q4】：不符合范式会带来哪些异常？**

A：数据冗余引发的三类异常：

- **插入异常**：想插入部分信息却缺少主键或对应记录，插不进去；
- **删除异常**：删除一行时把不该删的信息一起删掉（如删掉最后一个学生就丢了系主任信息）；
- **修改异常**：同一非主属性存了多次，改一处漏一处 → 数据不一致。

**Q [⭐⭐]【3.1.Q5】：BCNF 和 3NF 有什么区别？**

A：**BCNF 要求每个决定因素都是候选码**。差别在于：

- **3NF 只约束非主属性**，允许**主属性**对候选码的部分/传递依赖；
- **BCNF 不区分主属性与非主属性**，任何属性都不能部分/传递依赖候选码；
- 所以 **BCNF 比 3NF 更严格**（满足 BCNF 一定满足 3NF，反之不成立）。

**Q [⭐⭐⭐]【3.1.Q6】：三个范式的递进关系怎么一句话概括？**

A：**1NF = 属性原子性，2NF = 消除部分依赖，3NF = 消除传递依赖；每升一级就去掉一种冗余。**每个范式解决前一个范式遗留的问题：1NF 有重复组 → 2NF 消部分依赖 → 3NF 消传递依赖 → BCNF 消主属性对码的部分/传递依赖。

## 4. 存储与索引

### 4.1 索引结构：B+ 树 / 哈希 / 位图 ⭐⭐⭐

**Q [⭐⭐⭐]【4.1.Q1】：B+ 树索引的原理和优势是什么？**

A：

- **原理**：多路平衡树——**非叶节点只存键**用于导航，**叶子节点存数据（或主键）+ 指针**，且叶子用**链表串联**；
- **优势**：等值、**范围**、排序、最左前缀查询全都支持；树矮（3-4 层即可存百万行），减少磁盘 I/O；叶子链表让范围查询只需顺序扫描；
- **代价**：插入/删除要分裂合并，维护成本比哈希高。

**Q [⭐⭐⭐]【4.1.Q2】：哈希索引的原理、优势和局限是什么？**

A：

- **原理**：用哈希函数把键映射到桶，桶内挂链解决冲突；
- **优势**：**等值查询 $O(1)$**，最快；
- **局限**：**不支持范围查询、排序、最左前缀**；必须全列匹配（不能用部分索引列）；冲突多时退化成链表扫描；
- **适用**：只做等值查询的内存表（Memory 引擎默认）。

**Q [⭐⭐⭐]【4.1.Q3】：位图索引的原理、优势和局限是什么？**

A：

- **原理**：为每个不同取值建一个位向量，第 $i$ 位表示第 $i$ 行是否取该值；
- **优势**：低基数列（性别、状态）占用空间极小；位运算快，**多条件 AND/OR 高效**；
- **局限**：**锁粒度大**——改一行要锁一整个位图段，写并发差；高基数列的位图会膨胀；
- **适用**：数据仓库/OLAP 的低基数维度列，**不适合 OLTP**。

**Q [⭐⭐⭐]【4.1.Q4】：聚簇索引和非聚簇索引有什么区别？什么是回表？**

A：

| | 聚簇索引 | 非聚簇索引 |
| --- | --- | --- |
| 存储 | 数据按索引键**物理排序存储**，叶子节点存**完整一行数据** | 索引与数据分离，叶子节点存**索引键 + 主键** |
| 数量 | **一个表只能有一个** | **可有多个** |
| 查数 | 直接拿到数据 | 先拿主键，**再回聚簇索引找数据（回表）** |

**回表**：走二级索引查到主键后，还要**再查一次聚簇索引**才能拿到整行数据，因此多一次查找、更慢；若查询的列都在索引里（覆盖索引）就不用回表。

**Q [⭐⭐]【4.1.Q5】：为什么数据库用 B+ 树而不用红黑树？**

A：**B+ 树节点大（一页），树矮**——3-4 层就能存百万行，一次 I/O 能读到一整个节点的键，大幅减少磁盘 I/O；**红黑树是二叉树，太深**，每次比较都可能触发一次 I/O，磁盘访问次数远超 B+ 树。此外 B+ 树叶子链表天然支持范围查询。

**Q [⭐⭐]【4.1.Q6】：什么是自适应哈希索引（AHI）？**

A：InnoDB 在**内存中**为**热点等值查询**自动建立的哈希索引——它不改变 B+ 树索引本身，只是给频繁等值访问的键再挂一层哈希加速，把等值查询做到近似 $O(1)$。

## 5. 事务与并发控制

### 5.1 ACID ⭐⭐⭐

**Q [⭐⭐⭐]【5.1.Q1】：事务的 ACID 四大特性分别是什么？**

A：

- **原子性（Atomicity）**：事务要么全做、要么全不做；
- **一致性（Consistency）**：事务执行前后数据库都处于合法一致的状态；
- **隔离性（Isolation）**：并发执行的事务互不干扰；
- **持久性（Durability）**：事务提交后的修改永久保存，故障也不丢。

**Q [⭐⭐⭐]【5.1.Q2】：ACID 各自靠什么实现？**

A：

| 特性 | 实现依赖 |
| --- | --- |
| 原子性 | 日志（**Undo Log**，回滚用） |
| 一致性 | 约束 + 触发器 |
| 隔离性 | 锁 + **MVCC** |
| 持久性 | 日志（**Redo Log**，重做用） |

> 记忆：**原子靠 Undo，持久靠 Redo，隔离靠锁与 MVCC，一致靠约束**。

### 5.2 隔离级别 ⭐⭐⭐

**Q [⭐⭐⭐]【5.2.Q1】：脏读、不可重复读、幻读分别是什么？**

A：三类并发异常：

- **脏读**：读到了别的事务**还没提交**的数据（对方一回滚，你读到的就是脏数据）；
- **不可重复读**：同一事务内两次读**同一行**，结果不一样（别的事务 UPDATE 并提交了）；
- **幻读**：同一条件的查询两次执行，**行数不同**（别的事务 INSERT / DELETE 了）。

**Q [⭐⭐⭐]【5.2.Q2】：SQL 标准定义了哪四个隔离级别？各自允许哪些异常、如何加锁？**

A：

| 隔离级别 | 脏读 | 不可重复读 | 幻读 | 加锁 |
| --- | --- | --- | --- | --- |
| 读未提交 | ✅ 允许 | ✅ 允许 | ✅ 允许 | 无 |
| 读已提交 | ❌ 禁止 | ✅ 允许 | ✅ 允许 | 写锁（读完即放读锁） |
| 可重复读 | ❌ 禁止 | ❌ 禁止 | ✅ 允许 | 长写锁 + 短读锁 |
| 串行化 | ❌ 禁止 | ❌ 禁止 | ❌ 禁止 | 全部加锁 |

**逐级解释**：

- **读未提交**：能读未提交数据，三类异常全有；几乎不加锁，并发最高但最不安全，实际基本不用；
- **读已提交（RC）**：只能读已提交数据，**杜绝脏读**；别人改旧行 → 不可重复读，别人插新行 → 幻读；
- **可重复读（RR）**：同一事务内多次读同一行结果不变，解决不可重复读；**理论上仍存在幻读**；
- **串行化**：事务强制串行执行、读写全加锁，三类异常全部消除，并发性能最差。

> 规律：**级别越高，能消除的异常越多，并发性能越差**。

**Q [⭐⭐⭐]【5.2.Q3】：不可重复读和幻读有什么区别？**

A：区别在"**别人做了什么**"：

| 异常 | 触发动作 | 表现 |
| --- | --- | --- |
| **不可重复读** | 别的事务 **UPDATE 旧行** | 同一行数据前后两次读到的值不同 |
| **幻读** | 别的事务 **INSERT / DELETE 行** | 同一条件的查询前后两次"行数"不同 |

一句话：**不可重复读是"行内数据被改"，幻读是"集合里多/少了行"**。

**Q [⭐⭐⭐]【5.2.Q4】：MySQL InnoDB 默认的隔离级别是什么？靠什么实现？**

A：

- 默认级别是**可重复读（Repeatable Read，RR）**（单选高频）；
- 通过 **MVCC** 实现：读不加锁、写加锁，用版本号实现**快照读**，同一事务读到同一个快照；
- 注意口径：MySQL 用 MVCC **很大程度缓解**了幻读，但按教材答题——**RR 不能消除幻读，只有串行化才消除**。

## 6. 数据库恢复

### 6.1 恢复策略（WAL）与三类故障 ⭐⭐

**Q [⭐⭐]【6.1.Q1】：数据库恢复的基本策略是什么？**

A：**WAL（Write-Ahead Logging，日志优先写）——先写日志，再写数据**。这样即使写数据时崩溃，也能靠日志把事务**重做（Redo）**或**回滚（Undo）**，保证原子性与持久性。

**Q [⭐⭐]【6.1.Q2】：三类故障分别怎么恢复？**

A：

| 故障类型 | 影响范围 | 恢复方式 |
| --- | --- | --- |
| **事务故障** | 单个事务出错 | **Undo（回滚）**该事务 |
| **系统故障** | 断电/崩溃，内存丢失、磁盘完好 | 重启后 **Redo + Undo**：已提交的重做、未提交的回滚 |
| **介质故障** | 磁盘损坏，数据丢失 | 用**备份 + 日志**重做 |

## 7. 关系型 vs 非关系型数据库

### 7.1 除了关系型数据库还有什么数据库？⭐⭐

**Q [⭐⭐]【7.1.Q1】：除了关系型数据库，还有哪些类型的数据库？（北航真题）**

A：按**数据模型**的演进顺序：

| 类型 | 数据结构 | 特点 | 代表 |
| --- | --- | --- | --- |
| **层次模型** | 树（一对多） | 结构简单、查询快，但只能沿父子链访问，多对多需冗余 | IBM IMS |
| **网状模型** | 图（多对多） | 用指针表达任意联系，结构复杂、用户需了解存取路径 | DBTG |
| **关系模型** | 二维表 | 非过程化，理论基础是关系代数/关系演算 | MySQL、Oracle |
| **面向对象模型** | 对象 + 类 + 继承 | 支持复杂数据类型与继承，适合 CAD/GIS/多媒体 | ObjectStore |
| **NoSQL** | 键值/文档/列族/图 | 弱 Schema、易横向扩展、BASE 一致性 | 见下一问 |
| **NewSQL** | 关系表（分布式） | 同时要关系型的 ACID 与 NoSQL 的横向扩展 | TiDB、OceanBase、Spanner |
| **时序数据库 TSDB** | 时间戳序列 | 专为高写入的监控/物联网数据设计 | InfluxDB、TDengine |
| **向量数据库** | 高维向量 | 近似最近邻检索，服务于 RAG/推荐 | Milvus、Pinecone |

> 演进主线：**从强结构化到弱 Schema、从单机纵向扩展到分布式横向扩展**。

**Q [⭐⭐]【7.1.Q2】：NoSQL 有哪四种典型形态？**

A：

- **键值型**：Redis、Memcached——结构最简单，查询只有 get/put；
- **文档型**：MongoDB、CouchDB——半结构化 JSON，字段可嵌套；
- **列族型**：HBase、Cassandra——按列族存储，适合海量稀疏数据；
- **图型**：Neo4j——天然表达关系，适合社交网络、知识图谱。

**Q [⭐⭐]【7.1.Q3】：NewSQL 是什么？**

A：NewSQL 是"**两头都要**"的一类分布式数据库：既保留关系型的**SQL 接口与 ACID 强一致**，又具备 NoSQL 的**横向扩展能力**。代表产品：**TiDB、OceanBase、Spanner**。

### 7.2 关系型 vs 非关系型对比 ⭐⭐

**Q [⭐⭐]【7.2.Q1】：关系型数据库和非关系型数据库有什么区别？**

A：

| | 关系型（RDBMS） | 非关系型（NoSQL） |
| --- | --- | --- |
| 数据模型 | **表 + 关系** | 键值/文档/列族/图 |
| Schema | **固定**（先定表结构） | 灵活/无 |
| ACID | **严格保证** | 最终一致性（BASE） |
| 扩展方式 | 纵向（加机器配置） | **横向（加机器数量）** |
| 代表 | MySQL、PostgreSQL | Redis、MongoDB、HBase |

**结论**：关系型**强一致但难扩展**，NoSQL **易扩展但弱一致**；实际系统常**混合使用**（如 MySQL 存交易、Redis 做缓存）。

**Q [⭐⭐]【7.2.Q2】：为什么说关系型难扩展、NoSQL 易扩展？**

A：因为扩展方向不同：

- **关系型靠纵向扩展（Scale Up）**：提升单机 CPU/内存/磁盘，受**单机硬件上限**与成本限制，且分库分表要应用层自己处理；
- **NoSQL 天生为分布式设计，靠横向扩展（Scale Out）**：加机器即扩容，用**分片**分散数据、**副本**保证可用，代价是放松强一致性，改为 **BASE（基本可用、软状态、最终一致）**。
