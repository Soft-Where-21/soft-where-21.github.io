# 数据库 - 保研面试知识点总结

> [!info]+ 复习策略  
> 数据库的核心逻辑是"如何高效、安全、一致地管理大量数据"。面试时从"问题→设计→优化"三步走：遇到什么数据管理问题？用什么模型/技术解决？如何进一步优化？
>
> 重点标注：⭐⭐⭐ 高频 | ⭐⭐ 中频 | ⭐ 低频但重要
>
> 北航软院面试高频考点：**三大范式、关系型 vs 非关系型数据库**

---

> [!abstract]+ 学科总览  
> 数据库按"从抽象到具体"的逻辑分成几块：
>
> - **基础模型**（第1-3章）：数据模型（层次/网状/关系）→ 关系模型（关系代数/SQL）→ 关系数据理论（范式/函数依赖）。这块回答"数据怎么组织和操作"。
> - **设计与实现**（第4-6章）：数据库设计（ER→关系模式）→ 存储与索引（B+树/哈希索引）→ 查询处理与优化。这块回答"数据怎么高效存取"。
> - **管理与应用**（第7-9章）：事务管理（ACID/并发控制/恢复）→ 安全性 → NoSQL。这块回答"数据怎么安全一致地运行"。
>
> 暗线：**组织数据 → 高效存取 → 安全运行**。范式保证"数据不冗余"，索引保证"查询快"，事务保证"不出错"。

## 1. 数据库基础与关系模型

> [!note]+ 章节导引  
> **本章知识点之间的关系**：数据库的"世界观"——数据怎么组织、怎么抽象。逻辑链：**三级模式结构**（外模式/模式/内模式 + 二级映像）→ **数据模型**（概念/逻辑/物理三层）→ **关系模型**（表=关系、行=元组、列=属性）→ **关系代数**（选择/投影/连接/除，是 SQL 的数学基础）→ **完整性约束**（实体/域/参照/用户定义）→ **E-R 模型与合并**（概念设计）。
>
> **与上一章的关系**：无（起点）。
>
> **与学科的关系**：三级模式是数据库架构的根基，关系代数是 SQL 的理论基础。

### 1.1 三级模式 + 二级映像 ⭐⭐⭐

| 层次            | 对应     | 数量     |
| ------------- | ------ | ------ |
| **外模式**       | 用户视图   | 多个     |
| **模式**（概念模式）  | 全体逻辑结构 | **1个** |
| **内模式**（存储模式） | 物理存储方式 | **1个** |

**二级映像**：

- 外模式/模式映像 → 保证**逻辑独立性**（改逻辑结构不影响用户视图）
- 模式/内模式映像 → 保证**物理独立性**（改存储方式不影响逻辑结构）

### 1.2 关系代数 ⭐⭐⭐

| 运算   | 符号        | SQL对应        | 说明                   |
| ---- | --------- | ------------ | -------------------- |
| 选择   | $\sigma$  | WHERE        | 行过滤                  |
| 投影   | $\pi$     | SELECT       | 列过滤                  |
| 连接   | $\bowtie$ | JOIN         | 按条件合并两表              |
| 自然连接 | $\bowtie$ | NATURAL JOIN | 同名列等值连接+去重复列         |
| 除    | $\div$    | /            | "包含"关系查询。查找匹配右侧全部的元组 |

### 1.3 数据库的完整性约束 ⭐⭐⭐

**完整性约束** = 保证数据库中数据"正确、相容"的规则，共四类（前三类是关系模型固有的，第四类是应用语义附加的）：

| 类型          | 约束对象  | 含义                                      | SQL 实现                            |
| ----------- | ----- | --------------------------------------- | --------------------------------- |
| **实体完整性**   | 行（元组） | 主属性（主码）不能为 NULL，且不能有相同值，能唯一标识每行         | `PRIMARY KEY`                     |
| **域完整性**    | 列（属性） | 字段的值域、数据类型及有效规则等约束                      | 数据类型、`NOT NULL`、`CHECK`、`DEFAULT` |
| **参照完整性**   | 表与表之间 | 外码的取值必须是所参照表中已存在的主码值（或为 NULL）           | `FOREIGN KEY`                     |
| **用户定义完整性** | 业务语义  | 针对具体应用语义的补充规则，如课程分数既要为整数又要在 $[0,100]$ 内 | `CHECK`、断言、触发器                    |

> [!tip]+ 易错点
>
> - 实体完整性只约束**主属性**；外码若不属于主属性的一部分，则允许取 NULL（表示"暂未确定"）。
> - 前三类约束由 DBMS 自动检查；用户定义完整性由应用语义决定，DBMS 只是提供表达机制。
> - **参照完整性 vs 外键**：外键是手段，参照完整性是目的——它保证表间引用不出现"悬空指针"。

### 1.4 E-R 模型与 E-R 图合并 ⭐⭐

**E-R 图三要素**：实体（矩形）、属性（椭圆）、联系（菱形），联系有 $1:1$、$1:n$、$m:n$ 三种类型。

**数据库设计流程**：需求分析 → 概念结构设计（局部 E-R 图 → **合并** → 全局 E-R 图）→ 逻辑结构设计（E-R 图转关系模式）→ 物理设计。

**E-R 图合并时的注意事项（消除三类冲突）**：

| 冲突类型     | 表现                                      | 解决          |
| -------- | --------------------------------------- | ----------- |
| **属性冲突** | 同一属性的类型、取值范围、单位或精度不一致（如"年龄" vs "出生日期"）  | 统一约定后改写     |
| **命名冲突** | 同名异义（不同实体中同名属性含义不同）或异名同义（不同名字指同一属性）     | 改名 or 统一命名  |
| **结构冲突** | 同一对象在不同局部图中抽象层次不同（一处是实体、另一处是属性），或联系类型不同 | 统一抽象层次与联系类型 |

**合并后的优化**：

- **实体合并**：能合并的实体尽量合并，减少实体个数；
- **联系简化**：消除冗余联系（可由其他联系推出的联系）；
- 原则：实体个数尽量少、联系尽量少、属性分配合理。

> [!tip]+ 面试一句话  
> E-R 图合并要消除**属性冲突、命名冲突、结构冲突**三类冲突，合并后再做实体合并与冗余联系消除。

## 2. SQL 与查询优化

> [!note]+ 章节导引  
> **本章知识点之间的关系**：SQL 是关系代数的"工程化版本"。逻辑链：**DDL**（建表/改表/删表）→ **DML**（增删改查）→ **查询**（SELECT-FROM-WHERE-GROUP BY-HAVING-ORDER BY）→ **嵌套查询**（子查询）→ **视图**（虚表，外模式对应）→ **查询优化**（代数优化→物理优化）。
>
> **与上一章的关系**：SQL 实现了关系代数的所有运算。
>
> **与学科的关系**：SQL 是数据库面试的"实践层"，查询优化是面试的"理论层"。

### 2.1 SQL 执行顺序 ⭐⭐⭐

```
FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY
```

> [!tip]+ 面试一句话  
> SQL 逻辑执行顺序：FROM→WHERE→GROUP BY→HAVING→SELECT→ORDER BY。WHERE 在分组前过滤，HAVING 在分组后过滤。

### 2.2 查询优化 ⭐⭐

**代数优化**（逻辑层）：选择下推（尽早过滤减少数据量）、投影下推（尽早投影提前去掉不需要的列）、连接重排序（小表先链接，控制中间结果的规模）

**物理优化**：

- 选择索引扫描（利用索引快速定位满足条件记录） vs 全表扫描（顺序读取整张表所有块）：如果查询要取出表中大部分行，索引反而更慢（回表 IO 开销大），优化器会选全表扫描。
- 嵌套循环连接 vs 排序归并连接 vs 哈希连接
  1. **嵌套循环连接**：遍历外表 R 每一行，去内表 S 查找匹配行。  
     ✅适合：外表很小；内表连接字段有索引。  
     ❌缺点：内表无索引时，代价很高。
  2. **排序归并连接**：先把 R、S 按连接属性分别排序；然后两个有序序列像归并一样顺序匹配。  
     ✅适合：连接字段有序；大表连接；多次重复查询。  
     ❌缺点：排序本身有开销。
  3. **哈希连接**：对较小表建立哈希表，遍历大表，用哈希匹配。  
     ✅适合：大表连接、无索引、连接字段无序。大数据场景最常用。  
     ❌缺点：消耗内存，内存不足会溢写到磁盘，性能下降。

### 2.3 SQL 的四种语言 ⭐⭐

| 分类      | 全称                                   | 作用                     | 典型语句                                |
| ------- | ------------------------------------ | ---------------------- | ----------------------------------- |
| **DDL** | Data Definition Language（数据定义语言）     | 定义、修改、删除数据库对象（表、视图、索引） | `CREATE`、`ALTER`、`DROP`、`TRUNCATE`  |
| **DML** | Data Manipulation Language（数据操作语言）   | 对表中**数据**的增删改查         | `SELECT`、`INSERT`、`UPDATE`、`DELETE` |
| **DCL** | Data Control Language（数据控制语言）        | 权限控制与用户管理              | `GRANT`、`REVOKE`                    |
| **TCL** | Transaction Control Language（事务控制语言） | 事务的提交与回滚               | `COMMIT`、`ROLLBACK`、`SAVEPOINT`     |

> [!tip]+ 易错点
>
> - **DDL 是隐式提交的**：`TRUNCATE` 虽删数据但属于 DDL，**不能回滚**；`DELETE` 属于 DML，可回滚。这是二者最常被考的差别。
> - `SELECT` 单独归 DML（有的教材叫 DQL 查询语言，面试提一句即可）。
> - DCL 管"谁能做什么"，TCL 管"这件事算不算数"。

## 3. 关系数据理论与范式 ⭐⭐⭐（面试极高频）

> [!note]+ 章节导引  
> **本章知识点之间的关系**：范式是"消除数据冗余和更新异常"的分级方案。逻辑链：**函数依赖**（X→Y，决定关系）→ **候选码/主码**（能唯一确定元组的最小属性集）→ **三大范式**（1NF→2NF→3NF，逐步消除冗余）→ **BCNF**（3NF 的强化版）→ **多值依赖与4NF**（更高级的冗余）。每个范式解决前一个范式遗留的问题——1NF有重复组→2NF消除部分依赖→3NF消除传递依赖→BCNF消除主属性对码的部分/传递依赖。
>
> **与上一章的关系**：范式是对"关系模式设计质量"的评价标准——不好的设计会导致插入/删除/更新异常。
>
> **与学科的关系**：三大范式是面试必考，必须能说清每级消除什么依赖。

### 3.1 三大范式 ⭐⭐⭐⭐

| 范式      | 条件                 | 消除的问题 | 非范式的异常          |
| ------- | ------------------ | ----- | --------------- |
| **1NF** | 属性不可再分             | 重复组   | /               |
| **2NF** | 1NF + **消除部分函数依赖** | 部分依赖  | 修改异常（同一非主属性存多次） |
| **3NF** | 2NF + **消除传递函数依赖** | 传递依赖  | 插入/删除异常         |

> [!note]+ 三个范式的严格定义
>
> - **1NF（第一范式）**：关系模式的**每个属性都是不可再分的原子值**——不能是集合、记录或重复组。这是关系模式的最基本要求。
> - **2NF（第二范式）**：满足 1NF，且**每个非主属性都完全函数依赖于候选码**（不存在对码的部分函数依赖）。即码为组合码时，非主属性不能只依赖其中一部分。
> - **3NF（第三范式）**：满足 2NF，且**每个非主属性都不传递依赖于候选码**（不存在 $X \to Y$、$Y \to Z$、$Y \not\to X$ 的链）。
> - 递进关系：1NF 保证"值原子"，2NF 保证"非主属性依赖整个码"，3NF 保证"非主属性不绕道依赖码"。

> [!tip]+ 关键概念
>
> - **部分函数依赖**：$X \to Y$，但 $X$ 的某个真子集也能决定 $Y$（码是组合码但非主属性只依赖其中一部分）
> - **传递函数依赖**：$X \to Y$，$Y \to Z$，且 $Y \not\to X$（非主属性通过中间属性间接依赖码）
> - **BCNF**：每个决定因素都是候选码（比 3NF 更严格：3NF 允许主属性对候选码的部分/传递依赖，BCNF 不允许）

> [!tip]+ 面试一句话  
> 1NF=属性原子性，2NF=消除部分依赖（非主属性完全依赖码），3NF=消除传递依赖。BCNF=每个决定因素都是候选码。

## 4. 存储与索引

> [!note]+ 章节导引  
> **本章知识点之间的关系**：数据存磁盘→需要索引加速→需要选择索引结构。逻辑链：**磁盘基础**（块读写，随机访问慢）→ **索引结构**（B+树索引 vs 哈希索引 vs 位图索引）→ **聚簇 vs 非聚簇索引**。B+树是数据库索引的标配（也是 CO 中树结构的实际应用）。
>
> **与上一章的关系**：索引决定了查询优化器能选择哪些物理执行方案。
>
> **与学科的关系**：B+树索引是数据库和 CO 的交叉考点。

### 4.1 索引结构：B+ 树 / 哈希 / 位图 ⭐⭐⭐

**三种索引结构对比**

| 索引结构       | 原理                                          | 优势                                          | 局限                                    | 适用场景                       |
| ---------- | ------------------------------------------- | ------------------------------------------- | ------------------------------------- | -------------------------- |
| **B+ 树索引** | 多路平衡树：非叶节点只存键用于导航，叶子节点存数据（或主键）+ 指针，且叶子用链表串联 | 等值查询、**范围查询**、排序、最左前缀全支持；树矮（3-4 层），磁盘 I/O 少 | 插入/删除需分裂合并，维护成本高                      | 绝大多数场景（范围查询、ORDER BY）      |
| **哈希索引**   | 哈希函数把键映射到桶，桶内挂链解决冲突                         | **等值查询 O(1)**，最快                            | **不支持范围查询、排序、最左前缀**；冲突多时退化成链表；只支持全列匹配 | 只做等值查询的内存表（Memory 引擎默认）    |
| **位图索引**   | 为每个不同取值建一个位向量，第 $i$ 位表示第 $i$ 行是否等于该值        | 低基数列（性别、状态）空间极小；位运算快，多条件 AND/OR 高效          | **锁粒度大**（改一行锁一整个位图段，写并发差）             | 数据仓库/OLAP 的低基数维度列，不适合 OLTP |

> [!tip]+ 面试一句话  
> 等值查询用哈希、范围与排序用 B+ 树、低基数多条件筛选用位图。InnoDB 默认 B+ 树，另有内存中的**自适应哈希索引（AHI）**为热点的等值查询进一步加速。

- **聚簇索引**：数据按索引键物理排序存储，叶子节点存完整一行数据（**一个表只能一个**）
- **非聚簇索引**：叶子节点存索引键+主键，拿到主键，再去聚簇索引找数据（回表）（**可有多个**）

> [!tip]+ 为什么数据库用 B+ 树而非红黑树？  
> B+ 树节点大（一页），树矮（3-4层可存百万行），减少磁盘 I/O。红黑树太深，每次比较可能一次 I/O。

## 5. 事务与并发控制 ⭐⭐⭐

> [!note]+ 章节导引  
> **本章知识点之间的关系**：事务是数据库"正确运行"的保障。逻辑链：**ACID 四大特性**（原子性/一致性/隔离性/持久性）→ **并发问题**（脏读/不可重复读/幻读）→ **隔离级别**（读未提交→读已提交→可重复读→串行化）→ **封锁协议**（S锁/X锁/两阶段锁）→ **死锁处理**。
>
> **与上一章的关系**：事务管理建立在存储引擎之上。
>
> **与学科的关系**：ACID 和隔离级别是面试必考，和 OS 的同步/互斥紧密关联。

### 5.1 ACID（事务的四大特性）⭐⭐⭐⭐

| 特性                  | 含义          | 实现依赖         |
| ------------------- | ----------- | ------------ |
| **原子性 atomicity**   | 事务要么全做要么全不做 | 日志（Undo Log） |
| **一致性 consistency** | 事务前后数据库状态一致 | 约束+触发器       |
| **隔离性 isolation**   | 并发事务互不干扰    | 锁+MVCC       |
| **持久性 durability**  | 提交后修改永久保存   | 日志（Redo Log） |

### 5.2 隔离级别 ⭐⭐⭐⭐

| 隔离级别 | 脏读 | 不可重复读 | 幻读 | 加锁      |
| ---- | -- | ----- | -- | ------- |
| 读未提交 | ✅  | ✅     | ✅  | 无       |
| 读已提交 | ❌  | ✅     | ✅  | 写锁      |
| 可重复读 | ❌  | ❌     | ✅  | 长写锁+短读锁 |
| 串行化  | ❌  | ❌     | ❌  | 全部加锁    |

**四个隔离级别的通俗解释**

- **读未提交（Read Uncommitted）**：能读到别的事务**还没提交**的数据——脏读、不可重复读、幻读三类异常全都有。几乎不加锁，并发最高但数据最不安全，**实际基本不用**。
- **读已提交（Read Committed，RC）**：只能读到别人**已经提交**的数据，**杜绝脏读**；但别人可以修改你读过的行并提交 → **不可重复读**，也可以插入新行 → **幻读**。加锁：写数据时加写锁，读完就释放读锁。
- **可重复读（Repeatable Read，RR，MySQL 默认）**：同一事务内多次读同一行**结果保持不变**，解决不可重复读；但**理论上仍存在幻读**。加锁：写锁持续到事务结束（长写锁），读锁读完即释放（短读锁）。
- **串行化（Serializable，最高级别）**：所有事务**强制串行执行、不能并发**，读写全部加锁，脏读/不可重复读/幻读**全部消除**。代价是并发性能最差，一般很少用。

**易混点：不可重复读 vs 幻读**

| 异常        | 触发动作                       | 表现                        |
| --------- | -------------------------- | ------------------------- |
| **不可重复读** | 别的事务 **UPDATE 旧行**         | 同一行数据前后两次读到的值不同           |
| **幻读**    | 别的事务 **INSERT / DELETE 行** | 同一条件的查询，前后两次"行数"不同（多了/少了） |

> [!tip]+ 一句话背诵  
> 隔离级别由低到高：读未提交 → 读已提交 → 可重复读 → 串行化。**级别越高，能消除的并发异常越多，并发性能越差**。读未提交三类全有；读已提交消除脏读；可重复读消除脏读+不可重复读（**答题仍按"允许幻读"**）；串行化三类全消。

> [!tip]+ 考试坑点
>
> - MySQL InnoDB 默认隔离级别是**可重复读（RR）**（单选高频）。
> - 区分二者：**不可重复读是修改旧行，幻读是新增/删除行**。
> - RR 下 MySQL 用 MVCC 快照**很大程度缓解**了幻读，但按教材答题：**RR 不能消除幻读，只有串行化才消除**。

> [!tip]+ 面试一句话  
> MySQL InnoDB 默认"可重复读"，通过 MVCC 实现——读不加锁，写加锁，通过版本号实现快照读。

## 6. 数据库恢复 ⭐⭐

### 6.1 恢复策略（WAL）与三类故障 ⭐⭐

**恢复策略**：日志优先写（WAL）——先写日志再写数据

- Undo 日志：记录**修改前旧数据**，用来撤销操作（回滚）
- Redo 日志：记录**修改后新数据**，用来重做操作

**三种故障**：

1. 事务故障：**单个事务在执行中途失败**（比如代码报错、主动 rollback），事务没正常提交。  
   问题：事务已经修改了部分内存数据，要撤销已经做的改动。  
   ✅恢复方法：**Undo（回滚）**，利用 Undo 日志，把这个事务已经做的修改全部撤销。
2. 系统故障：数据库服务突然挂了，内存里的脏页（修改过但没刷盘的数据）丢失；**磁盘上的数据文件本身没有损坏**。  
   ✅恢复方法：重启数据库后**Redo + Undo**
   - 对**已经提交到Redo日志，但修改还没刷到磁盘**的事务：Redo 重做，把修改应用到数据文件
   - 对**未提交就中断**的事务：Undo 回滚，撤销修改
3. 介质故障：**磁盘损坏、硬盘坏块，磁盘上的数据文件本身被破坏丢失**。  
   内存 + 磁盘原始数据损坏，光靠日志不够。  
   ✅恢复方法：**先加载最近的数据库备份，再利用备份之后的 Redo 日志，重做所有已提交事务**。


## 7. 关系型 vs 非关系型数据库 ⭐⭐⭐

### 7.1 除了关系型数据库还有什么数据库？⭐⭐

按**数据模型**的演进顺序：

| 类型 | 数据结构 | 特点 | 代表 |
| --- | --- | --- | --- |
| **层次模型** | 树（一对多） | 结构简单、查询快，但只能沿父子链访问，多对多需冗余 | IBM IMS |
| **网状模型** | 图（多对多） | 用指针表达任意联系，结构复杂、用户需了解存取路径 | DBTG |
| **关系模型** | 二维表 | 非过程化（只需说"要什么"），理论基础是关系代数/关系演算 | MySQL、Oracle |
| **面向对象模型** | 对象+类+继承 | 支持复杂数据类型与继承，适合 CAD/GIS/多媒体 | ObjectStore |
| **NoSQL** | 键值/文档/列族/图 | 弱 Schema、易横向扩展、BASE 一致性 | 见下 |
| **NewSQL** | 关系表（分布式） | 同时要关系型的 ACID 与 NoSQL 的横向扩展 | TiDB、OceanBase、Spanner |
| **时序数据库 TSDB** | 时间戳序列 | 专为高写入的监控/物联网数据设计 | InfluxDB、TDengine |
| **向量数据库** | 高维向量 | 近似最近邻检索，服务于 RAG/推荐 | Milvus、Pinecone |

**NoSQL 的四种典型形态**（面试最常追问）：

- **键值型**：Redis、Memcached —— 结构最简单，查询只有 get/put
- **文档型**：MongoDB、CouchDB —— 半结构化 JSON，字段可嵌套
- **列族型**：HBase、Cassandra —— 按列族存储，适合海量稀疏数据
- **图型**：Neo4j —— 天然表达关系，适合社交网络、知识图谱

> [!tip]+ 面试一句话
> 除关系型外还有：层次/网状（早期模型）、面向对象、NoSQL（键值/文档/列族/图）、NewSQL、时序与向量数据库。演进主线是**从强结构化到弱 Schema、从单机纵向扩展到分布式横向扩展**。

### 7.2 关系型 vs 非关系型对比

| | 关系型（RDBMS） | 非关系型（NoSQL） |
| --- | --- | --- |
| 数据模型 | **表+关系** | 键值/文档/列族/图 |
| Schema | **固定** | 灵活/无 |
| ACID | **严格保证** | 最终一致性（BASE） |
| 扩展方式 | 纵向（加机器配置） | **横向（加机器数量）** |
| 代表 | MySQL、PostgreSQL | Redis、MongoDB、HBase |

> [!tip]+ 面试一句话
> 关系型保证强一致性但难扩展，NoSQL 易扩展但弱一致。实际系统常混合使用。

## 附：数据库面试速查表

| 问题           | 一句话回答                                      |
| ------------ | ------------------------------------------ |
| 三级模式         | 外模式/模式/内模式 + 二级映像保证逻辑/物理独立性                |
| 1NF/2NF/3NF  | 1NF=原子性 2NF=消部分依赖 3NF=消传递依赖                |
| 聚簇 vs 非聚簇    | 聚簇=数据按索引排序(1个) 非聚簇=索引指向数据(多个)              |
| ACID         | 原子/一致/隔离/持久 → Undo+约束+锁+Redo               |
| 隔离级别         | 读未提交→读已提交→可重复读→串行化（越来越安全但越来越慢）             |
| 不可重复读 vs 幻读  | 不可重复读=别人 UPDATE 旧行；幻读=别人 INSERT/DELETE 行   |
| 为什么用 B+ 树    | 树矮(减少磁盘I/O) 叶子链表(范围查询快)                    |
| 三种索引结构       | B+树=范围+排序 哈希=等值O(1)不支持范围 位图=低基数多条件筛选       |
| 完整性约束        | 实体=主码非空唯一(行) 域=列取值类型范围 参照=外码(表间) 用户定义=业务规则 |
| SQL 四种语言     | DDL 定义 / DML 增删改查 / DCL 授权 / TCL 事务控制      |
| E-R 图合并      | 先消属性冲突、命名冲突、结构冲突，再实体合并+消冗余联系               |
| 除关系型外的数据库    | 层次/网状/面向对象/NoSQL(键值·文档·列族·图)/NewSQL/时序/向量  |
| 关系型 vs NoSQL | 关系型=强一致难扩展 NoSQL=弱一致易扩展                    |
| WAL          | 先写日志再写数据，故障后可 Redo/Undo 恢复                 |
