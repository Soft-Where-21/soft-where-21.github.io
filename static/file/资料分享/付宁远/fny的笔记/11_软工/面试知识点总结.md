# 软件工程 - 保研面试知识点总结

> [!info]+ 复习策略  
> 软工的核心逻辑是"如何系统化地开发和维护软件"。面试不考画图细节，考**思想**——为什么需要需求工程？为什么要有设计模式？为什么测试要分白盒黑盒？记住每种方法的"解决什么问题"比记住"怎么做"更重要。
>
> 重点标注：⭐⭐⭐ 高频 | ⭐⭐ 中频 | ⭐ 低频但重要

---

> [!abstract]+ 学科总览  
> 软件工程按照"软件生命周期"组织——从需求到维护，每一步解决一个特定的开发问题：
>
> - **需求**：回答"做什么"——需求获取→分析→规格说明→验证
> - **设计**：回答"怎么做"——概要设计（架构）→详细设计（模块内部）
> - **实现**：把设计变成代码——编码规范、版本控制
> - **测试**：验证"做对了没有"——白盒/黑盒/单元/集成/系统
> - **维护**：交付后的持续改进
>
> 暗线：**需求→设计→实现→测试→维护**是一个从抽象到具体、从"做什么"到"怎么做"到"做对了没有"的递进过程。每个阶段的产品（需求文档→设计文档→代码→测试报告）是下一个阶段的输入。

---

## 1. 软件工程基础与过程模型

> [!note]+ 章节导引  
> **本章知识点之间的关系**：软工的"世界观"——软件是什么、为什么"工程化"、有哪些开发模式。逻辑链：**软件危机**（大型软件失败率高→催生软工）→ **软件生命周期**（五大基本流程）→ **过程模型**（瀑布→增量→螺旋→敏捷）→ **三要素**（方法/工具/过程）→ **规范**（怎么算"工程化"）→ **度量**（复杂度）→ **项目管理**（进度/成本/质量铁三角）。
>
> **与上一章的关系**：无（起点）。
>
> **与学科的关系**：本章是名词解释类的送分章——生命周期、瀑布阶段、软工三要素、开发模型、复杂度度量都是高频直接提问点，务必背到"能一句话给出"的程度。

### 1.1 软件生命周期与五大基本流程 ⭐⭐⭐

**软件生命周期**：软件从提出、开发、使用到最终废弃的全过程。

**软工的五大基本流程**（面试标准答法）：

| 阶段       | 回答什么问题           | 主要产品         |
| -------- | ---------------- | ------------ |
| **需求分析** | 做什么              | 需求规格说明书（SRS） |
| **设计**   | 怎么做（概要设计 + 详细设计） | 设计说明书、UML 模型 |
| **编码实现** | 把设计翻译成程序         | 源代码          |
| **测试**   | 做对了没有            | 测试用例、测试报告    |
| **运行维护** | 交付之后怎么改          | 变更记录、新版本     |

> [!tip]+ 面试一句话  
> 五大基本流程 = **需求分析 → 设计 → 编码实现 → 测试 → 运行维护**；前一阶段的输出是后一阶段的输入，其中**维护阶段耗时最长**（占整个生命周期 50% 以上）。完整过程还包含立项/可行性研究、计划、发布与退役。

### 1.2 过程模型对比 ⭐⭐⭐

| 模型       | 核心思想          | 优点          | 缺点          | 适用     |
| -------- | ------------- | ----------- | ----------- | ------ |
| **瀑布**   | 按阶段线性顺序推进     | 简单、文档齐全     | **需求变更代价大** | 需求明确   |
| **快速原型** | 先做可运行原型让用户提意见 | 需求容易澄清      | 原型容易被当成品    | 需求不明确  |
| **增量**   | 按功能分批交付       | 早期可用        | 架构需前瞻       | 大系统    |
| **螺旋**   | 风险驱动迭代        | **风险控制好**   | 复杂          | 高风险项目  |
| **敏捷**   | 小步快跑、拥抱变化     | **灵活、快速响应** | 文档少、大项目难管理  | 需求变化频繁 |

> [!tip]+ 面试一句话  
> 瀑布适合需求明确的项目，敏捷适合需求变化频繁的项目。**螺旋模型的特色是每轮迭代都做"风险分析"**。

### 1.3 瀑布模型的阶段 ⭐⭐

| 阶段             | 做什么                           | 产出           |
| -------------- | ----------------------------- | ------------ |
| **计划 / 可行性研究** | 值不值得做、能不能做                    | 可行性分析报告、项目计划 |
| **需求分析**       | 明确"做什么"                       | 需求规格说明书      |
| **设计**         | 概要设计（架构/模块/接口）+ 详细设计（算法/数据结构） | 设计说明书、UML 模型 |
| **编码**         | 按设计实现                         | 源代码、单元测试     |
| **测试**         | 验证是否正确                        | 测试用例、测试报告    |
| **运行维护**       | 交付后修改完善                       | 变更记录、新版本     |

**特点**：阶段之间严格**顺序推进、存在因果关系**；每个阶段结束要**评审**（里程碑）；**文档驱动**，上一阶段文档是下一阶段的输入；发现问题必须**回溯**到前面阶段，代价大。

> [!tip]+ 面试一句话  
> 瀑布六阶段：**计划 → 需求分析 → 设计 → 编码 → 测试 → 维护**；特点是线性推进、文档驱动、阶段末评审，最大缺陷是**测试滞后**——缺陷发现得越晚修复代价越大（这正是 V 模型要解决的）。

### 1.4 软件工程三要素 ⭐⭐

| 要素     | 含义                            | 举例                         |
| ------ | ----------------------------- | -------------------------- |
| **方法** | 完成软件开发的技术手段，回答"怎么做出软件"        | 结构化方法、面向对象方法、需求/设计/测试方法    |
| **工具** | 支撑方法的自动化软件                    | IDE、Git、建模工具、JUnit、Jenkins |
| **过程** | 把方法和工具组织起来的工作框架，回答"按什么步骤和顺序做" | 瀑布、增量、螺旋、敏捷                |

> [!tip]+ 面试一句话  
> 软工三要素 = **方法 + 工具 + 过程**：方法是"技术手段"，工具是"支撑环境"，过程是"管理与组织框架"，三者缺一不可。

### 1.5 软件工程需要遵守的规范 ⭐⭐

规范不是"某一条规则"，而是分层的约定体系：

| 层面         | 规范内容                                                          |
| ---------- | ------------------------------------------------------------- |
| **过程规范**   | 遵循选定的过程模型；阶段评审、里程碑、文档齐套（GB/T 8566《软件生存周期过程》）                  |
| **文档规范**   | 需求规格说明书、设计说明书、测试报告的模板与内容要求（GB/T 8567《计算机软件文档编制规范》）            |
| **编码规范**   | 命名、注释、格式、异常处理、日志的统一约定（Google Style、阿里 Java 开发手册）+ 代码评审 + 静态检查 |
| **配置管理规范** | 版本控制与分支策略（如 Git Flow）、变更控制流程（申请→评审→实施→回归）                     |
| **测试规范**   | 用例设计方法、覆盖率门限、缺陷分级与跟踪流程、出口准则                                   |
| **管理规范**   | 进度/成本/质量/风险管理；用 CMMI 成熟度等级衡量组织的规范化程度                          |

> [!tip]+ 面试一句话  
> 软工规范的本质是让开发**可重复、可追溯、可交接**——从过程、文档、编码、配置管理、测试到项目管理六个层面把"个人的手艺"变成"团队的流程"。

### 1.6 程序复杂度的度量 ⭐⭐⭐

| 方法               | 度量什么             | 关键指标                                                                       |
| ---------------- | ---------------- | -------------------------------------------------------------------------- |
| **代码行 LOC**      | 规模               | 有效代码行数，简单但与语言强相关                                                           |
| **功能点 FP**       | 从**用户视角**度量的功能规模 | 5 类要素（输入/输出/查询/内部逻辑文件/外部接口文件）加权，再用技术复杂度因子调整                                |
| **McCabe 环形复杂度** | 程序控制流的**逻辑复杂度**  | $V(G)=E-N+2$ = 判定节点数 + 1 = 独立路径数                                           |
| **Halstead 复杂度** | 从算子/操作数度量体积与难度   | 体积 $V=N\log_2 n$，难度 $D=\frac{n_1}{2}\cdot\frac{N_2}{n_2}$，工作量 $E=D\cdot V$ |
| **结构度量**         | 模块结构质量           | 扇入（被调用次数，越高复用越好）、扇出（调用次数，越高越复杂）、耦合与内聚                                      |
| **面向对象度量 CK**    | 类的设计质量           | WMC（方法数加权）、DIT（继承深度）、NOC（子类数）、CBO（耦合类数）、RFC（响应集）、LCOM（内聚缺乏度）               |

> [!tip]+ 面试一句话  
> 最常考的一条：**McCabe 环形复杂度 $V(G)=E-N+2$**，等价于"判定节点数 + 1"，也等价于**线性无关路径数**——所以它直接告诉你"基本路径覆盖需要设计几条用例"；工程上一般要求 $V(G)\le 10$。

### 1.7 项目管理铁三角 ⭐⭐

**进度、成本、质量**三者互相制约——要快就要加钱或降质量，要高质量就要加时间或加钱。

## 2. 需求工程

> [!note]+ 章节导引  
> **本章知识点之间的关系**：需求是"做什么"的答案。逻辑链：**需求获取**（访谈/问卷/观察）→ **需求分析**（建模：用例图/活动图）→ **需求规格说明**（SRS文档）→ **需求验证**（评审）→ **需求管理**（变更控制）。
>
> **与上一章的关系**：需求是软件生命周期的第一步，决定了后续所有工作的方向。
>
> **与学科的关系**：面试考"需求变更怎么办"——回答要体现"影响分析+变更控制流程"。

### 2.1 需求的类型 ⭐⭐

| 类型        | 含义        | 举例             |
| --------- | --------- | -------------- |
| **功能需求**  | 系统必须做什么   | "用户可以搜索商品"     |
| **非功能需求** | 系统必须怎么样   | "响应时间 < 200ms" |
| **领域需求**  | 来自应用领域的约束 | "金额保留2位小数"     |

### 2.2 需求工程的过程与需求变更管理 ⭐⭐

| 活动        | 做什么                                  | 产出        |
| --------- | ------------------------------------ | --------- |
| **需求获取**  | 访谈、问卷、观察、原型演示、文档分析                   | 原始需求素材    |
| **需求分析**  | 建模（用例图 / 活动图 / 领域类图 / DFD），发现冲突与不一致   | 分析模型      |
| **需求规格说明** | 写成 SRS，作为后续设计与验收的基准                  | 需求规格说明书   |
| **需求验证**  | 评审、原型演示、用例检查，确认需求正确、完整、一致、可验证        | 确认后的需求基线  |
| **需求管理**  | 需求基线控制、追踪矩阵、变更控制                     | 变更记录、追踪表  |

**需求变更控制流程**：提出变更申请 → **影响分析**（评估对进度、成本、设计、测试的影响）→ **变更控制委员会（CCB）审批** → 批准后修改需求文档与基线、同步更新设计与代码 → 实施并**回归测试**。

> [!tip]+ 面试一句话  
> 需求工程 = **获取 → 分析 → 规格说明 → 验证 → 管理**；需求变更不可怕，可怕的是"私下改"——必须走**影响分析 + CCB 审批 + 更新文档 + 回归测试**的变更控制流程，保证每次变更都留痕、可追溯。

## 3. 软件设计

> [!note]+ 章节导引  
> **本章知识点之间的关系**：设计回答"怎么做"——分两个层次。逻辑链：**概要设计**（架构设计：模块划分、接口定义、设计模式选择）→ **详细设计**（模块内部：算法选择、数据结构、接口细节）→ **设计范式的选择**（面向对象 vs 面向过程）→ **设计成果的表达**（UML 图）。概要设计确定"怎么切"，详细设计确定"每块怎么做"。
>
> **与上一章的关系**：设计把需求规格转化为可实现的方案。
>
> **与学科的关系**：设计模式、高内聚低耦合是面试重点；UML 图分类和面向对象 vs 面向过程的对比是纯背诵型送分题。

### 3.1 高内聚低耦合 ⭐⭐⭐

**内聚**（模块内部）：功能越集中越好

| 内聚类型 | 强度     | 说明            |
| ---- | ------ | ------------- |
| 功能内聚 | **最强** | 所有元素完成同一功能    |
| 顺序内聚 | 强      | 前一元素输出=后一元素输入 |
| 通信内聚 | 中      | 操作同一数据集       |
| 逻辑内聚 | 弱      | 逻辑相关但功能不同     |
| 偶然内聚 | **最弱** | 无关系硬凑         |

**耦合**（模块之间）：依赖越少越好

| 耦合类型  | 强度     | 说明         |
| ----- | ------ | ---------- |
| 非直接耦合 | **最弱** | 无直接联系      |
| 数据耦合  | 弱      | 只传数据       |
| 标记耦合  | 中      | 传数据结构      |
| 控制耦合  | 较强     | 传控制信息      |
| 内容耦合  | **最强** | 直接访问另一模块内部 |

> [!tip]+ 面试一句话  
> **高内聚低耦合**是模块设计的黄金法则——模块内部紧密相关，模块之间松散联系。追求功能内聚+数据耦合。

### 3.2 常见设计模式 ⭐⭐

| 类型      | 代表模式       | 核心思想      |
| ------- | ---------- | --------- |
| **创建型** | 单例、工厂、抽象工厂 | 控制对象创建方式  |
| **结构型** | 适配器、装饰器、代理 | 组合对象获得新结构 |
| **行为型** | 观察者、策略、状态  | 对象间通信模式   |

> [!tip]+ 面试常用  
> 单例模式：保证一个类只有一个实例（如数据库连接池）；工厂模式：创建对象不暴露创建逻辑；观察者模式：一对多依赖，状态变化自动通知。

### 3.3 面向对象 vs 面向过程 ⭐⭐⭐

| 维度      | 面向过程                         | 面向对象                                |
| ------- | ---------------------------- | ----------------------------------- |
| 关注点     | 实现的具体**过程与因果关系**（先做什么、再做什么）  | **对象（独立体）能完成哪些功能**                  |
| 最小单位    | 函数                           | 类 / 对象                              |
| 需求分析的思路 | 以**功能**为线索分解：数据流图（DFD）、功能分解图 | 以**现实世界实体**为线索建模：用例图、领域（概念）类图       |
| 设计的思路   | 自顶向下、逐步求精，产出模块结构图            | 识别类与对象、定义属性与操作，用**封装/继承/多态**组织，产出类图 |
| 耦合与扩展   | 耦合度高，**一环出问题整个系统受牵连**，扩展力差   | 耦合度低，扩展力强，更容易处理复杂的业务逻辑              |
| 复用性     | 没有"独立体"概念，**难以组件复用**         | 封装 + 继承 + 多态，**组件复用性强**             |
| 成本      | 前期投入低、开发快                    | 前期投入高，需要大量系统分析与设计                   |
| 适用场景    | 业务逻辑比较简单、流程固定的程序             | 业务复杂、需求易变、规模大的系统                    |

> [!tip]+ 面试一句话  
> 面向过程关注"**怎么做**"（过程与因果），面向对象关注"**谁来做**"（对象的职责）。从需求分析看：一个按功能分解业务，一个把现实世界的实体直接映射成对象，所以需求变更时 OO 的改动范围更小；从设计看：一个以**函数**为最小单位、一个以**类**为最小单位。代价是 OO 前期投入更高。

### 3.4 UML 图分类与泳道图 ⭐⭐⭐

UML 2.x 共 **13 种图** = 结构图（静态）**6 种** + 行为图（动态）**7 种**：

| 类别  | 图        | 说明                              |
| --- | -------- | ------------------------------- |
| 结构图 | **类图**   | 类、属性、操作及类间关系（关联/聚合/组合/泛化/实现/依赖） |
| 结构图 | 对象图      | 某一时刻的对象实例及它们之间的链接               |
| 结构图 | 包图       | 包以及包之间的依赖与组织关系                  |
| 结构图 | 组件图      | 构件及其对外接口（实现视角）                  |
| 结构图 | 部署图      | 节点与构件的物理部署（硬件拓扑）                |
| 结构图 | 组合结构图    | 类的内部结构（部件、端口、连接件）               |
| 行为图 | **用例图**  | 参与者与用例，描述系统对外的功能                |
| 行为图 | **顺序图**  | 按**时间顺序**描述对象间的消息交互             |
| 行为图 | 通信图      | 描述对象交互，强调对象之间的**链接结构**          |
| 行为图 | **活动图**  | 业务流程/控制流，支持判断、并发、泳道             |
| 行为图 | **状态机图** | 一个对象的状态及状态之间的转移                 |
| 行为图 | 定时图      | 交互过程中对**时间约束**的描述               |
| 行为图 | 交互概览图    | 活动图与顺序图的混合（交互的概览）               |

**泳道图（Swimlane Diagram）**：活动图的一种组织形式——**它不是第 14 种图，UML 官方叫"活动分区（activity partition）"，泳道只是俗称**（源自跨职能流程图 / BPMN 的 lane）。做法是用若干条平行"泳道"把活动按**执行者**（角色/部门/系统）分区，每条泳道只放它负责的活动。

- 泳道里有什么：**泳道名（负责的参与者）**、活动节点、控制流（判断、分叉、汇合、合并）、开始与结束节点、对象流（传递的数据）。
- 作用：一眼看出"**谁负责哪一步**"，适合跨部门/跨角色的业务流程与责任划分。

**类图的六种关系怎么认**：关联=实线；聚合=**空心菱形**+实线（部分可独立存在，如课程—教师）；组合=**实心菱形**+实线（部分随整体消亡，如订单—订单项）；泛化=**空心三角**+实线（指向父类）；实现=**空心三角**+虚线（指向接口）；依赖=**虚线箭头**（临时使用，如作参数或局部变量）。菱形与三角都指向**整体/父类/接口**一侧。

**用例图的两种关系**：`«include»`（包含）= 必然发生的公共行为被抽出去复用，箭头**基用例 → 被包含用例**（如"下单"总要"校验库存"）；`«extend»`（扩展）= 可选/条件性的增量行为，箭头**扩展用例 → 基用例**（如"下单"在满足条件时可"使用优惠券"）。

> [!tip]+ 面试一句话  
> UML 图 13 种 = **结构图 6 种**（类图/对象图/包图/组件图/部署图/组合结构图）+ **行为图 7 种**（用例图/活动图/状态机图/顺序图/通信图/定时图/交互概览图）；泳道图就是活动图按**执行者**分区，泳道里装"该执行者负责的活动"，用来表达**职责归属与跨角色协作**。

## 4. 软件实现与编码

> [!note]+ 章节导引  
> **本章知识点之间的关系**：实现是"把设计变成代码"。逻辑链：**结对编程**（用什么协作方式写）→ **面向对象实现细节**（重载/重写、可变/不可变对象）。写代码本身要遵守的规范见 §1.5。
>
> **与上一章的关系**：设计给出类与接口，实现把它们落地成可运行的代码。
>
> **与学科的关系**：重载/重写、可变/不可变对象几乎是必问的 Java 基础题；结对编程属于 XP 实践，常与"敏捷"一起被追问。

### 4.1 结对编程 ⭐⭐

**结对编程（Pair Programming）**：极限编程（XP）的核心实践之一——两名开发者共用一台机器、一个键盘，共同完成同一段代码。

| 术语                          | 含义                                  |
| --------------------------- | ----------------------------------- |
| **Driver（驾驶员 / 操作者）**       | 手放在键盘上的人，专注把当前这行代码写出来               |
| **Navigator（领航员 / 观察者）**    | 不碰键盘的人，负责审查代码、思考下一步策略、发现遗漏与隐患       |
| **角色互换（Switch / Rotation）** | 每隔一段时间（如 15–30 分钟或一个测试周期）交换角色       |
| **Ping-Pong 结对**            | 一人先写一个失败的测试，另一人写实现让它通过，交替推进（TDD 风格） |
| **重新配对（Re-pairing）**        | 每个任务完成后重组搭档，避免固定配对形成的认知盲区           |

- 价值：**实时的代码评审**、知识共享（避免"只有一个人懂这块代码"）、显著降低缺陷率；
- 代价：短期人力投入近似翻倍，适合复杂或高风险模块，不适合需要长时间静默思考的探索性任务。

> [!tip]+ 面试一句话  
> 结对编程的术语核心是 **Driver（驾驶员，负责写）与 Navigator（领航员，负责想和查）**，两人**定期互换角色**；它是 XP 的实践，本质是"不间断的实时代码评审"。

### 4.2 重载 vs 重写 ⭐⭐⭐

| 对比项  | 重载 Overload            | 重写 Override             |
| ---- | ---------------------- | ----------------------- |
| 发生位置 | **同一个类**中（同一作用域内）      | **子类与父类**之间（必须有继承关系）    |
| 方法名  | 相同                     | 相同                      |
| 参数列表 | **必须不同**（类型 / 个数 / 顺序） | 必须相同                    |
| 返回值  | 无限制（但不能只靠返回值区分重载）      | 相同或**协变**（子类类型）         |
| 绑定时机 | **编译期**（静态绑定 → 静态多态）   | **运行期**（动态绑定 → 动态多态）    |
| 访问权限 | 无限制                    | **不能缩小**（可以放大）          |
| 抛出异常 | 无限制                    | 不能抛出更宽的**受检异常**         |
| 注解   | 无                      | `@Override`（Java，编译期校验） |

> [!tip]+ 面试一句话  
> **重载看参数**——同一个类里参数列表不同，编译期就决定调哪个；**重写看继承**——子类覆盖父类同名同参方法，运行期按实际对象类型决定调哪个。重写遵守"两同两小一大"：方法名与参数列表**相同**，返回值和异常**不放大**，访问权限**不缩小**。

### 4.3 可变对象 vs 不可变对象 ⭐⭐

| 对比项   | 可变对象                                                               | 不可变对象                                                                 |
| ----- | ------------------------------------------------------------------ | --------------------------------------------------------------------- |
| 定义    | 创建后**内部状态可以被修改**                                                   | 创建后**状态不可改变**，任何"修改"都返回一个新对象                                          |
| 例子    | Java：`StringBuilder`、数组、`ArrayList`；Python：`list` / `dict` / `set` | Java：`String`、`Integer` 等包装类、`BigDecimal`；Python：`str` / `tuple` / 数字 |
| 线程安全  | 需要加锁等同步手段                                                          | **天然线程安全**，可以自由共享                                                     |
| 作为哈希键 | 有风险（修改后 hash 变了就找不到）                                               | 安全，`hashCode` 可以缓存                                                    |
| 代价    | 修改没有额外开销                                                           | 每次修改都新建对象，有内存与性能开销                                                    |

**怎么实现一个不可变对象**：类声明为 `final`；所有字段 `private final`；不提供 setter；构造时对可变类型做**防御性拷贝**，不把内部可变引用暴露出去。

易错点：Java 的 `final` 只保证**引用不可变**，不保证被引用对象的内容不可变。

> [!tip]+ 面试一句话  
> 不可变对象 = 创建后状态不可改（典型是 `String`），好处是**线程安全、可安全共享、可做哈希键、可缓存**，代价是频繁修改会产生大量临时对象——所以字符串拼接要用 `StringBuilder`。

## 5. 软件测试 ⭐⭐⭐

> [!note]+ 章节导引  
> **本章知识点之间的关系**：测试回答"做对了没有"。逻辑链：**测试方法**（白盒 vs 黑盒）→ **是否执行程序**（静态 vs 动态）→ **覆盖强度**（语句→路径）→ **测试层次**（单元→集成→系统→验收）→ **测试流程**（计划→用例→执行→报告）→ **修改之后怎么办**（回归测试）。
>
> **与上一章的关系**：测试验证设计是否正确实现——上一章产出的代码，本章负责证明它是对的。
>
> **与学科的关系**：白盒/黑盒、静态/动态、覆盖率和测试流程几乎年年被问，属于"背了就能答满"的题。

### 5.1 白盒 vs 黑盒 ⭐⭐⭐

- **白盒测试**：知道程序内部结构，按**内部逻辑**设计用例，又称结构测试、逻辑驱动测试。
- **黑盒测试**：不管内部结构，只依据**需求规格说明书**从输入输出角度验证功能，又称功能测试、数据驱动测试。

|         | 白盒测试          | 黑盒测试          |
| ------- | ------------- | ------------- |
| 知道内部结构？ | **是**         | 否             |
| 关注点     | 逻辑覆盖          | 功能正确性         |
| 方法      | 语句/分支/路径/条件覆盖 | 等价类划分/边界值/因果图 |
| 时机      | 单元测试          | 系统测试          |

### 5.2 静态测试 vs 动态测试 ⭐⭐⭐

|        | 静态测试                                       | 动态测试                       |
| ------ | ------------------------------------------ | -------------------------- |
| 是否运行程序 | **不运行**                                    | **运行**                     |
| 测试对象   | 代码、文档、模型（需求规格、设计图）                         | 可执行程序                      |
| 方法     | 人工审查（代码评审、走查、桌面检查）+ 静态分析工具（lint、SonarQube） | 按白盒/黑盒方法设计用例执行，比较实际输出与预期输出 |
| 优点     | 做得早（需求/设计阶段即可）、发现缺陷的成本低                    | 能验证真实运行行为（性能、并发、异常）        |
| 缺点     | 无法验证运行期行为                                  | 依赖环境，缺陷发现得晚                |

> [!tip]+ 面试一句话  
> **静态测试不跑程序**——审查代码/文档、用静态分析工具找问题；**动态测试要跑程序**——执行用例看输出。注意"白盒/黑盒"是按**是否知道内部结构**分，"静态/动态"是按**是否执行程序**分，是两个不同维度，别混着答。

### 5.3 覆盖率递增 ⭐⭐⭐

$\text{语句覆盖} < \text{判定覆盖} < \text{条件覆盖} < \text{判定/条件覆盖} < \text{路径覆盖}$

> [!tip]+ 面试一句话  
> 语句覆盖最弱（每个语句至少执行一次），路径覆盖最强（每条路径都走一遍）。

### 5.4 测试层次 ⭐⭐

| 层次       | 对象    | 方法                        |
| -------- | ----- | ------------------------- |
| **单元测试** | 单个模块  | 白盒为主                      |
| **集成测试** | 模块间接口 | 增式（自顶向下 / 自底向上 / 三明治）与非增式 |
| **系统测试** | 整个系统  | 黑盒为主                      |
| **验收测试** | 用户验收  | α 测试（开发者环境）/ β 测试（用户环境）   |


> [!tip]+ 测试 vs 调试  
> 测试=**找 bug**（系统化、可规划），调试=**修 bug**（分析定位修复）。测试证明有错，调试消除错误。

### 5.5 单元测试 ⭐⭐⭐

**定义**：对软件中**最小可测试单元**（函数 / 方法 / 类）进行的测试，通常由**开发者自己编写**并随代码一起维护，是测试体系的最低一层。

要点：

- 一般**以白盒方法设计用例**（语句/分支/路径覆盖），辅以黑盒的边界值；
- 被测试单元若依赖尚未完成的模块，用**桩模块（Stub）**顶替被调用的下层模块，用**驱动模块（Driver）**模拟上层调用者；
- 常用框架：JUnit / TestNG（Java）、pytest / unittest（Python）、GoogleTest（C++）；做法是"准备数据 → 调用被测方法 → 断言结果"；
- 地位：**持续集成（CI）**中每次提交都要自动跑的第一道防线，也是重构的安全网。

> [!tip]+ 面试一句话  
> 单元测试 = 针对**最小可测单元**（函数 / 类）的测试，**开发者自己写、白盒为主、用桩和驱动隔离依赖、用断言判定对错**；它跑得快、定位准，是 CI 里最核心的自动化测试。

### 5.6 软件测试的流程 ⭐⭐⭐

| 步骤              | 做什么                                  | 产出        |
| --------------- | ------------------------------------ | --------- |
| **1. 需求分析**     | 分析需求是否可行、是否可测，梳理出测试点                 | 测试需求      |
| **2. 编制测试计划**   | 确定测试范围、策略、资源、进度、环境                   | 测试计划      |
| **3. 编写测试用例**   | 用等价类/边界值/覆盖准则设计用例并评审（用例是**指导测试的文档**） | 测试用例、测试数据 |
| **4. 执行测试**     | 搭环境跑用例，**提交缺陷**、跟踪修复、做**回归测试**       | 缺陷单、测试记录  |
| **5. 编写测试总结报告** | 统计缺陷与覆盖率，判断是否达到出口准则                  | 测试总结报告    |

配套两点：缺陷生命周期 = **提交 → 指派 → 修复 → 验证 → 关闭**（没修好则**重开**）；整体顺序按"**单元 → 集成 → 系统 → 验收**"递进。

> [!tip]+ 面试一句话  
> 测试流程五步：**需求分析 → 测试计划 → 测试用例 → 执行测试（提交 bug + 回归测试）→ 测试总结报告**；其中写用例是核心，因为用例质量直接决定测试的有效性。

### 5.7 回归测试 ⭐⭐⭐

**定义**：产品修正了缺陷或增加了功能后生成新的版本，对**这个新版本**重新进行测试，就叫回归测试。

**作用**（两条，务必都答）：

1. **验证原有错误是否确实被修正了**——确认修复真的生效；
2. **发现因修改而可能引入的新错误**——改动常常"修好一个、弄坏一个"，回归测试是防止老功能退化的安全网。

补充：

- 触发时机：修复缺陷后、新增功能后、重构后、运行环境或依赖变更后；
- 范围策略：全量回归（慢但保险）vs 选择性回归（基于**影响分析**挑出受影响模块和用例）；
- 落地关键：回归测试**必须自动化**，把回归用例固化成脚本并接入 CI，否则成本高到做不动。

> [!tip]+ 面试一句话  
> 回归测试 = 出新版本后"**把以前测过的再测一遍**"，作用是**确认旧缺陷已修复 + 发现修改引入的新缺陷**；因为它代价高，所以工程上一定要自动化。

## 6. 软件维护 ⭐⭐

### 6.1 软件维护的四种类型 ⭐⭐

| 类型        | 占比       | 说明       |
| --------- | -------- | -------- |
| **完善性维护** | 最多(50%+) | 增加新功能    |
| **适应性维护** | 20%+     | 适应环境变化   |
| **改正性维护** | ~20%     | 修复缺陷     |
| **预防性维护** | 最少       | 提前改善可维护性 |

| 测试 vs 调试     | 测试=找bug，调试=修bug                                          |
| 维护四类型        | 完善(加功能) > 适应(改环境) > 改正(修bug) > 预防                        |
